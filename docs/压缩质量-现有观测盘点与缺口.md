## 2. 现在**看不见**的（真正的缺口）

| 缺口 | 后果 | 能不能自动测 |
|---|---|---|
| **压缩后关键信息还在不在**（约束 / 失败边 / 根目标） | 只能靠人工看摘要，或事后发现 agent 重复踩坑 | ✅ 能：从 graph 机械抽取 vs 摘要文本做**召回率**，零模型调用 |
| **压缩后 agent 还能不能干活** | 只有手写 `real-*.mjs` 脚本、人工判读 | ⚠️ 半自动：用小模型问三个固定问题（目标/试过什么/下一步），判分可规则化 |

| **降级档位分布**（L0–L5 各占多少） | 只知道"超没超预算"，不知道"常年停在 L3 意味着什么" | ✅ 能：`renderLedger` 已返回 `level`，只是没落盘 |

## 4. 评估体系的分层设计（草案）

> 分层原则：**越便宜越频繁**。每次 fold 都跑的东西必须零模型调用、<10ms。

### L1 · 每次 fold（零模型调用）

| 指标 | 定义 | 阈值 / 判据 |
|---|---|---|
| `provenanceCoverage` | 边行带 `(seq …)` 的比例 | 必须 = 1 |
| `ledgerBudget.fallback` | 热清单三态 | `impossible` = error；`over-budget` 连续 N 次 = warn |
| `constraintRecall` | 图里的约束条数 ÷ 摘要「目标」段里的约束条数 | 必须 = 1（少一条就是丢任务）|
| `failureRecall` | 本次 fold range 内的失败边数 ÷ 摘要失败清单行数 | 必须 = 1 |
| `compressionRatio` | `shadowedTokens ÷ summaryTokens` | 记录趋势，不设硬阈值 |
| `foldThrash` | 连续两次 fold 间隔 < 30 事件 | ≥2 = warn |

### L2 · 每小时 / 每日（轻量模型，可选）

| 指标 | 做法 |
|---|---|
| `resumeProbe` | 拿压缩后的历史问 3 个固定问题（目标 / 哪些做法失败过且为什么 / 当前在哪），用规则判分（关键字命中 + 条目数） |
| `hallucinationProbe` | 摘要里出现的节点/边 id 必须能在 `graph.json` 里找到（零模型，纯核查） |

### L3 · 发版前（真实任务，最贵）

| 指标 | 做法 |
|---|---|
| `realTaskContinuity` | 跑 `test/real-*.mjs` 里的真实会话，压一次后让 agent 继续做一件小事，看成败 |
| `revertEquivalence` | fold 后按 `foldMarks` 区间反查原文，必须逐字命中 |

## 5. 落地顺序建议

1. **L1 的 `constraintRecall` / `failureRecall`** —— 零成本、直接对应"压缩最该保的东西"，优先级最高；
   现成的机械抽取（`collectConstraintText` / `failureEdges`）已经在了，只差一次计数比对。
2. **`compressionRatio`** —— `foldMarks` 加一个 `summaryTokens` 字段即可（属于 graph schema 变更，需契约先行）。
3. **降级档位落盘** —— `renderLedger().level` 已经在返回值里，只差写进 `ledger-budget.json` 的直方图。
4. `resumeProbe`（L2）—— 等 L1 稳定后再做，避免"指标没建好就开始花模型钱"。

## 6. 明确不做

- 不用 ROUGE/BLEU 类"摘要像不像原文"的指标 —— 我们要的是"下游还能不能干活"，不是"摘要好不好看"。
- 不做跨会话的压缩质量对比（越界：那是记忆系统的事）。
- 不把评估结果塞进热清单（会让压缩产物为评估服务，本末倒置）。

## 7. 真实 ROI：一次 fold 到底值不值（2026-11-01 live 实测）

**数据**（`<home>/chess-context/sessions/*/graph.json` 的 foldMarks，共 3 次）：

| # | 遮蔽 token | 摘要 in | 摘要 out | 压前≈ | 压后 | 遮蔽÷输出 | 耗时 |
|---|---|---|---|---|---|---|---|
| 1 | 112,024 | 178,750 | 2,310 | 385,765 | 273,741 | **48.5×** | 16.4 s |
| 2 | 81,941 | 133,852 | 3,004 | 355,546 | 273,605 | **27.3×** | 19.0 s |
| 3 | 83,044 | 118,992 | 362 | 300,818 | 217,774 | **229×** | 5.0 s |

**两种算法，结论相反，必须都写清楚**：

| 算法 | 结果 | 说明 |
|---|---|---|
| 只看「省下的常驻上下文 − 摘要输出」 | **+271,333 tok**（净赚） | 这是**每次后续请求**都能省的量，按请求数放大 |
| 再把「摘要读入成本」也扣掉 | **−160,261 tok**（净亏） | 摘要模型要把被遮蔽的内容**再读一遍**（in 431,594 tok），这是**一次性**成本 |

**正确的判断方式**：摘要读入是一次性成本，上下文节省是**每次请求**的收益。设后续还有 N 次请求：

```
总收益 = N × 遮蔽量 − 摘要读入 − 摘要输出
回本请求数 N* = (摘要读入 + 摘要输出) ÷ 遮蔽量
```

按上表三次的实测值：`N* ≈ (431,594 + 5,676) ÷ 277,009 ≈ 1.58` ⇒ **再跑 2 次请求就回本**，之后全是净赚。
（真实会话一次 fold 后通常还有几十次请求，所以**经济上成立**。）

**但有两个必须盯住的前提**：

1. **摘要读入成本随遮蔽量线性增长**。如果 fold 被触发得太频繁（如 `foldThrash` 所示），
   每次都要重读一大段，`N*` 会迅速上升 —— 这正是「压缩无效」在经济上的样子。
2. **压缩比 229× 的那次（#3）值得单独看**：83k 遮蔽 → 362 tok 摘要。我们核过它的 `fallback: null`
   （走的是模型，不是规则模式），且摘要长度符合指令里的硬预算（「约 40 字符/死路 + 600 字符其它」）。
   **所以这不是 bug，是指令设计的结果** —— 但它说明：**摘要本身很薄，信息主要在图与热清单里**。
   ⇒ 任何「只看摘要好不好」的评估都会低估 GOkifu；评估必须同时看 `graph.json` 的节点/边/失败边。

**记录项**：建议把 `compressionRatio`（遮蔽 ÷ 摘要输出）与 `N*`（回本请求数）都落进 `foldMarks`，
这样「这次压缩划不划算」不需要事后手算。
