# 重启后验证清单

> 本插件已装进 `profiles/desktop` 与 preset `personal-assistant`，但**没有重启 DSH 验证过**
> —— 本会话不能重启自身。重启后按下面四条逐项确认；任何一条不过，先回滚再排查。

回滚（一行）：

```bash
cd D:/主工作区/projects/dsh-gokifu-compact && node test/rollback.mjs
```

---

## ① 插件加载成功（不是静默失败）

重启后看启动日志 / 控制台，应当**没有**这些字样：

```
service "compaction" has been registered at        ← 双实例（旧行没换掉）
Preset services require isolate realms             ← 行被挪出 group
Cannot find package 'dsh-gokifu-compact'            ← junction 或依赖没解析到
```

有任何一个 ⇒ 回滚，然后按对应项修。

> 静默失效面：`cordis.patch.yml` 的 patch 打不中目标时**只 warning 不报错**（`dsh-app-boot/lib/index.js:78-101`）。
> 所以「启动没报错」不等于「插件挂上了」—— 必须看下面第②条。

## ② 引擎真的接管了 compaction

新建一个会话，问 agent：`/compact`

| 期望 | 实际含义 |
|---|---|
| 返回「压缩了多少历史项 / 估算节省 token」且**没有**报 `no compaction service` | `ctx.compaction` 是我的引擎 |
| 报 `ManualCompactionError: busy` | agent 忙，等空闲再试（正常） |
| 报 `no compaction service` 或命令不可用 | 引擎没挂上 ⇒ 回滚 |

再看会话的 `compaction/start` / `compaction/summary` 事件是否出现在日志里（正常压缩的痕迹）。

## ③ 棋谱落盘

任一会话跑过几步之后：

```bash
ls "D:/DeepSeek Harness/home/chess-context/sessions/"
```

- 应出现 `<sessionId>/graph.json` 与 `graph.md`
- `graph.json` 里 `nodes` 至少有一个 `kind: "user"`（你的第一条消息，**逐字**）
- `graph.md` 打开能看到 `## n1 · USER`、`## n2 · STATE`、以及 `- **e1** … ⇒ failure` 这类行

若目录不存在：说明 keeper 的 `session/event` 没跑（插件没挂）或写盘失败（看 logger.warn：
`chess-context: 棋谱落盘失败`）。

## ④ 失败记忆与热上下文

造一次失败：让 agent 跑一个必然失败的命令（例如在空目录执行 `npm test`），然后在**同一个会话**里
发一句「刚才为什么失败？」。

| 期望 | 判据 |
|---|---|
| 下一条请求里出现 `<chess-ledger>` 块 | 在会话日志的 `user/message` 事件里搜 `chess-ledger` |
| 块里有 `PROVEN DEAD ENDS` 与那条失败的命令 | 同上 |
| 再跑一次同样的失败命令时，模型不重复盲试 | 行为观察（非硬判据） |

## ⑥ v0.1.2 修复的四个观察点（重启后应看到的变化）

| 观察点 | v0.1.0（旧） | v0.1.2（新） |
|---|---|---|
| `graph.json` 的 user 节点 | 含 `<hindsight_knowledge>` / `<system-reminder>` | **只有真人消息**（source.kind = user） |
| failure 边数量 | get_goal / read / skill 等只读工具大量误报 | 只保留**真失败**（exit≠0 / isError / ENOENT） |
| 落盘延迟 | 最长一个 25 事件窗口 | 变化后 ≤1.2s |
| 热上下文 tokens | 失败边多时线性膨胀 | 受 `hotLedgerMaxTokens` 硬约束（默认 500，L4 允许 ~12% 超） |

## 若 ① 通过但 ④ 不通过

按顺序排查：

1. `graph.json` 是否在长（说明落账在跑）
2. `graph.json.edges` 里是否有 `result: "failure"` 的边（判定是否触发）
   - 没有 ⇒ `src/verifier.mjs` 的判定规则没匹配上你的工具输出格式 —— 把原始输出贴进
     `test/verifier.test.mjs` 加一条用例，改规则（这是预期内的进化点）
3. `graph.json` 有失败边但没注入 ⇒ `hotLedger` 是否为 true；`runtime.lastLedgerDigest` 是否被
   误判为「已可见」（`alreadyVisible` 只扫 surface 尾部 40 个节点）

## 计量口径提醒

- 本插件的日志行 `chess-context: fold #N 遮蔽 seq a-b (~X tokens) → 总 Y tokens` 是判断是否真的 fold 的依据。
