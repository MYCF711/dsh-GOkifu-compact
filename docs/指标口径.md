# 指标口径：README 上每个数字从哪来、算的是什么

> **为什么单独一页**：README 是给第一次来的人看的，它只该说「这东西怎么样」；
> 而「这个数是怎么算的、分母是谁、什么时候测的」属于审计语言 —— 混在一起会让新人卡在第二段。
>
> **规矩（本仓踩过 4 次）**：每个数字都必须带 **定义式 + 分子 + 分母 + 时点**，缺一维视为不可引用。
> 跨批不可比。**没有数字的不进结论表**（那只是观点）。

## 一 · 热清单 token：417 是什么、不是什么

### 1.1 417 的口径

| 项 | 值 |
|---|---|
| 数字 | **417 tokens** |
| 夹具 | **2000 边合成夹具**（2001 节点 / 1201 失败边） |
| 档位 | **L5 降级档**（预算不够时的最低档） |
| 复跑 | `node scripts/bench-repro.mjs` |
| 落盘 | `evidence/bench-2000.json` 的 `ledgerTokens` |
| 权威常量 | `scripts/bench-repro.mjs` 的 `EXPECTED_TOKENS = 417`（**改基线就改这里**） |

> ⚠ **它不是「真实会话的平均值」**，是**合成夹具在降级档下的上界形状**。
> 任何把它当"典型会话开销"的说法都不准确 —— 真实分布见下一节。

**基线演进**（`bench-2000.json` 里只有现值，历史在 CHANGELOG）：
`↻k` 重试计数 **+1** → 图例单行化 **−1** → 同类失败标记汇总 **−16** → 清冗余指针 **−15** = **417**。

### 1.3 两套 token 口径并存（别混用）

| 口径 | 谁在用 | 怎么算 |
|---|---|---|
| **宿主 `ctx.tokenMeter.measure(session)`** | **会话压力 / fold 触发**（`thresholdRatio` / `growthFloorTokens` 作用在它上面） | 宿主自己的分词器 |
| **本仓加权估算 `ledger.estimateTokens`** | **热清单的硬预算**（`hotLedgerMaxTokens`，默认 500） | **CJK 1 token/字 + 其余 1/4 token/字**（ASCII 侧对齐宿主 `dsh-token-meter` 的 `CHARS_PER_TOKEN = 4`；全角标点算 CJK） |

**为什么热清单要自己算**：它是**硬预算**，宁可按上界估（超了就降档），也不能低估。

**这条公式怎么校准的**（1.13.0）：

- 锚点：一条 **2478 字符**的真实热清单（418 汉字 + 2060 ASCII），网关 `usage` 实测 **905 tokens**；
- 旧口径（`chars/3`）给 **826（−8.8%）**；新口径给 **933（+3.1%）**；
- 归档 **176 会话**复算：avg **412.40 → 417.88**、max **826 → 933**、over-500 **25 → 25**；
- **只换公式不重渲染**会是 over **56** ⇒ 旧口径那 25 张里有 **31 张靠低估撑出来**；
- **只有这一个有真实网关 usage 的样本** —— 要做全量对照得跑 `node scripts/token-calib.mjs`（未做）。

> 相关外研：`docs/knowledge/token计量官方比例-deepseek.md`。

## 四 · 落盘与回滚的口径

`graph.json` 从 **1.9.2** 起不再代表「最新状态」，而是「上一回合基线 + 当前增量」：

| | 每次都重写整图（≤1.9.1） | 增量落盘（1.9.2 起） |
|---|---|---|
| `graph.json` | 最新 | 上一个**回合边界**的完整基线 |
| `graph.json.delta.jsonl` | — | 本回合的增量帧（带 `baseHash` + `checksum31`） |
| 最新状态 | 直接读 | **基线 + 增量合并** |

**写放大**（三张真实图 × 60 步 + 1 回合边界）：
`e16faf2b` **×80.16 → ×37.41** · `d393944b` **×70.04 → ×33.31** · `5acafe42` **×61.75 → ×30.75**。
**fold 后 flush**：5 / 20 / 100 dirty = **8–12.7 / 18.9–47.8 / 55.4–95.3 ms**（改前全量 429–836 ms）。

**三条已知余量**（选型时要知道，别当已解决）：

1. **短回合写放大**：每回合边界落一份完整基线（0.5–0.6 MB）。真实分布 p50 = **40 步/回合**
   ⇒ 写放大 ≈ **×20–25**；但**极短回合（<10 步，p10 = 13.9）**摊销不足，写放大仍可能 **>×50**。
2. **dirty 数极大时收益收窄**：dirty > 100 的 flush 需实测，不是线性。
3. **`appendFileSync` 的原子性依赖 OS**：本机 NTFS 上 1 KB 级追加已过半写测试；
   **跨平台（尤其网络文件系统）未验证**。

**崩溃安全**：每帧带 `baseHash`（generation）+ `checksum31` —— 半写帧解码时就地停止，
加载时把 delta 截到最后一条好帧；**旧 generation 的帧整体忽略**。

## 六 · 怎么判断「这个结论还能不能引」

1. **看时点**：文件里的「生成于 / 当次输出」时间戳比文件 mtime 可信（`git checkout` 会刷 mtime）；
2. **看分母**：比例必须能说出分子和分母（「超预算 3/24」而不是「超预算 12%」）；
3. **看是否是生成物**：标了「自动生成，勿手改」的只认复跑命令；
4. **看有没有消费者**：本仓的纪律是「**没有消费者的指标不许进代码**」——
   一个数如果没人读它，它为什么存在，就该被问一次。
