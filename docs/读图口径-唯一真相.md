# 读图口径：只有一份真相（2026-11-02）

> 这份文档只讲一件事：**从磁盘读棋谱图时，必须走哪个入口**。
> 它存在的原因不是理论洁癖 —— 同一条错误**在 live 上发生了五次**，每次都让「证据」与「真相」对不上。

## 规则（一句话）

**任何从磁盘读 `<DSH_HOME>/chess-context/sessions/<sid>/graph.json` 的代码，都必须：**

| 场景 | 唯一入口 |
|---|---|
| 运行期（插件内部） | `kifu-persist.load()`（`createPersistStore(...).load(...)`） |
| 脚本 / 诊断 / 证据生成 | `scripts/graph-audit.mjs` 的 **`loadSessionGraph(file)`** |

两者做的是同一件事：**读基线 `graph.json` → 重放 `graph.json.delta.jsonl` → 得到"当前图"**。
绕过它们、直接 `JSON.parse(readFileSync(...))`，看到的是 **fold 之后的增量之前** 的旧图。

**判据**：`test/fold-mark-sites.test.mjs` 的 C183 静态守卫 —— 脚本目录里除 `graph-audit.mjs` 自身外，
不许出现 `fromJSON(nodeFs.readFileSync(...))` 的裸用法。

## 为什么这错误特别隐蔽

1. **基线本身是合法的** —— `JSON.parse` 不会报错，读到的是「某个时刻」的完整图；
2. **两者只在 fold 之后分歧** —— 刚 fold 完的会话差异最大，恰好是所有人都在看的那个；
3. **它让门禁说谎** —— handoff-check 报「FAIL 0 / WARN 5」，其中 5 条 warn 是尺子读错数据；
4. **它不对称** —— 漏掉的通常是「新增」的那部分（节点/边/foldMark），所以数字永远**偏低**，看起来像「没问题」。

- **不要**为了「省一次 IO」把 `loadSessionGraph` 换成裸读 —— delta 里可能有整段新节点；
- **不要**在**有非空 delta** 的会话上改写基线（C188 的坑：`--repair-foldmarks` 因此加了拒绝逻辑）；
- **不要**在没有备份的情况下跑任何写 `home/chess-context/` 的命令。
