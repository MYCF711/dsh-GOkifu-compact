## 一 · 目标（会变，随手改）

- 让「棋谱」这一层真正对模型有用 —— 不只是压缩器，而是**压缩后还能告诉模型「哪些路走过、结果如何、为什么」**。
- ~~把版本号推到 2.x~~ → 划掉（2026-10-29 R2）：版本号不产生价值，先修信息质量与工程闭环。
- 每个优化都要能**单独测试、单独验收、尽量单独卸载**（主人的「一个房间一个房间装修」纪律）。
- 不允许为了优化引入新的常驻成本（每步开销必须仍在亚毫秒级、热清单仍在一屏内）。

当前量化起点（实测，详见审计 §七）：
`135 tests / 0 failed`、`323 tokens 热清单 / 0.463 ms`、`33 次 fold / 264 万 token 遮蔽 / 0 失败（今日）`、`624 自环 = 5.9% / 2 个坍缩图`。

## 二 · 设想（R1 全量发散，好的坏的都写）

> R1 纪律：这一轮**不做取舍**。下面 24 条都先写下来，好坏在 R2 判。

### 设想 A · 图不变量守卫
- 内容：`test/verify-graphs.mjs` 增加硬不变量：① 自环边 = 0；② 边/节点比 ≤ 1.5；③ 坍缩图 = 0。违反即退出码 1，并作为提交门禁。
- 好处：1.9.1 修的 bug 从此有回归判据；不用真机就能发现同类坍缩。
- ⚠ 坏处 / 代价：老图会一直红，必须先把 2 个历史图洗掉，否则门禁永远失败。
- **状态**：候选

### 设想 B · 清理 2 个历史坍缩图
- 内容：`node test/rewash-selfloop.mjs --apply`，把 624 条自环边的 `to` 置 null（保留边与结果）。
- 好处：dead/redundant 标记在这两个会话上恢复可信；`verify-graphs` 可转绿。
- ⚠ 坏处 / 代价：改写历史数据（有备份机制，dry-run 默认）；洗完后这两个会话的置换关系会比真实情况稀疏。
- **状态**：候选

### 设想 C · `weak-success`（只读工具弱成功）
- 内容：`read` / `glob` / `grep` 成功返回且无错误行 ⇒ 记 `weak` 信号（`verify.kind='read-ok'`），**只用于 `WORKING:` 路径推断，不进「已验证事实」段**。
- 好处：直击评估报告 C-2 的 88% `unverified`；热清单里「我试过什么、哪些成了」不再长期缺席。
- ⚠ 坏处 / 代价：只读成功不等于目标达成，可能让 WORKING 路径出现「读了一眼」的假进展；必须限定它只影响路径排序，不影响 success 统计。
- **状态**：候选

### 设想 D · 压缩降级可见
- 内容：摘要三层降级到「规则摘要」时，在热清单/checkpoint 里显式提示 `⚠ 上次摘要是规则生成（无模型润色）`；连续失败已有提示（1.9.1），补上「降级」这一档。
- 好处：评估报告 B 扣分点 2 的直接修复；用户/模型知道自己正在看低质量摘要。
- ⚠ 坏处 / 代价：每步多一行（约 20–30 tokens）；需要把「上次 fold 模式」持久化到 graph。
- **状态**：候选

### 设想 E · `minFoldTokens` 随窗口缩放
- 内容：`max(8000, 窗口 × 0.08)`；小窗口不再 1.2 步一 fold。
- 好处：评估报告 A/D 都点了名：小窗口 fold 后 prompt 反而 +749~+2,679，净亏。
- ⚠ 坏处 / 代价：窗口大的会话 fold 更晚触发，峰值上下文会略高。
- **状态**：候选

### 设想 F · `TRACE` 行具体化
- 内容：热清单的 `TRACE:` 不再只写路径，补「最近 3 个节点：n12 改缓存 / n15 跑测试 / n18 定位」。
- 好处：今日评估说三层树使用率只有 1 次/天 —— 模型不知道该去查什么；给出节点 id 就能按需 read。
- ⚠ 坏处 / 代价：约 30–50 tokens；节点多时要做预算截断。
- **状态**：候选

### 设想 G · `graph.json` 增量落盘
- 内容：新增 `src/store.mjs`：append-only journal + 周期 snapshot，替代每次 1.41 MB 全量重写。
- 好处：E 维度唯一的扣分点；5,000 边时 IO 线性成本可削。
- ⚠ 坏处 / 代价：引入双格式（journal + snapshot）和恢复逻辑，复杂度显著上升；当前 1.41 MB/3.6 ms 并不痛。
- **状态**：候选（低优先级）

### 设想 H · 冷缓存首折削峰
- 内容：首折阈值单独配置（`firstFoldRatio`，默认低于 0.45），让第一次 fold 在更小上下文上发生。
- 好处：把 62.9 万全新输入的尖峰摊薄。
- ⚠ 坏处 / 代价：首折次数变多、摘要总成本可能上升；收益依赖缓存命中率，难量化。
- **状态**：候选（低优先级）

### 设想 I · 真实链路门禁
- 内容：`npm run test:real` 串起 `real-modules → real-fold → replay-verify`，并在 AGENTS.md 的提交清单里注明「改动 engine/graph 时必须跑」。
- 好处：补 R7：单测全绿 ≠ 真实链路可用（P0 就是这么躲过去的）。
- ⚠ 坏处 / 代价：需要 asar 提取闭包、耗时长；`replay-verify` 依赖本机会话日志，换机器不可复现。
- **状态**：候选

### 设想 J · 发布链修复
- 内容：给 1.3.5–1.6.3、1.9.0、1.9.1 共 10 个版本补 tag；npm 发 1.9.1 稳定版；README 版本号同步。
- 好处：`check-maintenance` 现在退出码 1；用户拿不到新版。
- ⚠ 坏处 / 代价：补 tag 会改历史（推 tag 需要主人授权）；npm 发布不可撤回。
- **状态**：候选（需主人授权，本阶段禁止提交/推送）

### 设想 K · 安装器 `link:` 路径修复
- 内容：`scripts/install.mjs` 写 `link:` 时用真实项目路径；`test/verify-install.mjs` 增加「link 目标存在」检查（现在只查字符串前缀，假绿）。
- 好处：现在 profile 里写的是不存在的 `D:/主工作区/projects/dsh-gokifu-compact`，重装即坏。
- ⚠ 坏处 / 代价：改 profile/package.json 属于动主人正在用的实例，必须备份 + 重启才生效。
- **状态**：候选

### 设想 L · 文档同步
- 内容：README 顶部版本改 1.9.1/1.8.1 事实；`docs/计划表.md` 标注「已归档，见根目录计划表.md」；HANDOFF 顶部「必须重启」改为当前状态。
- 好处：下一个会话不会被过期文档误导。
- ⚠ 坏处 / 代价：纯文档，零风险。
- **状态**：候选

### 设想 M · `nodes/*.md` 按需渲染
- 内容：不再每次 flush 全量写 `nodes/<id>.md`，改成模型 read 时按需生成。
- 好处：减少 IO。
- ⚠ 坏处 / 代价：`read` 一个不存在的文件会失败，破坏「三层树可读」契约；要改默认工具行为，风险高。
- **状态**：候选（低优先级）

### 设想 N · 重踩失败实时告警
- 内容：当新动作与历史失败边语义相似时，热清单里追一句「这条你试过（e12）」。
- 好处：今日评估「重复已知失败动作 6.0%」还能再降。
- ⚠ 坏处 / 代价：相似度判定要么靠规则（误报）要么靠模型（成本）；6% 已经不高，收益边际。
- **状态**：候选（低优先级）

### 设想 O · 压缩质量自动评分
- 内容：每次 fold 后机械统计「失败边保留率 / 约束保留率 / 摘要压缩比」，写进 graph 的 `foldMarks`，doctor 展示趋势。
- 好处：把「摘要质量」变成可回归指标，而不是靠人读。
- ⚠ 坏处 / 代价：保留率只能按「文本里是否出现」粗判，可能奖励「把原文全抄一遍」。
- **状态**：候选

### 设想 P · 只读型会话关掉 dead 判定
- 内容：检测到会话几乎全是只读工具时，不输出 `dead` / `redundant` 标记。
- 好处：避免错误标记伤害模型。
- ⚠ 坏处 / 代价：治标不治本 —— 根因已由 1.9.1 修复；关掉功能等于放弃棋谱核心价值。
- **状态**：~~已否决~~（见 §三 第 1 条）

### 设想 Q · 用 SQLite 存图
- 内容：`graph.json` 换成 SQLite（better-sqlite3 / node:sqlite）。
- 好处：增量写、查询快。
- ⚠ 坏处 / 代价：引入原生依赖（Electron 版本绑定）；`graph.json` 是「可读、可备份、可人查」的设计资产；单文件卸载性变差。
- **状态**：~~已否决~~（见 §三 第 2 条）

### 设想 R · 把 `graph.mjs` 拆成多文件

- ⚠ 坏处 / 代价：典型的「按技术层装修」；拆完接口更多、单测要跟着搬，没有任何独立验收价值。

### 设想 S · 引入 `tokenlens` 做 token 计数

- **状态**：~~已否决~~（见 §三 第 4 条）

### 设想 T · 接入 token 级压缩（LLMLingua / ACON）
- 内容：token 级压缩历史。
- 好处：压缩率更高。

- 内容：把棋谱画成图，支持拖拽/编辑。
- 好处：人看着爽。

### 设想 X · 跨会话全局失败库
- 内容：所有会话共享一张「已知失败」表，新会话直接看到。
- 好处：同类任务不重踩。
- ⚠ 坏处 / 代价：不同项目的失败原因不可迁移，容易污染；隐私边界模糊。
- **状态**：候选（先证明单会话失败记忆有效，再谈跨会话）

### 设想 Y · 失败边「一句话原因」强制非空
- 内容：`errorSnippet` 为空的失败边，落账时用 `verify.summary` 兜底，禁止空原因。
- 好处：热清单里「失败但不知道为什么」是最没用的一类。
- ⚠ 坏处 / 代价：兜底文本可能误导；需要区分「真没输出」与「抽取失败」。
- **状态**：候选（可并入 C 的实现一起验收）

### 设想 Z · 每步热清单 A/B 基建

- ⚠ 坏处 / 代价：夹具要维护两份渲染器，容易腐化。
- **状态**：候选

## 五 · 决定（R3 收敛 + R4 切片后的结果）

| # | 决定 | 依据 |
|---|---|---|
| 1 | 先做 **S1 图不变量守卫 + 历史坍缩图清理**，作为第一个切片 | 零模型成本、完全离线可测、直接恢复 dead/redundant 可信度；且后续所有「棋谱质量」指标的度量前提是图干净 |
| 2 | 第二个切片做 **S2 `weak-success`**（只读工具弱成功，只影响 WORKING 路径） | 评估报告 C-2：88% 的边是 unverified，是当前「给模型的信息」最大缺口 |
| 3 | 第三个切片做 **S3 降级可见**（规则摘要提示） | 评估报告 B 扣分点 2；成本仅一行 tokens |

### 9.2 新设想（R5 发散，好坏都写）

**AA · 滚动修复（三层容器）**
- 内容：`page{height:100%;min-height:0;overflow:hidden}` + `pageScroll{flex:1;min-height:0;overflow:auto}` + `pageContent{max-width:980px;margin:auto;padding}`。
- 好处：与官方同槽页面（`TaskManagerPage`）形态一致，后来者可以照抄；不动宿主。
- ⚠ 代价：`scrollbar-gutter:stable` 会让内容窄约 9px ⇒ 参数行三列网格要复验 900px 视口。
- **状态**：候选 → **采纳为 M1**

**AB · 摘要模型三态（跟随 / 注册 / 外部）**
- 内容：`summarizationMode` 枚举 + 各自独立面板；默认 `follow`。
- 好处：把「零配置能跑」与「我要指定」两种需求分开表达；三态语义不同，互斥但可回退。
- ⚠ 代价：新增一个配置键，`sanitizePatch` / `parseEngineBlock` / UI 三处都要同步，漏一处就静默丢值。
- **状态**：候选 → **采纳为 M2-1 / M2-2**

**AC · 外部 OpenAI 兼容 API 作为独立文件 + 动态 import**
- 内容：`src/external-summary.mjs`，只在 `summarizationMode === 'external'` 时 `await import()`。
- 好处：不用它的人**物理上不加载**这段代码；删文件不影响任何既有路径。
- ⚠ 代价：动态 import 让「首次调用」多一次模块解析（可忽略）；错误分类要自己写（auth/http/timeout/empty）。
- **状态**：候选 → **采纳为 M3-1 / M3-2**

**AD · 每次 fold 的可观测行**
- 内容：`foldMarks[]` 增 `route` / `fallback` / `ms` / `usage`；页面出表；`doctor` 显示最近 5 次。
- 好处：M2/M3 的效果**只能靠它看见**；没有它，「换了模型有没有变好」永远只能靠感觉。
- ⚠ 代价：`foldMarks` 随会话增长 ⇒ 必须只留最近 20 条，否则 `graph.json` 继续变大。
- **状态**：候选 → **采纳为 P2-2**

**AE · 同日志对比（`scripts/compare-models.mjs`）**
- 内容：同一段 `session.v4.jsonl.zstd`、同一 fold 切片、同一 prompt，只换模型，比质量/延迟/token/失败率。
- 好处：把「哪个模型更好」变成可复跑的表，而不是一次性的印象。
- ⚠ 代价：**真实花钱**；temp>0 有抖动 ⇒ 3 次取中位数；缓存命中率不同会让延迟不可比 ⇒ 必须记录是否命中。
- **状态**：候选 → **采纳为 P2-1（排最后）**

**AF · 版本徽章修复（S10′）**
- 内容：`readVersion()` 改 `fileURLToPath(new URL(import.meta.url))`。
- 好处：10 分钟，消除页面上唯一的「?」；顺带证明「非 ASCII 路径」这条坑。
- ⚠ 代价：无。唯一风险是单元测试要构造一个含非 ASCII 的目录（`mkdtemp` 加中文前缀即可）。
- **状态**：候选 → **采纳为 S10′**

**AG · 把「参数」卡折叠**
- 内容：15 行参数默认收起，只显示近期改动过的 3 行。
- 好处：首屏更短，模型选择这张卡更靠前。
- ⚠ 代价：折叠会藏住「哪个参数被改过」；需要「已改动多少项」的角标兜底。
- **状态**：候选（C-08，不排期）

**AH · 用现成方案代替自研**
- 内容：查 npm/GitHub 有没有「插件页滚动容器」或「模型选择器」的现成实现。
- 结论：**没有可复用的** —— DSH 的槽位契约（`display:contents` + 定高 flex 列）是项目私有的，

  `library_search("react scroll container panel plugin")` 返回的都是应用层方案，与本场景不匹配。
- **状态**：已消费（结论：自研，但只有 3 个样式对象）

### 13.2 两条缺陷的根因（一句话版）

1. **生成端**：路径曾被**按包名猜目录名**写死（`…/projects/dsh-gokifu-compact`），而真实目录叫 `dsh-chess-context`；更糟的是安装器判据是「键存在就跳过」，**没有修复路径**，而 pnpm 对坏 `link:` 只 WARN 不报错 —— 于是「坏」可以被无限期保留且没人发现。

### 13.2b 第三个缺陷（取证路上顺手撞见）

**症状**：`node <profile>/node_modules/dsh-gokifu-compact/scripts/install.mjs --dry-run` → **零输出、退出码 0**。
**根因**：末尾「是否被直接执行」用 `nodePath.resolve(process.argv[1]) === fileURLToPath(import.meta.url)`。
经 junction 调用时 Node 已把 `import.meta.url` 解析成**真身**（`D:主工作区projectsdsh-chess-contextscriptsinstall.mjs`），
而 `argv[1]` 仍是链接路径（`…profilesdesktop
ode_modulesdsh-gokifu-compactscriptsinstall.mjs`）⇒ 判 false ⇒ 连 `run()` 都没调用。
`test/verify-install.mjs` 末尾同一处，所以**校验器经 junction 调用时也是空的** —— 一个「退出码 0 + 什么都不打印」的校验命令，
正是本切片要消灭的那类假绿。
**修法**：比较改用 `samePath`（realpath），一行；`F1`/`F2` 两条用例从「子进程经 junction 入口」黑盒验证，变异自检能把它们变红。

### 17.2 新视角（R11 与前面几轮不同的三个问题）

1. **「挂起」与「撤销」是两种动作，绝不能混。** UI 暂停时最省事的做法是「把 §十四.2 / §十九 划掉」——但那会把**已经花掉的实测成本**（31 条缺陷的复现、滚动契约的四属性验证、token 合成对比度计算）一起扔掉，等恢复时从零再来。⇒ **纪律：优先级反转时只改「排期」与「状态」，不改「定稿形态」与「结论」。** 方案里写「挂起」，不写「作废」。
2. **一次性子代理是「按任务建人」，持久队友是「按角色建人」。** 前者把「任务的全部上下文」压在一个子代理的窗口里，一旦耗尽就**人亡政息**（脚本与日志还在，结论没了，还占着目录名让人以为在做）。后者把「职责」固化成人，任务可以重派、上下文可以重建。⇒ **11 个阵亡目录里 10 个能重派，是因为任务书还在任务板上；唯独 `ws-infra/` 与 `ws-configdrift/` 没人能接，因为它们连一条任务都没有。** **教训：先有任务板条目，再派人。**
3. **审核必须与执行分离，且审核者不得有写权限。** 主人要求「让专门的审核角色审核当前成果」——若审核者同时能改文件，它就会在发现问题时顺手改掉，于是**「谁审的」与「谁改的」变成同一个主体**，审核这道门就形同虚设。⇒ **纪律：reviewer 只读、只给证据与最小修复建议、不代改。** 配套的是**结果语义**：任何切片**只有带 `复验` 标记才算完成**（自报/复核/复跑都不够）。

## 二十一 · R15 · **基线起点不是「时刻」，是「签字」**（2026-10-30 03:4x）

> **这一轮只问一件事：为什么「我报了基线的时刻」这件事，连续三次都没用？**

### 21.1 三次同型（**逐条保留**）

| 次 | 谁在什么时候写 | 我/别人据此宣布的基线 | 后果 |
|---|---|---|---|
| **1（1.9.1）** | 打完基线后，**我**改了 `docs/方案` 修 V4 死链 | `e9be1e2d…` | **基线作废，白跑一轮 re-gate** |
| **2（1.9.2）** | 我报 03:21:19 快照 → **release 03:21:41** 回填 373 | `README f2da22b4…` | **lead 确认的那一刻就已过期** |
| **3（1.9.3）** | 预检跑完 → **release 03:36:40** 又改 CHANGELOG +114 B | `03:35:23` 起点 | **起点被越过** |

**⇒ 共同结构：写入方总在「基线被宣布之后」还有最后一次写入。**
**⇒ 而且第 3 次最阴险：预检 shasum `7070e8e5…` 已经算出来了，之后又改 +114 B ⇒ 那个 shasum 已经不代表最终包。**

### 21.2 根因（不是「谁不小心」，是「定义错了」）

**我们把「基线起点」定义成一个**时刻**。但时刻是**推断**出来的 —— 我看到的只是「已经发生的写入」，看不到「还没发生的写入」。**

**⇒ 正确的定义不是时刻，是**签字**：**
> **基线起点 = 写入方明确声明「我不再写了」之后，由（任一可信方）立刻现测得到的值。**

**⇒ 差别在于：时刻来自**观察**（可错），签字来自**承诺**（可追责）。**

### 21.3 本轮否决（R15-1…R15-3）

| # | 设想 | 否决理由 | 时间 |
|---|---|---|---|
| R15-1 | ~~「按最后修改时间推定基线起点」~~ | **三次全部被打穿**。mtime 只能证明「过去没写」，不能证明「以后不写」 | 2026-10-30 |
| R15-2 | ~~「预检 / precheck 的 shasum 就是发布基线」~~ | **1.9.3 实证**：预检 `7070e8e5…` 之后 CHANGELOG 又改 ⇒ 最终 `e117c876…`。**预检只能「发现阻断」，基线用于「事后对账」，两者不同** | 2026-10-30 |
| R15-3 | ~~「用文件大小判断冻结面有没有变」~~ | **1.9.3 给出两个反例**：`README` 1.9.1→1.9.3 **大小不变**、`package.json` 1.9.2→1.9.3 **大小不变**，**只有 sha 变**。**版本号 bump 本身就必然产生「同尺寸内容变更」** | 2026-10-30 |

### 21.4 新纪律（四步，缺一不可）

1. **写入方回「已停」**；
2. **停手后立刻现测**六份 `mtime + sha256`；
3. **再跑 `npm pack` 取 shasum**（必须在 ② 之后）；
4. **基线记录同时写「时刻 + 六份 sha + pack shasum + 全树指纹」四样。**

**⇒ 与 R14「核验对象错位」、R13「时机错」同族：都是**检查范围没界定** —— 我查了「我以为要查的那一处」，没查「同类还有没有别处」。
