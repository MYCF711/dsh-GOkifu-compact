# 核查清单：怀疑某个结论时，按这个顺序查

> 2026-11-01 · 与 `docs/工程教训集.md` 互补：那份讲**教训**（踩过什么坑），这份讲**步骤**（怎么查）。
> 用法：出现「测试红了 / 数字不对 / 展示异常 / 不知道改动生效没有」时，从 §0 往下走，**别跳步**。

---

## §0 先分类：是「代码错了」还是「数据旧了」？

这一问能省掉一半排查时间。

| 症状 | 最可能的原因 | 下一步 |
|---|---|---|
| 功能行为不对（算错、崩溃、越界） | 代码 | §2 核测试 |
| 数字/状态不符合预期，但功能正常 | **数据是旧的**（live 没加载新代码 / 旧 foldMark 没新字段） | §1 核运行态 |
| 测试红但单文件绿 | **并发干扰** | §2 |
| 文档说的和实际不符 | 文档过时 | §3 |

---

## §1 核运行态：live 跑的是不是最新代码

**两个信号，都查才算数**：

```bash
# ① 进程启动时间 vs 最后一次提交时间
#    （Windows 用 Get-Process 看 StartTime；这里给的是通用思路）
git log -1 --format="%ci %h %s"

# ② 数据里的新字段有没有出现（最硬的证据）
node -e "…读 graph.json，看 foldMarks 里有没有 quality/summaryChars 等新字段…"
```

**判据**：
- 进程启动时间**晚于**最后一次提交 → 新代码已加载；
- 新字段在数据里出现 → 确实在跑；
- **两者都没有，就是"还没生效"** —— 这时看到的任何"异常"都先别归因于代码。

> 本仓实例：`DSH_HOME=<workspace> Harness/home`，会话图在 `chess-context/sessions/*/graph.json`。

**不能做的事**：不要为了让它生效去重启 DSH（AGENTS 铁律 1）。只能等，或者写 staging 脚本交给用户。

---

## §2 核测试：真红还是并发假红

**症状**：`T2-5 … 应产生 1 条，实际 2` 这类偶发红。

**两步验证**：

```bash
node test/run.mjs tier2        # ① 单独跑那个文件
tasklist | grep -c node.exe    # ② 看有没有别的会话在跑测试
```

**判据**：单文件绿 + 有多个 node 进程 ⇒ **并发假红**（共用 `test/.harness/graphs`）。
两个条件都成立才敢下结论——**只跑单文件不够**（那只能说明"当前时刻不红"）。

**另外**：`tail -2` 可能只截到 `Node.js v24.20.0` 之类的残行，看着像崩溃。**要看完整的 `== N passed ==` 行**。

---

## §3 核数字：这个数字是哪天的

**最重要的一条**：**不要看文件 mtime** —— git checkout 会把 mtime 统一刷成检出时间。

**看内容里的时间戳**：

```bash
head -3 evidence/真实模型测试.md        # 「生成于 2026-11-01T15:13Z」
grep -n "生成于\|2026-" docs/research/*.md | head
```

**分档判断**：
- `evidence/README.md` 有新鲜度分档（✅ 最新 / ⚠ 历史）；
- 文档里的数字如果没带时间，**默认不可信**，回源去查。

**引用纪律**：`[外]`（别人的） / `[本]`（我们实测）要标清；夹具口径与真实分词口径不能比。

---

## §4 核展示：有数据时会怎么显示（不用等 live）

**这是最有用的一招**：要验证"新字段的展示对不对"，不必等真实数据产生。

```bash
# ① 把真实产物复制到临时 home（不碰 live）
tmp="$HOME/.tmp-verify"; rm -rf "$tmp"; mkdir -p "$tmp/chess-context/sessions"
cp -r "<workspace> Harness/home/chess-context/sessions/<某个会话>" "$tmp/chess-context/sessions/"

# ② 手工注入"还没有的字段"（模拟升级后的数据）
node -e "…读 graph.json，给 foldMarks[0] 补 quality，写回…"

# ③ 用 DSH_HOME 把工具指过去（两个脚本都支持）
DSH_HOME="$tmp" node scripts/doctor.mjs
DSH_HOME="$tmp" node scripts/handoff-check.mjs

# ④ 跑完删临时目录
rm -rf "$tmp"
```

**判据**：输出里那些字段是否按预期出现、分级是否正确（如 `constraintRecall<1`=error、`failureRecall<1`=warn）。

**零风险**：live 一个字节不动。

---

## §5 端到端四步（发版前 / 大改后）

```bash
node test/run.mjs 2>&1 | tail -3           # ① 必须 0 failed
node scripts/bench-repro.mjs               # ② 不许 DRIFT
node scripts/handoff-check.mjs             # ③ FAIL 0；WARN 逐条判读
node scripts/doctor.mjs                    # ④ 错误 0；警告逐条判读
```

**警告判读表**（见 `docs/压缩的重注入契约.md` §7 的实际记录）：

| 警告类型 | 性质 | 处理 |
|---|---|---|
| 「未采集」（旧数据缺新字段） | 预期 | 不动，等新数据 |
| 「轻微超预算」（如 509/500） | 可接受 | 记录趋势 |
| 「会话形态特殊」（如没有 rootUserNodeIds） | 合理 | 不动 |
| **其余** | **真问题** | 查 |

---

## §6 什么时候可以下结论

**必须同时满足**：

1. 现象能被**两次独立验证**复现（如单文件测试 + 进程数；或两个不同工具的输出）；
2. 已经排除 §1（数据旧）与 §2（并发干扰）；
3. 结论的**范围**与证据匹配（单测绿 ⇒ 只能说"单测层面绿"，不能说"真实环境没问题"）。

**特别注意**：诊断结论要停在诊断本身，**别顺手滑到"所以做不到"**——
先分是「架构限制」（改不了）还是「实现没写完」（当前没做但能做）。这条踩过（见工程教训集 §3）。

---

## §7 一页速查

```
现象 ──┬─ 功能不对 ──────────────→ §2 核测试（单文件 + 进程数）
       ├─ 数字/状态怪 ─────────────→ §1 核运行态（进程时间 + 新字段）
       ├─ 文档与实际不符 ───────────→ §3 核数字（看内容时间戳，不看 mtime）
       ├─ 想验"有数据时" ───────────→ §4 临时 home + 注入
       └─ 要发版 / 大改后 ──────────→ §5 四步 + 警告判读表
```
