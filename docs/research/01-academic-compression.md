# 学术前沿：上下文压缩与 agent 记忆（2026-11 调研）

> 读者：`dsh-gokifu-compact` 的维护者。目的不是写综述，是回答一个工程问题：
> **棋谱式压缩（因果图 + 失败边 + 约束清单 + 每步约 351 tokens 热清单）该从学术前沿借什么、必须拒绝什么。**
>
> 一句话结论：**2026 年的实测证据已经把「压多少」这个问题降级了，真正的分水岭是「压缩器有没有重写事实」。**
> 机械抽取（79.1% 关键细节保留）对 LLM 摘要（16.0%）是 5 倍差距，且这个差距在真实 SWE 修复上直接换算成任务成败。
> GOkifu 走的「从事件机械建图、失败边逐字保留」正好站在这条分界线的正确一侧 —— 但它缺三样东西：
> **来源指针（哪条事件支撑这个节点）、被遮蔽物的显式标注、以及 page-in（按需回填）通道。**

## 1 · 提示压缩（prompt compression）

### 1.1 这一族方法的共同前提 —— 也是它们不能直接搬到会话压缩的原因

这一族全部做同一件事：**在一次推理调用内部，把「这次要喂进去的输入」变短**。

三个必须看清的性质（**这是本节最重要的一段**，比任何单个方法的数字都重要）：

1. **无状态**。压缩结果不落盘、不进会话历史、不会被下一步继承。下一次调用重新压一遍，甚至可能压出不同的结果。
2. **原文仍完整存在**。被删掉的 token 还在 harness 的缓冲区里；压缩是**投影**，不是**销毁**。所以压错了可以下一次改回来。
3. **不解决上下文增长**。输入本身在变长，「每次少花点」只是把斜率压小，不改变「历史无限增长」这个事实。它买的是**成本**，不是**容量**。

会话级压缩（compaction）三条全部相反：持久、原文被遮蔽、直接决定「历史能不能继续增长」。
**⇒ 提示压缩的所有容错设计，都不能直接继承到会话压缩。** §6 会把这条展开成表。

### 1.3 逐个：机制 / 结论 / 可借鉴 / 不可借鉴

**LLMLingua（2310.05736）**

- **核心机制**：coarse-to-fine 三级。(a) **budget controller**——给 prompt 的不同成分（指令 / 示例 / 问题）分配**不同的压缩率**，而不是整体一个比率；(b) **token 级迭代压缩**——逐 token 判断去留时把「已压缩内容」作为条件，建模 token 之间的相互依赖；(c) 用 instruction tuning 做分布对齐，让压缩后的文本更像模型见过的分布。
- **关键结论**：4 个数据集上最高 20x 压缩而「几乎没有性能损失」。这个 20x 是在 GSM8K（数学推理）、BBH（推理）、ShareGPT（对话）、Arxiv 论文上测的，**不是多轮 agent 轨迹**。
- **可借鉴**：**budget controller 的分段预算**。这是本节唯一可以直接搬进 GOkifu 的机制 —— 热清单不该只有一个总预算，该有「约束 30 / 失败边 120 / 成功路径 80 / 目标 20」这类**分项配额**，因为不同成分的丢弃代价差两个数量级（见 §5.2）。GOkifu 现在的 351 tokens 是**总量**，没有分项下限。
- **不可借鉴**：token 级删除。它默认「同义改写不改变语义」，这对自然语言成立，对**路径 / commit sha / 端口 / 错误原文**不成立。§5.4 有直接实测证据（τ-bench 上 LLMLingua-2 无增益，因为后续工具调用需要精确标识符）。

**LongLLMLingua（2310.06839）**

- **核心机制**：在 LLMLingua 基础上针对长上下文做三件事：(a) **question-aware 的粗筛**——用问题去估算段落相关性，再细压；(b) **文档重排**——把高相关段落挪到上下文的**两端**（直接对冲 lost-in-the-middle，见 §4.1）；(c) 动态压缩率 + 子序列恢复。
- **关键结论**：NQ 上**性能提升 21.4% 的同时 token 少 4x**（即压缩不只是省成本，还能**提升**准确率，因为提高了关键信息的密度）；LooGLE 成本降 94.0%；10k token 输入在 2–6x 压缩下端到端延迟降 1.4–2.6x。
- **可借鉴**：**「压缩可以提分」不是悖论**。当关键信息被稀释在长文里时，删掉噪声本身就在提升注意力分配。这对 GOkifu 的 351 tokens 是个正面证据：**极小热清单不只是省钱，是性能手段**。另外「把高相关内容挪到两端」是一条零成本的渲染规则（§4.5 给具体排序建议）。
- **不可借鉴**：question-aware 粗筛需要**当前问题**。会话压缩没有「当前问题」——压缩发生在第 N 步，而热清单要服务第 N+1 到 N+k 步的**未知**问题。§5.4 的实测正好打在这里：为当前问题选句子，对未来问题**不比随机删除好**。

**LLMLingua-2（2403.12968）**

- **核心机制**：把压缩从「按信息熵删 token」改成**token 分类任务**——用 Transformer encoder（XLM-RoBERTa-large / mBERT）在**双向**上下文下判断每个 token 保留与否；训练数据由 GPT-4 蒸馏而来（让大模型标注「哪些词删了不影响」）。
- **关键结论**：小模型（比 7B 小两个数量级）就能压，压缩器本身快 3–6x；端到端 1.6–2.9x；跨 LLM 泛化好。**并且明确把「faithfulness」当成设计目标**：因为是抽取式，输出必然是原 token 的**子集**，不会凭空生成。
- **可借鉴**：**「抽取式 ⇒ 保真」这条推理链**。GOkifu 的失败边逐字保留，本质就是抽取式；论文给的理论支撑是「输出是输入的子集 ⇒ 不可能引入输入里没有的事实」。这条可以写进设计文档当**正确性论证**。
- **不可借鉴**：即便抽取式，**删词**仍然会破坏语法与指代（"it" 的先行词被删）。LLMLingua-2 自己也承认压缩率越高越脆。对 GOkifu：**失败边可以逐字，但不能截断**；截断一条错误信息比不写它更糟。

**Selective Context（2310.06201）**

- **核心机制**：用一个小 LM 算每个词/短语的**自信息（self-information）**，把信息量低的（"the"、"as we know"、冗余修饰）剪掉。本质是「按困惑度剪枝」。
- **关键结论**：上下文减 50% ⇒ 显存 -36%、时间 -32%，代价是 BERTScore -0.023、**faithfulness -0.038**。注意它**自己也报了 faithfulness 下降**——这是这一族里少见的诚实数字。
- **可借鉴**：极低成本的初筛（不需要 GPU 大模型）。如果 GOkifu 将来要压「工具输出的冗余体」，这类无监督打分是零依赖方案。
- **不可借鉴**：自信息 = 罕见 ⇒ 重要。这个假设在 agent 轨迹上是**反的**：`EACCES`、`ECONNREFUSED`、`0x80070005` 都是高频或低信息词，但它们是失败边的全部价值。**按信息量剪枝会优先删掉错误码。**
- **附带一条**：该论文 arXiv 页面有一条 admin note ——「substantial text overlap with arXiv:2304.12102」。引用时注意它的原创性归属。

**RECOMP（2310.04408）**

- **核心机制**：检索到的文档先压成摘要再入 prompt。两版：**抽取式**（选句子）与**生成式**（多文档综合）。两者都**针对下游任务训练**（不是通用摘要）。关键设计：**selective augmentation** —— 若检索内容与问题无关或没增量信息，**直接返回空串**。
- **关键结论**：压到 **6%** 而性能损失极小，显著优于「拿现成摘要模型来压」。且在一个 LM 上训的压缩器**可迁移**到别的 LM。生成式摘要「largely faithful」。
- **可借鉴**：**「允许压到零」**。这条比压缩率重要：绝大多数压缩系统被设计成「必须留点东西」，于是无关内容被硬压成一句含糊的话，反而制造噪声。GOkifu 的 `OPTIONS` 段（未结算的候选边）在语义上接近，但方向相反——它是「保留但标注不确定」，而 RECOMP 是「直接不给」。两者可以并存：**无来源支撑的条目 → 删；未结算但有来源的条目 → 标 OPTIONS**。
- **不可借鉴**：针对下游任务训练压缩器，需要任务分布和梯度。DSH 插件两条都没有。

**软提示路线：Gist / AutoCompressor / ICAE（2304.08467 / 2305.14788 / 2307.06945）**

- **核心机制**：不改文本，改**表示**。把长 prompt 编码成少量「gist token」或「summary vector」，作为 soft prompt 拼进输入。Gist 靠改注意力掩码 + 指令微调实现；AutoCompressor 分段处理长文、把历史段的 summary vector 拼给下一段；ICAE 用自编码 + 语言建模双目标预训练一个压缩器（只加约 1% 参数）。
- **关键结论**：Gist 26x、AutoCompressor 支持 30,720 tokens、ICAE 4x；都能显著降 FLOPs / 延迟。
- **可借鉴**：几乎为零（对插件而言）。**唯一可借的是概念**：AutoCompressor 的「分段 + 每段一个 summary vector + 后续段看到前面所有 vector」在结构上就是 GOkifu 的**增量 fold**（每段压一次，不重压历史）。可以用它当「分段压缩而非递归压缩」的文献先例。
- **不可借鉴**：三条都需要**改模型权重或推理栈**。DSH 插件只能操纵文本。**任何需要 soft prompt 的方案在 DSH 里都不存在落地路径** —— 这条要写死，避免以后有人提议。

### 1.4 这一族给出的两个硬事实

1. **压缩率的天花板与任务强相关**。20x 出现在 GSM8K/BBH 这类「答案由少量关键步骤决定」的任务上；一旦任务依赖长尾细节（多跳、精确标识符、时序），可用压缩率掉到个位数。RECOMP 的 6%、LongLLMLingua 的 2–6x、Selective Context 的 50% ——**同一批作者，数字差 3 倍以上，差别全在任务**。
2. **压缩有「提分」区间**。LongLLMLingua 的 +21.4% 说明：在信息被稀释的场景里，适度压缩 > 不压缩。这给「351 tokens 会不会太少」提供了一个反直觉的答案：**少可能更好，前提是留下的都是高密度的**。

### 1.5 本节对 GOkifu 的净结论

| 想借的东西 | 借不借 | 理由 |
|---|---|---|
| 分段预算（budget controller） | **借** | 直接可用，且能修「351 tokens 无分项下限」这个缺陷 |
| 抽取式 ⇒ 保真 的论证 | **借**（当论证用） | 支撑「失败边逐字」的合法性 |
| 允许压到零（RECOMP） | **借** | 与 OPTIONS 语义互补 |
| 把高相关内容挪到两端 | **借** | 零成本渲染规则，§4.5 |
| token 级删除 | **不借** | 毁标识符，§5.4 有实测 |
| question-aware 选择 | **不借** | 会话压缩没有「当前问题」 |
| 自信息剪枝 | **不借** | 会优先删错误码 |
| soft prompt / gist | **不借** | 需改权重，DSH 无落地路径 |

## 2 · 摘要式记忆

### 2.1 MemGPT 的真实机制（读了全文，不是摘要）

摘要只说「virtual context management / 分层记忆 / interrupts」。全文里真正可工程化的是一组**具体阈值和动作**（arXiv:2310.08560，§2.2 Queue Manager，【核实·全文】）：

- **主上下文 = 三段**：system instructions + **working context**（可写、可被模型自己编辑）+ **FIFO queue**（滚动消息历史）。
- **外部上下文 = 两个库**：**recall storage**（完整对话历史，可全文检索）+ **archival storage**（任意长文本对象，读写数据库）。
- **FIFO queue 的第 0 项是一条系统消息，内容是「已被驱逐消息的递归摘要」**（原文：*"a system message containing a recursive summary of messages that have been evicted from the queue"*）。**这一句是本节最关键的一句**，见 §2.5。
- **memory pressure 警告**：prompt token 超过上下文窗口的 **70%** 时，queue manager 插入一条系统消息警告模型即将驱逐，让模型有机会先把重要信息写进 working context 或 archival storage。
- **flush**：超过 **100%** 时真的驱逐，一次驱逐**约 50%** 的消息。
- **page fault 的类比是显式写出来的**：OS 把溢出数据换到磁盘，「via a **page fault**」再取回内存；MemGPT 让 LLM 自己管理什么留在上下文里，从而伪造出「更大的内存」这个假象。
- **自编辑记忆**：模型通过函数调用（`core_memory_append/replace`、`archival_memory_insert/search`、`conversation_search` 一类）**自己决定**写什么、改什么、检索什么。`request_heartbeat=true` 允许连续链式函数调用而不返回用户。

**四段**：

- **核心机制**：把上下文窗口当 L1，把「完整历史 + 长文本库」当磁盘；用**显式阈值 + 模型自编辑**在两层之间搬运数据；用 page fault 语义保证「搬出去的东西还能拿回来」。
- **关键结论**：分层 + 自编辑 + 中断控制，能在固定窗口下做文档分析和多会话聊天。**它的收益来自「可换回」**，不是来自「压得好」。
- **可借鉴**：**三条，按价值排序**：
  1. **把阈值参数化成三元组 `(warn, flush, evict_ratio)` = (70%, 100%, 50%)**。GOkifu 现在有 `INJECT_MIN_EVENTS=40` 与 `INJECT_MIN_FAILURE_DELTA=5` 两个**触发**阈值，但**没有「一次压多少」的比率**。缺这一维意味着 fold 范围由 fold-planner 隐式决定，无法调参、无法解释。
  2. **70% 处先警告、100% 才动手**。GOkifu 是到点直接压。中间那 30% 的窗口本来可以让 keeper 补抽、让 fold-planner 收敛，现在浪费了。
  3. **page fault 可以作为正式机制引进**（见 §2.6 与 §6）。
- **不可借鉴**：**递归摘要**。FIFO 头部的摘要是「摘要的摘要」——每轮驱逐都把上一轮的摘要再压一次。这是 ρ^k 几何衰减的教科书实现（§2.5 给定量）。GOkifu 的增量 fold 恰好避开了它，**不要为了「像 MemGPT」而把这条加回来**。

### 2.2 RecurrentGPT（2305.13304）

- **核心机制**：用自然语言模拟 LSTM。每个时间步生成一段文本，然后更新两处记忆：**长期记忆写硬盘**（语言化的「记忆」文件）、**短期记忆写 prompt**。相当于把 LSTM 的 cell state 换成一段可读可编辑的文字。
- **关键结论**：可以生成任意长文本而不遗忘；记忆是自然语言 ⇒ 人类**可读、可编辑**；作者顺带提出「AI As Contents」这种交互小说用法。
- **可借鉴**：**「记忆必须是人类可读可编辑的自然语言」**这条设计约束。GOkifu 的棋谱已经是可读的（节点/边/渲染），这在调试和审计上是决定性优势 —— §5.3 的 provenance 问题、§5.1 的「哪条是编的」问题，都只有在**记忆可读**时才查得出来。
- **不可借鉴**：它是**生成**框架（写小说），不需要「历史必须精确」。它的记忆更新是**重写**（rewrite），而会话压缩最怕的就是重写。RecurrentGPT 的评测指标是「文本连贯性」，不是「事实保真」。

### 2.3 2025–2026 的续作：Mem0 / A-MEM

**Mem0（2504.19413）**【核实·摘要】

- **机制**：从对话里**抽取**显著信息 → 整合（consolidate，含冲突消解：新事实覆盖旧事实）→ 按需检索；另有一个图记忆变体。
- **结论**：LOCOMO 上比 OpenAI 的记忆方案 LLM-as-Judge **+26%**；图变体只比基础版 **+2%**；p95 延迟 **-91%**、token 成本 **-90%+**（对比 full-context）。
- **可借鉴**：**「写时整合」而不是「读时压缩」**。Mem0 在**写入**阶段就做去重和冲突消解，所以读取时不用再压。GOkifu 的**置换检测（tewari）**是同一思路的不同切面 —— 但 GOkifu 在**渲染时**才做，Mem0 在**入库时**就做。入库时做的好处是：图里不会同时存在两条互斥的边，热清单渲染不用再判断。
- **不可借鉴**：Mem0 的「新事实覆盖旧事实」是**破坏性**的。对「用户改主意」这是对的；对「这个方案试过、失败、后来换个条件成功了」这是**灾难**——它会把失败边擦掉，正是 GOkifu 明确要保留的东西。**覆盖语义必须限定在「同一对象的属性」上，不能用在「尝试历史」上。** 这也解释了为什么 Mem0 的图变体只 +2%：图在这里只是索引，没承担「保留失败」的职责。

**A-MEM（2502.12110, NeurIPS 2025）**【核实·摘要】

- **机制**：Zettelkasten 式。每条新记忆生成一个结构化 note（上下文描述 / 关键词 / 标签），然后**主动分析历史记忆、建立链接**；新记忆还能**反向更新旧记忆的上下文表示**（memory evolution）。
- **结论**：六个基座模型上优于 SOTA 基线。
- **可借鉴**：「新节点入库时主动连边」——GOkifu 的 keeper 已经在做（意图→动作→结果），但 A-MEM 多了一步：**新节点可以改变旧节点的属性**。对 GOkifu 的具体含义：一条失败边在「后来成功了」之后**不应该被删除**，但**应该被标注 `superseded_by=<edge_id>`**。这样热清单可以渲染成 `FAILED (superseded by e42): ...`，信息量与「只有失败」完全不同。
- **不可借鉴**：「memory evolution 允许重写旧记忆的表示」在 A-MEM 里是无害的（它只影响检索排序）。在会话压缩里**重写旧节点 = 篡改历史**。**只许加标注，不许改内容。**

### 2.4 透明压缩：2026 年最贴近 GOkifu 的一篇

**transparent-compact（2610.20116）**【核实·摘要，单篇预印本】

- **机制**：为开源 Pi coding agent 做的**确定性**压缩。三条硬约束：(a) **用户与助手的散文（prose）在上下文中绝不被模型或算法改写**；(b) **显式标注哪里被剥掉了信息**；(c) 不做任务/上下文特定的结构化。
- **结论**：对四档模型（重点 Qwen3.8-27B，消费级硬件可本地跑的轻量模型）在**承诺（commitments：只存在于对话里的用户规则）**和**事实召回**两组探针上，**匹配或超过** Pi 的默认模型写摘要，也超过 pi-vcc（另一个确定性方法，但不逐字保留散文）。**尤其在于减少「自信的错误」（confident blunders）——把假信息当事实断言，而不是承认「没想起来」。** 前沿模型上优势仍在但更小。
- **可借鉴**：**这是本文对 GOkifu 最有价值的一篇**，三个理由：
  1. 它把「**逐字不改写**」当**第一原则**，而不是实现细节 —— 与 GOkifu「失败边逐字保留」同源。而且它证明这条在**轻量模型**上收益最大，正好是本地部署场景。
  2. 它把 **commitments（只存在于对话里的用户规则）** 单独拎出来当评测对象。GOkifu 的「约束清单」就是这个东西。**可以直接借它的探针设计来做 GOkifu 的回归测试**（现在 GOkifu 的测试里没有「约束是否在 k 次 fold 后仍在热清单」这类断言）。
  3. 「**显式标注被剥掉了什么**」是 GOkifu **缺的那一块**。现在遮蔽是静默的：模型不知道「有一段历史被折叠了」。加一行 `[folded: 12 events, 3 failures → see nodes n41-n53]` 成本个位数 token，但它把「我不知道」和「没有这回事」分开了 —— 这正是论文里 `confident blunders` 的成因。
- **不可借鉴**：「不做结构化」是它的选择，因为它要通用。GOkifu 有领域结构（棋谱），**结构化是 GOkifu 的立身之本**，不该放弃。这条只提醒一件事：结构化不能以「改写原文」为代价。

### 2.5 递归摘要的 ρ^k 衰减（定量）

这是 MemGPT 与官方 `dsh-compaction-basic` 共有的结构，也是 GOkifu 存在的理由。把它算清楚：

设一次「摘要重写」后，某条细节仍被保留的概率为 **ρ**。若每次压缩都把**上一轮的摘要**连同新事件一起重摘，则经过 **k** 次压缩的存活率为 **ρ^k**。

ρ 的实测取值（**都是单篇预印本，未见复现**）：

| 压缩方式 | 单次保留率 ρ | 出处 |
|---|---|---|
| LLM 摘要（14 个摘要模型里最好） | **0.16**（"retain at most 16.0% of recurring details"） | arXiv:2610.31710 Compact-Bench 【核实·摘要】 |
| LLM 摘要（生产环境第一次边界） | **0.157** | 同上 |
| **机械抽取** | **0.791** | 同上 |

代入：

| k（压缩次数） | LLM 摘要 0.16^k | 机械抽取 0.79^k |
|---|---|---|
| 1 | 16.0% | 79.1% |
| 2 | 2.6% | 62.6% |
| 3 | 0.41% | 49.5% |
| 5 | 0.0105% | 30.9% |

**读法**：LLM 摘要走递归，第三次压缩后关键细节基本归零；机械抽取即便递归也还有一半。
但 GOkifu 的结构是**增量 fold**：一条细节在**第一次覆盖它的 fold** 里被抽成图节点，之后**只被渲染、不再被重写** ⇒ 存活率是 **ρ¹，不是 ρ^k**。

**这里必须诚实**：GOkifu 的 ρ^k 消失了，但**风险没有消失，只是换了名字** —— 从「**被改写**」变成「**不在热清单里**」。
一个节点在 k 次 fold 后仍然完好地存在于 `graph.json`，但如果它没进那 351 tokens，模型就看不见它。
**⇒ 真正的失效模式是检索，不是损坏。** 这也是为什么 §2.6 的 page-in 和 §3.4 的可达性排序是本文对 GOkifu 的核心建议。

### 2.6 本节净结论

| 想借的东西 | 借不借 | 落地形态 |
|---|---|---|
| `(warn 70%, flush 100%, evict 50%)` 三元阈值 | **借** | config-schema 加两个键，注释可改 |

## 3 · 结构化/图式记忆与压缩

> **本节要回答的问题**：GOkifu 已经在做「图」（棋谱：节点 + 边 + seq 出处），而学术界的图记忆（RAPTOR / GraphRAG / HippoRAG）几乎都在做**跨文档知识库**。两者的差别不是规模，是**生命周期**。本节把**可借的三条**（竞争式选层、逐级替换〔本仓已有，学术给了外证〕、PPR 可达性排序）和**必须拒绝的四条**（LLM 建图、社区摘要、重聚类、按 query 定制）分开写。

**证据说明（接 §0）**：§3–§7 另有 **11 处【核实·全文】**（2401.18059 / 2404.16130 / 2405.14831 / 2307.03172 / 2310.08560 / 2610.31710 / 2610.20116 / 2608.01056 / 2605.17304 / 2609.32961 / 2404.06654），本轮均抓到 `arxiv.org/html/*` 正文并逐段核对。§0 里「4 处引全文」的统计**只覆盖 §0–§2**，未改动。

### 3.1 为什么这一族最像 GOkifu，也最容易被误借

三篇论文的共同点：**把长文本变成结构，再在结构上检索**。这跟棋谱（把事件变成节点/边，再渲染成 351 tokens）在形状上完全一致，所以极容易被当成"我们本来就该做的事"。但它们的**输入端**和 GOkifu 有五处根本不同：

| 维度 | RAPTOR / GraphRAG / HippoRAG | GOkifu 的 fold |
|---|---|---|
| 输入 | 静态语料，建索引时**一次读全** | 事件流，**追加式**，每次只看新增区间 |
| 可否重建 | 可以：换聚类、换提示、整棵重跑 | 不可以：历史只能**追加标注**，不能重写（§2.3 已裁定） |
| 问题 | 已知（query-focused：先有问题再检索） | **未知**（压在第 N 步，服务 N+1…N+k） |
| 成本位置 | 建索引侧，离线，可等几分钟到几小时 | 会话中途，**必须在对话里完成** |
| 目标 | 答得全、答得深（comprehensiveness / diversity） | 能不能**接着干活**（§5.1） |

**⇒ 一句话**：它们的**结构**可以借，**建图方式**一条都不能借 —— 因为建图要用 LLM 读原文再写，而重写正是 §2.5 里 ρ^k 的来源。

### 3.2 RAPTOR（2401.18059）：同一预算里让所有层级竞争

【核实·全文】机制（读的是 HTML 正文，不是摘要）：

- **自底向上建树**：文本块 embed → **软聚类**（GMM；允许一块属于多个簇，因为一段文本常同时属于多个主题）→ 每簇交 LLM 摘要 → 摘要再 embed、再聚类，**直到簇内上下文超过模型 token 上限时在该簇内递归再聚**。高维距离不可靠 ⇒ 先用 **UMAP** 降维再聚类；簇数用 **BIC** 选。
- **两种查询**：`tree traversal`（逐层 top-k 往下走）与 `collapsed tree`（**把所有层的节点拍平成一层**，按相似度取到 token 预算上限）。
- **结论**：拍平**稳定更好**。作者给的原因关键 —— traversal 下「高层主题 / 底层细节」的**比例是固定的，与问题无关**；拍平后「检索到的信息处于正确的粒度」。
- 预算按 **token** 而不是条数：collapsed tree 设 **2000 tokens ≈ top-20 节点**。
- 代价：**约 4% 的摘要含轻微幻觉**；作者称未传播到父节点、对 QA 无可见影响。

**对 GOkifu 的含义（本节最有用的一条）**：

本仓并没有"分项配额"（§1.3 的批评正是"没有分项下限"），所以 RAPTOR 反对的"比例锁死"**在 GOkifu 里不是已犯的错**。但反过来的风险是真的：**没有下限 = 某一类可能被整体饿死**，而渲染是逐档降级到装得下为止（`ledger.mjs` 的 L0–L5 阶梯），预算一紧，先被压的是"最长的那些行"，不是"最不重要的那些行"。

**⇒ 正确形态：分类只设下限，不设比例。** 即 `有失败边则 ≥1 条`、`约束全给（或给溢出计数）`，剩余额度由所有候选边在**同一个池子里竞争**（按 §3.4 的可达性分数填，而不是"失败边占 120 tokens"）。

这条与 §1.3 想借的 **budget controller（分段预算）** 表面冲突，必须在这里解决：
- LLMLingua 的分段预算是**保护性下限**（防止某类被整体挤掉）；
- RAPTOR 的拍平是**竞争性上限**（防止比例与问题错配）。
两者不矛盾 —— **只要把分段预算实现成"下限"而不是"配额"**。§1.3 的表述若不改，很容易被实现成后者。

**不借的两条**：

1. **重聚类**。RAPTOR 每次建索引都重新聚一遍，节点身份会变。棋谱的节点 id 是**出处指针的锚**（§4.3），重聚类等于让 `seq` 指错地方。
2. **LLM 摘要建树**。4% 幻觉率对 QA 无害（答错一题），对压缩有害：把失败边写成"已解决"就是 §5.7 的 mutation / polarity 错误。

### 3.3 GraphRAG（2404.16130）：建图在入库侧，压缩在每次 fold 侧

【核实·全文】机制：LLM 从文档抽实体图 → **Leiden 层次社区检测** → 为每个社区**预生成摘要** → 查询时 map-reduce（每个社区摘要出一个部分答案，再汇总）。目标是「global sensemaking」类问题（"这批文档的主要主题是什么"），这类问题向量检索答不了。

关键数字（1M token 级语料，2 个数据集）：

| 指标 | 数字 |
|---|---|
| comprehensiveness 胜率（对向量 RAG） | **72–83%**（Podcast）/ **72–80%**（News），p<.001 |
| diversity 胜率 | **75–82%** |
| token 节省（低层社区 C3 / 根层 C0） | **26–33%** / **>97%** |
| 建索引耗时 | Podcast（1M tokens）**281 分钟** |

还有一个**直接可搬的预算技巧**（原文 §3.1.5）：社区摘要**装不进上下文时，不是删条目，而是用更短的子社区摘要逐级替换更长的元素摘要，直到装得下**。这是"降级表示"而不是"丢弃内容"。

**对 GOkifu 的含义**：
- **这条本仓已经在做**：`ledger.mjs` 从 L0 到 L5 逐档渲染更短的形态，选第一个装得下的（装不下才落 `over-budget` 兜底）。GraphRAG 给了它**外证**：这是文献里被验证过的策略，不是拍脑袋。**因此不要再新增"降级机制"，该做的是把降级理由变成可观测的**（现在有 `level` / `over-budget` / `overBudgetBy`，缺的是"这一档为什么被跳过"）。
- **可借的增量**：跨边合并时**保 seq 全集**。本仓有 `provenanceCoverage` 保证"失败边行带 seq"，但它只保证**行级**有出处，**不保证合并后的 seq 集合等于合并前的并集**。两者是不同强度的断言（§5.6 probe #4）。
- **不借**：LLM 建图 + 社区摘要。两条理由都是硬的：(a) 需要 LLM 读原文再写，直接违反 §2.4 的"逐字不改写"；(b) 281 分钟/1M token 的建索引成本，会话中途不可能付。
- **不借（最容易被误借）**：对 fold 后的图再生成一次"社区摘要"当热清单。这是递归摘要的图版本，ρ^k 换了个名字（§2.5）。

### 3.4 图检索对「可寻址」的启示：可达性排序（HippoRAG 2405.14831）

【核实·全文】这是三篇里**唯一一个可以整段落地**的，因为它把"检索"变成了一个**不用训练、不用 LLM、确定性**的图算法。

机制：
1. **离线**：从 passage 抽 KG 三元组（OpenIE），另加**同义边**（余弦相似度超阈值就连边），并记一个**节点×passage 的出现矩阵**。
2. **在线**：从 query 抽命名实体 → 映射成 **query 节点**（种子）→ 在图上跑 **Personalized PageRank**（概率只在种子集上初始化、其余为 0）→ 把节点概率按出现矩阵**加总到 passage** 得到排序。
3. **node specificity**：节点的 IDF 式权重（出现在越少 passage 里越重要），乘在种子概率上，用来调制度量。

数字：多跳 QA 上**最高 +20%**；单步检索与迭代式 IRCoT 相当，但**便宜 10–30 倍、快 6–13 倍**。
一个反直觉的消融（对工程很重要）：**只把种子节点的邻居扩散进来（不做 PPR）比只用种子节点更差** —— 朴素"相关就拉进来"是负收益，必须有全局归一化。

**对 GOkifu 的含义（落地形态）**：

棋谱**已经具备 PPR 需要的全部要素**，不需要新建任何东西：
- 节点 = 事件 / 文件 / 命令 / 错误（已有）；
- 边 = 因果（意图→动作→结果）、工具对、文件依赖、置换（已有）；
- 种子 = **当前这一步的可寻址锚点**：最近一条用户消息里出现的标识符、当前工具调用及其参数、`touched-files` 房间记住的最近文件（已有）。

⇒ 新增一个**纯函数** `rankReachable(graph, seeds, budgetTokens)`：
- 幂迭代 PPR（二十来行，零依赖，无随机性）；
- 分数 × node specificity（用已有的节点出现次数算，不新增字段）；
- 从高到低填热清单，直到 token 预算满；
- **每个入选条目必须带 `seq`**（否则不可回溯，§7.1）。

这条同时回答了 §2.5 留下的那句话 ——「真正的失效模式是检索，不是损坏」：**PPR 就是那个缺失的检索函数**。而且它可测：给定图 + 种子，输出**唯一**，可以直接写 `t.eq`；行数（选谁）由它定，位置（放哪）再由 §5.6 probe #6 的位置规则叠加。

**不借**：用 LLM 做 OpenIE 抽图。棋谱的图是从**结构化事件**（工具名/参数/结果/退出码）机械抽的，这是它相对 HippoRAG 的结构优势 —— HippoRAG 必须付 LLM 调用才有图，GOkifu 不用。换成 OpenIE 是**降级**（多花一次模型调用，换来改写风险）。

### 3.5 界线：跨文档知识库 ≠ 会话内压缩

这是 §0 第 2 条自我限制的具体化，也是 `docs/压缩的职责边界.md` §2「跨会话记忆 / 知识库 ❌」在学术侧的对齐：

| 判据 | 跨文档知识库（RAPTOR/GraphRAG/HippoRAG） | 会话内压缩（GOkifu） | 后果 |
|---|---|---|---|
| 内容来源 | 外部语料，与本次会话无关 | **产自本次会话历史**（职责边界判据①） | 图里混入外部知识 = 越界 |
| 生命周期 | 常驻、跨会话、可重建 | 只在压缩生命周期出现（判据②） | — |
| 写入语义 | 可重写、可重聚类、可覆盖 | 只追加；旧节点只加标注、不改内容 | 重写 = 篡改 |
| 召回时机 | 用户提问时 | **每一步**（351 tokens 热清单） | 成本量级不同 |
| 成功判据 | 答案全面/多样 | 能不能接着干活（§5.1） | 指标不可互换 |
| 失败代价 | 答得不全 | 重复劳动 / 踩已探明的死路 / 违约 | 不可比 |

**一句话**：知识库是"我记得世界"，压缩是"我记得这次干到哪了"。**GOkifu 借图算法，不借图内容。**

### 3.6 本节净结论

| 想借的东西 | 借不借 | 落地形态 | 证据 |
|---|---|---|---|
| 分类只设下限，余量竞争填充 | **借** | `有失败边则 ≥1`/`约束全给（或给溢出计数）`；余量按 `rankReachable` 填 | RAPTOR【核实·全文】 |
| 逐级替换而非删条目 | **已有，外证** | L0–L5 阶梯保持；补"这一档为什么被跳过" | GraphRAG【核实·全文】 |
| 合并后保 seq 全集 | **借** | 渲染合并时 `seq` 取并集，用**集合相等**断言 | GraphRAG + 本仓 `provenanceCoverage`【工程观察】 |
| PPR 可达性排序 + node specificity | **借**（最高优先） | 纯函数 `rankReachable(graph, seeds, budget)`，零依赖、可 `t.eq` | HippoRAG【核实·全文】 |
| 用"当前步骤锚点"当种子 | **借** | 最近用户消息 / 当前工具参数 / touched-files | HippoRAG + 本仓现状【工程观察】 |
| LLM 建图 / OpenIE | **不借** | — | 违反逐字原则；成本在会话中途不可付 |
| 社区摘要 / 重聚类 | **不借** | — | 递归摘要换皮（ρ^k）；节点 id 是出处锚 |
| 按 query 定制检索 | **不借** | — | 压缩时没有"当前问题"（§1.3 同结论） |

## 4 · 检索与 page-in / fault-in

### 4.1 Lost-in-the-Middle（2307.03172）：56.1% 到底是什么

【核实·全文】先纠正一个容易引错的数字 —— §0 提到本文有这处全文引用，但没展开：

- **56.1% 不是"中间位置的表现"，是 closed-book 基线**（不给任何文档时 GPT-3.5-Turbo 在多文档 QA 上的成绩）。原文：*"when relevant information is placed in the middle of its input context, GPT-3.5-Turbo's performance on the multi-document question task is lower than its performance when predicting without any documents (i.e., the closed-book setting; 56.1%)"*。
- 所以真正结论比"中间差一点"重得多：**把证据放中间，比完全不给证据还差**；文中另一处表述是"can drop by more than 20%"。
- 形状是 **U 形**：开头（primacy bias）与结尾（recency bias）最好，中间塌陷；**纯 KV 检索任务也一样**（说明不是"推理难"，是**位置本身**在扣分）。

**对 GOkifu 的含义**：先给结论 —— **本仓的渲染顺序天然是对的**（`ROOT USER` → `CONSTRAINTS` 在头，`LEARNED`（失败边）与 `OPTIONS` 在尾，见 `ledger.mjs` 的 `renderFacts` 组装顺序）【工程观察】。这不是因为我们读了这个结论，而是"重要的先写、明细放后"的自然结果；但它现在有**外证**了，不该在重构时被"按时间顺序排版更易读"之类的理由改掉。

**真正可借的增量在块内**：约束块（**修前**最多 12 条，`cons.slice(0, 12)`；C656 起改成全量逐字、只有病态超限才显式省略）、失败边块可能几十条 —— **块内部的中间位置同样会塌陷**。所以规则要下沉一层：每个块内部也把最强的放两端（如失败边：最近一条放最前、第二强放最后）。这是纯字符串顺序问题，**零 token 成本**，可用 `t.ok(indexOf(...) < n)` 断言（§5.6 probe #6）。

⚠️ 边界：LITM 是**单次推理**的位置实验，不是多步 agent 记忆实验。只能当**排序规则**用，不能当"中间位置一定失效"的定律（§5.5 会看到不同模型在 32K 上的差异极大）。

### 4.2 MemGPT 的 page fault：类比，不是机制

§2.1 已引 MemGPT 全文的阈值与动作。这里补 §2.6 承诺的「page out / fault in」到底能落成什么：

【核实·全文】三条容易读漏的事实：

1. **"page fault" 是论文自己的类比**（拿 OS 换页类比 LLM 管上下文），不是实现里的一个机制。实现里对应的是**函数调用**：`archival_memory_search` / `conversation_search` 一类，由**模型自己决定**何时查。
2. **外部上下文分两类，检索方式有三类**：`recall storage`（完整历史）+ `archival storage`（读写库）；检索支持 **timestamp-based / text-based / embedding-based** 三种。第二类是关键 —— 只有时间索引等于"只能取最近 N 条"，那不算检索。
3. **它明确做了分页**：原文 *"our memory retrieval mechanisms ... implement pagination to prevent retrieval calls from overflowing the context window"*。

**⇒ page-in 的本质不是"把东西拿回来"，而是"模型发起一次有预算上限的检索"**。这条区别决定落地形态：回填若没有 token 上限，它会变成**第二次上下文爆炸**。

**不借**：把"什么时候该 restore"教给模型。那是行为指导，`docs/压缩的职责边界.md` 已判为越界。压缩只能**提供指针**（"seq 10–643 已折叠，可展开"），不能写"你应该展开"。

### 4.3 按需回填的四个必要条件

从 MemGPT（4.2）+ Anthropic 的 just-in-time（4.4）+ HippoRAG（3.4）反推，一个能用的 page-in 通道必须同时满足四条。缺一条就退化成"看起来能查"：

| 条件 | 为什么必须 | GOkifu 现状 |
|---|---|---|
| ① **稳定的可寻址 id** | 回填是按 id 取；id 不稳定就取不回 | 有节点 id + `seq`。但"fold 后 id 仍全局唯一、且不因合并而失效"未见断言【工程观察】 |
| ② **至少两种索引** | 只有时间索引 ⇒ 只能"最近 N 条"，等于没检索；至少要能按**原文**查（错误码/路径/命令） | 缺。`sessionPaths` 有 append-only 日志，但没有按内容查的入口 |
| ③ **每次回填有预算 + 游标** | 否则回填 = 二次爆炸（MemGPT 的分页） | 缺。当前没有任何回填通道，所以也谈不上上限 |
| ④ **回填结果带来源** | 不带 `seq` 的回填等于二次创作 | 边已带 `seq`（`provenanceCoverage` 应恒为 1） |

**⇒ 结论：①④ 已有原料，②③ 缺。** 而"再做一个 decompress 工具"被职责边界明确禁止（工具层越界），所以可行形态只剩一个：**热清单里的指针 + 宿主已有的检索能力**（见 4.5 与 §6.4）。

### 4.4 progressive disclosure：工程共识，不是论文

【核实·全文】Anthropic《Effective context engineering for AI agents》（工程博客，不是论文；按【核实·全文】引用，但请按工程证据打折）：

- **just-in-time 的核心做法**：agent 只持有 **lightweight identifiers**（文件路径、存好的 query、链接），运行时再用工具把数据**动态加载**进来。Claude Code 的例子：写定向 query、存结果、用 `head`/`tail`，从不把整个数据对象塞进上下文。
- **progressive disclosure 的定义**（原文）：*"allows agents to incrementally discover relevant context through exploration"*；每次交互都产出"下一个决策要用的上下文"（文件大小暗示复杂度、命名暗示用途、时间戳可当相关性代理）。
- **代价明说**：*"runtime exploration is slower than retrieving pre-computed data"*；没有好的工具与启发式，agent 会浪费上下文、追死路、找不到关键信息。
- **折中（最贴近 GOkifu）**：hybrid —— 一部分**预算前置**（Claude Code 把 CLAUDE.md 塞进上下文），其余按需探索。

**对 GOkifu 的含义**：351 tokens 热清单的正确定位就是"**前置的 identifiers 层**"：节点 id + `seq` 区间 + 一行事实。它的职责**不是**把历史讲清楚，而是**让下一步能定位**。这解释了一个反直觉的取舍：热清单里"读起来更完整"的写法（补背景、补因果链）会挤掉指针，是**反向优化**。

### 4.5 落地形态：热清单放指针，回填放正文

把 §4.1–4.4 合成一张表，只列**压缩本职内**的动作：

| 动作 | 形态 | 依据 | 代价 |
|---|---|---|---|
| 指针化 | 每条尽量是 `[seq 12-19] tool=pnpm test → EACCES …`，而不是叙述句 | Anthropic just-in-time | 需保证指针稳定（4.3①） |
| 排序 | `rankReachable`（PPR）× 位置规则（每块两端放最强） | HippoRAG + LITM | 纯函数，无额外 token |
| 合并 | 同因多条 → 一行多 `seq`（GraphRAG 的逐级替换） | GraphRAG | 省 token，不损可回溯（前提：保 seq 全集） |
| 分页 | 任何回填设 `maxTokens` + `cursor` | MemGPT pagination | 需要入口（当前缺，§6.4） |
| 省略行 | `[folded: 12 events, 3 failures → nodes n41-n53]` | §2.4 transparent-compact | 个位数 token |

**一条必须写下来的成本证据**：回填不是免费的。transparent-compact 因为带查找通道，在 Qwen 的承诺探针上**每轮未命中缓存的 prompt token 从 21,389 涨到 57,300（约 2.7 倍）**【核实·全文】。所以 page-in 的价值必须算**净账**：省下的折叠 token vs 回填带来的 token 与延迟。当前"一步 351 tokens"这个数字的前提是**不回填**，一旦加回填，它的语义就变了 —— **这也是 §0 那个 351/323 口径问题必须先解决的原因**。

### 4.6 本节净结论

| 想借的东西 | 借不借 | 落地形态 |
|---|---|---|
| 位置规则（每块两端放最强） | **借** | 渲染顺序，纯函数可测（本仓块间已对，块内待做） |
| 指针化（id + seq + 一行事实） | **借**（最高优先） | `renderFacts` 的输出形态 |
| 分页预算 + 游标 | **借**（但需入口裁定） | 见 §6.4 |
| 显式省略行 | **借** | §2.4 方向，补"被遮蔽的 seq 区间" |
| 预算前置 + 按需混合 | **借（当架构原则）** | 热清单=前置层；回填=可选层，默认关闭 |
| 教模型"何时 restore" | **不借** | 越界（职责边界 §2 灰色地带） |
| 无预算的"全文回填" | **不借** | 二次爆炸 |

## 5 · 评测方法：哪些能搬成回归测试

> 本节是全文**唯一直接产出测试**的地方。本仓测试风格：零依赖 `node test/run.mjs` + `tests["名字"] = (t) => {...}`，断言只有 `t.ok / t.eq / t.ne / t.includes / t.notIncludes / t.throws`，**零断言 = 红**（`run.mjs` 的 `zeroAssertions` 检测）。所以下面每个探针都按"能不能在**不调模型**的前提下判定"分类 —— 这是硬筛子。

### 5.1 Compact-Bench（2610.31710）：配对重放，目前最像我们要的评测

【核实·全文】这是本轮找到的**最相关**评测（也是 §2.5 那组 ρ 数字的出处）。

**设计（可直接抄的部分）**：

- **配对**：同一边界、同一 repo 快照，PRE 拿完整历史、POST 只拿摘要，**同样的 agent / 工具 / 环境 / 步数上限（8 步）**，用 `FAIL_TO_PASS` 测试判定。
- **四分类**，不是一个成功率：`preserved`（两边都过）/ `damaged`（PRE 过、POST 挂）/ `rescue`（PRE 挂、POST 过）/ `unsolved`（都挂）。原文理由：分开报**防止某些用例的改善抵消另一些的损失**。
- **稳定性判据**：首轮 damaged/rescue 的用例**再跑两个 seed**，三次里至少两次失败才算 stable damage。
- 规模：35 个 SWE-bench 修复（7 个 repo）、146 个会话（143 real + 3 合成）、106 条生产链、**9,330 条 recurring detail**。

**recurring detail 的定义**（对 GOkifu 极其关键）：只统计**后面请求里还会再出现的结构化值** —— **路径、commit SHA、PR 标识、错误类型**，判据是 *"literal preservation"*（逐字）。

**最重要的发现（比 16.0% / 79.1% 更重要）**：

> *"summaries can retain the target file and relevant strings while losing the progress needed to finish a repair"*
> *"retaining relevant information alone does not ensure successful continuation"*

即：**细节保留率不是充分指标**。摘要可以 100% 保留文件路径与错误串，却把"已经改到哪了、哪个假设被否了"弄丢。这直接支持 GOkifu 保留失败边与 OPTIONS —— 不是为了"信息全"，而是为了**进度状态**。

另一个可直接搬的探针（原文 §3.1 明确记录它测什么）：**摘要会不会把"已完成的文件写入"描述成"待办"**。这正是棋谱的 OPTIONS / 未结算边最容易犯的错（§5.6 probe #3）。

### 5.2 丢弃代价：同长度差 4.7 倍 —— 并核对 §1.3 的「两个数量级」

§1.3 借 budget controller 的理由是"不同成分的丢弃代价差两个数量级（见 §5.2）"。本轮**没能核实到"两个数量级"**，能核实到的是同向但更小的差：

【核实·全文】2608.01056（Control Under Compression；9 个控制上下文 × 3 个模型 × 6 档预算 = 15,525 runs）：

| 条件 | 实际长度 | 成功率 |
|---|---|---|
| SBC（按语义单元选）@35% | ~503 tokens | **47.0%** |
| GLR（通用 LLM 改写）@35% | ~503 tokens | **19.9%** |
| 机械截断 MT @35% | — | **11.7%** |
| LLMLingua @50% | 607 tokens | **10.0%**（45/450） |
| 全量 100% | — | **93.8%**（633/675） |

**同长度量级（503–607 tokens）下最大差 4.7 倍**（47.0% vs 10.0%）。且失败归因高度集中：全部失败的 run 里 **79.7% 是工具执行失败、20.0% 是输出解析失败**，只有 0.2% 是别的。

**⇒ 结论修正**：分段预算该借（§1.3 的结论不变），但**理由要改** —— 不是"代价差两个数量级"，而是"**同长度下选什么差 4.7 倍，且失效集中在执行层**"。这个差别在工程上很重要：前者暗示"要精细分配比例"，后者说明"**只要别把执行必需的东西删掉，比例怎么分不敏感**"，所以只需设**下限**（与 §3.2 的 RAPTOR 结论一致）。

### 5.3 commitments 探针（2610.20116）：27 条探针是怎么造出来的

§2.4 已引它的结论，这里补**可复制的探针工艺** —— 这是唯一被证明"逐字保留赢过模型摘要"的评测：

【核实·全文】

1. **commitment 定义**：会话早期明确下来、**只存在于对话里**的东西，分两类 —— `constraints`（用户要求 / 禁止 / 豁免的）与 `decisions`（商定的选择或约定）。
2. **探针写法**：为每条 commitment 写**一句自然的后续用户消息**；如果 agent 忘了这条，就会**悄悄违约**，而这句话**完全不提**该约束。
3. **防污染**：该 commitment 的关键字符串在整段会话里**只能出现一次**（否则后文复述会替模型"记住"）；每条探针还配一条**对照消息**（明说该约束），对照都失败 ⇒ 探针本身无效，剔除。最终 **27 条 / 18 个会话**。
4. **失败要分性质**：pass / 失败但表达了不确定（提问、警告、hedge）/ **confident failure**（直接断言、没有犹豫）。pi-vcc 有 41% / 52% / 56% 的回复是 confident failure。
5. **3 次重复**；判定用**盲评**（判定者不知道方法名）。

**对 GOkifu 的含义**：棋谱的「约束清单」在语义上正是 constraints + decisions。现在**没有任何断言**检查"k 次 fold 后约束还在不在、有没有被削窄"。第 3 步的"只出现一次"尤其重要：**本仓 fixture 若让同一条约束在历史里出现多次，测试会假绿**。

### 5.4 压缩在「有标识符的任务」上会怎样：与 §1.3 引用的核对

§1.3 断言"τ-bench 上 LLMLingua-2 无增益，因为后续工具调用需要精确标识符（见 §5.4）"。核对结果：**方向对，引用对不上**。

- 本轮**没有**抓到"τ-bench + LLMLingua-2"的原文（记为未核实项，见 §7.3）。
- 能核实的是 **2608.01056 的 §V-C**（标题即 *"The Evaluated LLMLingua Configuration Transfers Poorly to ACCs"*）【核实·全文】：
  - 测的是 **LLMLingua**（`llmlingua==0.2.2`，固定 GPT-2 checkpoint），**不是** LLMLingua-2；
  - **不是** τ-bench，是 9 个人工构造的**控制上下文（ACC）**；
  - 结果比"无增益"惨得多：50% 预算 **45/450 = 10.0%**；25% 与 10% 预算 **0/450**；**25% 时每一个 run 都挂在 action parsing 上**（10% 时 449/450）；
  - 而且它保留的 token 并**不更少**（607 vs OAC 665 / GLR 716 / SBC 721），成功率却是 10.0% vs 49.5% / 37.8% / **67.9%**。作者结论：*"preserving broadly informative tokens is not sufficient to preserve tool identifiers, control envelopes, and executable protocol semantics"*。
  - 它还给了一个**可直接搬的度量**：`ID complete` —— 每个预注册的保留标识符都必须存活，否则该 artifact 记失败。

**⇒ 对 GOkifu 的含义**：这条比"LLMLingua-2 无增益"强得多，因为它给出了**失效形状** —— 不是答得差，是**动作解析失败 / 工具执行失败**。而热清单里全是标识符（路径、命令、退出码、seq）。所以：

- **token 级压缩在 GOkifu 上没有中间地带**：要么标识符全在，要么下一步执行失败。§1.3 的"不借"成立，但要按这个形状写。
- **`ID complete` 应当成为本仓一等指标**（§5.6 probe #1）。

### 5.5 NIAH / RULER / NoLiMa：为什么 "needle in a haystack" 不够

- **NIAH**（Kamradt 2023，博客/仓库，**非 arXiv**）本质是一次**单点检索**：把一句话埋进无关文本，再问那句话。RULER 对它的评价很直白：*"indicative of only a superficial form of long-context understanding"*。【核实·摘要，2404.06654】
- **RULER**【核实·全文】：把 NIAH 扩成 **4 类 13 任务**（检索 / 多跳追踪 / 聚合 / QA），并给"有效上下文长度"下了可操作定义 —— **平均分仍高于 Llama2-7B 在 4K 时的 85.6%** 的最大长度。结论：所有标称 32K+ 的模型里，**没有一个能在其标称长度上维持该基线**。
- **NoLiMa**【核实·摘要，2502.05167】：把 needle 与问题的**字面重叠降到最低**后，**32K 处 11 个模型掉到短上下文基线的一半以下**。

**对 GOkifu 的含义**：热清单本身就是一个 haystack，needle 是"必须被用上的那条失败边/约束"。三个可直接借的**难度旋钮**（都不需要模型）：

1. **多 needle**（RULER 的 MK-NIAH）：同时埋 3 条互不相关的约束，要求全部存活 —— 比"存活 1 条"严格得多。
2. **同形 needle**（MV-NIAH）：3 条失败边长得几乎一样，只有退出码/路径不同 —— 直接命中合并逻辑（`mergeNodeInto`）的风险。
3. **无字面重叠**（NoLiMa）：问"上次那个权限问题解决了吗"，而热清单里写的是 `EACCES`（没有"权限"二字）—— 这正是 351 tokens 里最真实的情形，也是最该测的那一种。

### 5.6 能直接搬进 `node test/run.mjs` 的六个探针

筛选标准：**确定性**（同输入同输出）、**零依赖**、**不调模型**、可用 `t.ok / t.eq / t.includes` 表达。前四个建议先做。

| # | 探针 | 搬自 | 判据（确定性） |
|---|---|---|---|
| 1 | **标识符完整率** | 2608.01056 `ID complete` | 折叠后热清单文本里，每条边/约束的关键标识符（路径、错误码、命令）**逐字**出现 |
| 2 | **约束 k 次 fold 后仍在** | 2610.20116 commitments | 构造 k=5 的 fold 序列，断言约束文本 + `seq` 仍在，且未被削窄（fixture 里该约束**只出现一次**） |
| 3 | **进度方向不倒** | 2610.31710（"已完成写成待办"） | 已结算的成功边**不得**出现在 OPTIONS；未结算的边**必须**出现（至少计数行） |
| 4 | **合并保 seq 全集** | GraphRAG 逐级替换 + 本仓 `provenanceCoverage` | 合并后 `seq` 集合必须**等于**合并前各边 `seq` 的并集（集合相等，比 `provenanceCoverage` 的"行带 seq"更强） |
| 5 | **多 needle 全存活** | RULER MK-NIAH | 同时埋 3 条互不相关的失败边，断言 3 条的标识符全在 |
| 6 | **渲染顺序** | LITM 位置规则 | 断言 `ROOT USER`/`CONSTRAINTS` 在输出前 5 行、`LEARNED` 在末尾 N 行（纯 `indexOf` 断言） |

形态示意（零依赖、可直接跑，断言用本仓现有 `t.*`）：

```js
// test/commitment-survives-k-folds.test.mjs
import { foldN } from "./fixtures/history.mjs";
export const tests = {
  "约束在 5 次 fold 后仍逐字在热清单里": (t) => {
    const { history, hot } = foldN(5);            // 纯函数 fixture，不调模型
    for (const c of history.commitments) {
      t.includes(hot, c.text, `constraint @seq ${c.seq} 必须逐字保留`);
      t.includes(hot, String(c.seq), `constraint @seq ${c.seq} 必须带出处`);
    }
  },
  "同因合并后 seq 集合不变": (t) => {
    const { before, after } = mergeSameError();    // 固定 fixture
    t.eq(after.seqs.slice().sort(), before.seqs.slice().sort(), "合并必须保全集");
  },
};
```

**顺带一个可测的 omission 风险（已被真机证实并修掉）**：修前约束块是 `cons.slice(0, 12)`（`ledger.mjs` 与 `engine.mjs` 的规则兜底摘要同源），而这 12 条之外**没有溢出计数行** —— 第 13 条起就是**静默消失**（Context Codec 的 `omission` 类），正是"沉默即断言"在渲染层的翻版。

**2026-11-08 真机实锤**：一次 pressure fold（rules 规则兜底）把 14 条约束只写回 12 条，落盘 `quality.constraintRecall=12/14=0.857`、`missingConstraints` 恰为被截掉的两条（`State policy: …` / `mutate team state only through agent_teams_* tools.`）；同一条 12 上限还在每步热清单里（并叠了 120 字符 clip，14 条只有 7 条逐字完整）。

**C656 修法**：三处上限全部去掉，约束按原文逐条全量；热清单里预算装不下时按 C41/C44 **如实超预算**（不裁约束），只有病态输入（约束段 >8,000 字符）才转**显式省略行** `CONSTRAINTS_OMITTED: k of N … graph.json nodes[*].constraints`，并由 `handoff-check` ⑧ 强制校验该指针存在。回归用例：`test/constraint-fidelity.test.mjs`（真机 14 条夹具，修前 12/14、修后 14/14）。

**不能搬的（必须明说）**：`preserved/damaged` 的执行判定、confident-blunder 的盲评、ANOVA、`5–64%` 这类跨模型数字 —— 都要跑模型。本仓的等价物只能是 `real-*.mjs` 手工脚本（**不进** `run.mjs`），否则测试会变成"要网络 + 要钱 + 结果不稳定"的三重不可靠。

**降级原则（写死）**：只能做确定性断言时，把"模型能否继续任务"替换成"**继续任务所需的标识符是否可寻址**"。这是**可判定**的近似；从 2608.01056 的失败归因（79.7% 在工具执行）看，这个近似抓住了主要失效模式。

### 5.7 度量口径：「压得更小」不等于「更好」

两条独立的负面证据：

- 【核实·全文】2609.32961（近 35,000 agent runs，SWE-bench Verified + Terminal-Bench 1.0，3 个开源模型）：**token 只需 1/3，端到端反而慢 20–80%**（Terminal-Bench + Qwen）；成功率相近的两种策略**解的是不同的题**；同一策略在不同模型上差别很大。
- 【核实·全文】2608.01056：75% 预算下把输入 token 降了 21.6%（GLR）/ 19.3%（SBC），但**中位延迟从 4.21s 升到 5.03s / 4.88s** —— 作者明确拒绝声称"降低延迟"。

**⇒ 本仓的度量必须同时记三样**：热清单 token 数、**步数**、**wall-clock**。只优化第一项会得到一个更慢的系统。这对 `doctor` 的"热清单预算"是个提醒：`over-budget=0` 只证明没超预算，**不证明压缩有效**。

另外，2605.17304（Context Codec）给了一套**可移植的度量口径**，与棋谱的字段几乎一一对应：

| Context Codec | 定义 | GOkifu 对应 |
|---|---|---|
| Critical Atom Recall | 关键承诺在压缩产物里**可恢复**的比例 | 约束 / 失败边的存活率 |
| Weighted Atom Recall | 按 criticality 加权的召回 | 失败边权重 > 成功路径 |
| Commitment Density | **每 token 保住的承诺数**（不是压缩率） | 热清单应报这个，而不只报 token |
| Round-trip recoverability | 能否从压缩产物反解出等价原子 | 节点 id + `seq` 能否回到原文 |

它的**错误分类学**（8 类）可以直接当 GOkifu 的**测试清单**，每类就是一条 fixture：

| 错误类 | 含义 | GOkifu 里的样子 |
|---|---|---|
| `omission` | 关键原子消失 | 约束/失败边没进热清单（probe #2） |
| `weakening` | 硬约束变模糊 | "必须用 pnpm，不要用 npm" → "建议用 pnpm" |
| `mutation` | 值被改 | 退出码 `1` → "失败" |
| `polarity flip` | 否定丢失/反转 | "不要改 migrate/" → "改 migrate/" |
| `scope error` | 约束挂错对象 | "只在 test/ 下禁改"的"只在"丢了 |
| `temporal/decision error` | **被否的/过时的选择重新出现** | 失败边被擦掉，模型重踩死路（本仓最该防的一类） |
| `hallucinated commitment` | 凭空多一条要求 | 摘要编造节点（`verify.mjs` 已有方向） |
| `safety-boundary erasure` | 拒绝/禁区被删 | 悬空排除、protectedTools 保护失效 |

## 6 · 边界：哪些学术结论不能搬

### 6.1 边界表（11 条）

**逐条一句理由。** 这些方向都有人在别的项目里试过，所以在 GOkifu 里要**写死不许**，而不是"暂时不做"。

| # | 方向 | 代表 | 为什么不能搬（一句话） |
|---|---|---|---|
| 1 | **KV cache 压缩 / 量化** | H2O 2306.14048、SnapKV 2404.14469、KIVI 2402.02750、StreamingLLM 2309.17453 | 它们压的是**推理时的 KV 张量**，不产生任何可持久文本；插件只能改文本，压了也不进会话历史，与"历史能不能继续增长"无关。 |
| 2 | **soft prompt / gist / summary vector** | 2304.08467、2305.14788、2307.06945 | 需要改权重或推理栈，DSH 插件没有落地路径（§1.3 已写死）。 |
| 3 | **训练专用摘要/压缩器** | LLMLingua-2 2403.12968、ICAE 2307.06945 | 与"机械抽取 + 一次润色"架构冲突，且本仓零依赖、不训练、不下载权重。 |
| 4 | **遗忘曲线 TTL / 自动过期** | MemoryBank 2305.10250（Ebbinghaus）、03 号文档的认知类比 | 过期 = **删除**；"取不到"≠"该删"，本仓已有 27.8% 悬空残留（00 §4.1），再加自动过期会静默吃掉证据。 |
| 5 | **衰减权重排序**（灰色地带） | Generative Agents 2304.03442 的 recency | 与第 4 条的区别：衰减**只能改顺序，不能改存在性**；一旦参与"是否渲染"就退化成第 4 条。 |
| 6 | **模型自评重要性** | Generative Agents 的 importance 打分 | 不可复现，且发生在"重构失真最活跃"的时刻（00 §4.1 已裁定）。 |
| 7 | **跨文档知识库 / 向量检索 / GraphRAG 本体** | 2404.16130 等 | 越界：不属于"产自本次会话历史"（职责边界判据①）；§3.5 已给六条分界。 |
| 8 | **提示压缩（无状态投影）** | LLMLingua 系 | 生命周期不同：它每次重算、原文仍在；压缩是**持久化遮蔽**（§1.1）。 |
| 9 | **递归摘要（含其图版本）** | MemGPT FIFO 头摘要、社区摘要 | ρ^k：第三次压缩后关键细节基本归零（§2.5）；换成图结构不改变这一点。 |
| 10 | **"把热清单写得更通顺"** | 各类摘要改写 | 流畅性可能是风险；保留原始报错串是**防伪手段**（00 §4.1）。 |
| 11 | **"窗口够大就不用压"** | 长上下文扩容 | 标称 128K 的模型在字面不重叠的 32K 上掉到基线一半以下（NoLiMa）；LITM 也说明"放得下 ≠ 用得上"。 |

### 6.2 两处必须写明的灰色地带

第 5 条（衰减）与第 11 条（长窗口）**都不是全否**。容许的形态各只有一种：

- **衰减 / 近因只用于排序**：可以进 `rankReachable` 的加权，**不可以参与"是否渲染"的决策**。判据很硬：把这条权重设成 0，热清单的**条目集合**不应改变，只应改变**顺序**。
- **长窗口只当缓冲**：扩张窗口可以推迟 fold，但不能替代 fold —— 压缩触发阈值（§2.1 的 `(warn 70%, flush 100%, evict 50%)`）仍按窗口**比例**算，不按绝对 token 算。

### 6.3 为什么这些"不能搬"不是保守

每一条失败都有具体机制，不是口味问题：KV 量化改的是张量（插件碰不到）；soft prompt 改的是权重（DSH 没有路径）；TTL 改的是**存在性**（而本仓的可回溯性是 append-only 换来的）；知识库改的是**内容来源**（职责边界判据①）。**能搬的都在这三处有替代物**：量化 → 不用（我们本来就不推理）；soft prompt → 指针化文本；TTL → 排序而非删除。

### 6.4 一处必须裁定的边界：page-in 的入口归谁（回应 §2.6 的「见 §6.4」）

§2.6 把「page out / fault in」判为**借**，并把落地形态指向本节。这里给结论：**机制借，入口不借。**

- **不能搬的**：MemGPT 式的**自编辑检索工具**（模型自己调 `archival_memory_search` 一类）。在 DSH 里这属于**工具层**，`docs/压缩的职责边界.md` 明写"不许自建 decompress 工具去接管工具层"。
- **能搬的**：把回填降级成**压缩产物的一个属性** —— 热清单给出**可寻址的指针**（`seq` 区间 + 节点 id + 可点的树路径）。"怎么把那段历史取回来"由宿主已有的读文件/检索能力完成，压缩只负责**让指针存在且唯一**。
- **因此 §4.3 的 ②③（按内容索引、回填预算+游标）不归压缩**，而"指针稳定 + 带 seq + 省略行说明缺了什么"归压缩。这条划线一旦含糊，压缩就会长成一个知识库（§3.5）。

**⇒ 待裁定项（写进 00 号的候选表，不在本文实施）**：是否允许压缩层**只读**地引用 append-only 日志的路径（如 `sessions/<sid>/index.md`），而不提供任何检索 API。现状是热清单里已经有一行 TRACE 相对路径（`ledger.mjs` P6a）—— 那其实就是"只读指针"的最小形态，可以当这条裁定的先例。

## 7 · 净结论表

**只限压缩本职**（`docs/压缩的职责边界.md` 的两条判据：产自本次会话历史 + 只在压缩生命周期出现）。表按压缩的四个动作分组（**压什么 / 怎么降维 / 怎么保真 / 怎么可回溯**），末尾两行是**度量**与**不借**。

### 7.2 三句话

1. **压缩的分水岭不在比率，在「谁决定删什么」**：结构化选择（SBC、抽取式、`ID complete`）与通用改写（GLR、LLMLingua）在同长度下差 **4.7 倍**，且失效形状是**执行失败**，不是"答得差"。
2. **GOkifu 的洞不在"压"，在"取"**：ρ^k 已被增量 fold 消掉，剩下的风险是"节点在图里、但不在热清单里"。第一优先项是**可达性排序（PPR）+ 指针化**，不是更多摘要技巧。
3. **能进 `run.mjs` 的探针都是确定性探针**：标识符完整率、约束存活、进度方向、seq 集合守恒、多 needle、渲染顺序。要跑模型的那部分（配对重放、confident blunder）只能进 `real-*.mjs`，否则测试不可靠。
