# 学术前沿：上下文压缩与 agent 记忆（2026-11 调研）

> 读者：`dsh-gokifu-compact` 的维护者。目的不是写综述，是回答一个工程问题：
> **棋谱式压缩（因果图 + 失败边 + 约束清单 + 每步约 351 tokens 热清单）该从学术前沿借什么、必须拒绝什么。**
>
> 一句话结论：**2026 年的实测证据已经把「压多少」这个问题降级了，真正的分水岭是「压缩器有没有重写事实」。**
> 机械抽取（79.1% 关键细节保留）对 LLM 摘要（16.0%）是 5 倍差距，且这个差距在真实 SWE 修复上直接换算成任务成败。
> GOkifu 走的「从事件机械建图、失败边逐字保留」正好站在这条分界线的正确一侧 —— 但它缺三样东西：
> **来源指针（哪条事件支撑这个节点）、被遮蔽物的显式标注、以及 page-in（按需回填）通道。**

## 1 · 提示压缩（prompt compression）

### 1.1 这一族方法的共同前提 —— 也是它们不能直接搬到会话压缩的原因

这一族全部做同一件事：**在一次推理调用内部，把「这次要喂进去的输入」变短**。

三个必须看清的性质（**这是本节最重要的一段**，比任何单个方法的数字都重要）：

1. **无状态**。压缩结果不落盘、不进会话历史、不会被下一步继承。下一次调用重新压一遍，甚至可能压出不同的结果。
2. **原文仍完整存在**。被删掉的 token 还在 harness 的缓冲区里；压缩是**投影**，不是**销毁**。所以压错了可以下一次改回来。
3. **不解决上下文增长**。输入本身在变长，「每次少花点」只是把斜率压小，不改变「历史无限增长」这个事实。它买的是**成本**，不是**容量**。

会话级压缩（compaction）三条全部相反：持久、原文被遮蔽、直接决定「历史能不能继续增长」。
**⇒ 提示压缩的所有容错设计，都不能直接继承到会话压缩。** §6 会把这条展开成表。

### 1.3 逐个：机制 / 结论 / 可借鉴 / 不可借鉴

**LLMLingua（2310.05736）**

- **核心机制**：coarse-to-fine 三级。(a) **budget controller**——给 prompt 的不同成分（指令 / 示例 / 问题）分配**不同的压缩率**，而不是整体一个比率；(b) **token 级迭代压缩**——逐 token 判断去留时把「已压缩内容」作为条件，建模 token 之间的相互依赖；(c) 用 instruction tuning 做分布对齐，让压缩后的文本更像模型见过的分布。
- **关键结论**：4 个数据集上最高 20x 压缩而「几乎没有性能损失」。这个 20x 是在 GSM8K（数学推理）、BBH（推理）、ShareGPT（对话）、Arxiv 论文上测的，**不是多轮 agent 轨迹**。
- **可借鉴**：**budget controller 的分段预算**。这是本节唯一可以直接搬进 GOkifu 的机制 —— 热清单不该只有一个总预算，该有「约束 30 / 失败边 120 / 成功路径 80 / 目标 20」这类**分项配额**，因为不同成分的丢弃代价差两个数量级（见 §5.2）。GOkifu 现在的 351 tokens 是**总量**，没有分项下限。
- **不可借鉴**：token 级删除。它默认「同义改写不改变语义」，这对自然语言成立，对**路径 / commit sha / 端口 / 错误原文**不成立。§5.4 有直接实测证据（τ-bench 上 LLMLingua-2 无增益，因为后续工具调用需要精确标识符）。

**LongLLMLingua（2310.06839）**

- **核心机制**：在 LLMLingua 基础上针对长上下文做三件事：(a) **question-aware 的粗筛**——用问题去估算段落相关性，再细压；(b) **文档重排**——把高相关段落挪到上下文的**两端**（直接对冲 lost-in-the-middle，见 §4.1）；(c) 动态压缩率 + 子序列恢复。
- **关键结论**：NQ 上**性能提升 21.4% 的同时 token 少 4x**（即压缩不只是省成本，还能**提升**准确率，因为提高了关键信息的密度）；LooGLE 成本降 94.0%；10k token 输入在 2–6x 压缩下端到端延迟降 1.4–2.6x。
- **可借鉴**：**「压缩可以提分」不是悖论**。当关键信息被稀释在长文里时，删掉噪声本身就在提升注意力分配。这对 GOkifu 的 351 tokens 是个正面证据：**极小热清单不只是省钱，是性能手段**。另外「把高相关内容挪到两端」是一条零成本的渲染规则（§4.5 给具体排序建议）。
- **不可借鉴**：question-aware 粗筛需要**当前问题**。会话压缩没有「当前问题」——压缩发生在第 N 步，而热清单要服务第 N+1 到 N+k 步的**未知**问题。§5.4 的实测正好打在这里：为当前问题选句子，对未来问题**不比随机删除好**。

**LLMLingua-2（2403.12968）**

- **核心机制**：把压缩从「按信息熵删 token」改成**token 分类任务**——用 Transformer encoder（XLM-RoBERTa-large / mBERT）在**双向**上下文下判断每个 token 保留与否；训练数据由 GPT-4 蒸馏而来（让大模型标注「哪些词删了不影响」）。
- **关键结论**：小模型（比 7B 小两个数量级）就能压，压缩器本身快 3–6x；端到端 1.6–2.9x；跨 LLM 泛化好。**并且明确把「faithfulness」当成设计目标**：因为是抽取式，输出必然是原 token 的**子集**，不会凭空生成。
- **可借鉴**：**「抽取式 ⇒ 保真」这条推理链**。GOkifu 的失败边逐字保留，本质就是抽取式；论文给的理论支撑是「输出是输入的子集 ⇒ 不可能引入输入里没有的事实」。这条可以写进设计文档当**正确性论证**。
- **不可借鉴**：即便抽取式，**删词**仍然会破坏语法与指代（"it" 的先行词被删）。LLMLingua-2 自己也承认压缩率越高越脆。对 GOkifu：**失败边可以逐字，但不能截断**；截断一条错误信息比不写它更糟。

**Selective Context（2310.06201）**

- **核心机制**：用一个小 LM 算每个词/短语的**自信息（self-information）**，把信息量低的（"the"、"as we know"、冗余修饰）剪掉。本质是「按困惑度剪枝」。
- **关键结论**：上下文减 50% ⇒ 显存 -36%、时间 -32%，代价是 BERTScore -0.023、**faithfulness -0.038**。注意它**自己也报了 faithfulness 下降**——这是这一族里少见的诚实数字。
- **可借鉴**：极低成本的初筛（不需要 GPU 大模型）。如果 GOkifu 将来要压「工具输出的冗余体」，这类无监督打分是零依赖方案。
- **不可借鉴**：自信息 = 罕见 ⇒ 重要。这个假设在 agent 轨迹上是**反的**：`EACCES`、`ECONNREFUSED`、`0x80070005` 都是高频或低信息词，但它们是失败边的全部价值。**按信息量剪枝会优先删掉错误码。**
- **附带一条**：该论文 arXiv 页面有一条 admin note ——「substantial text overlap with arXiv:2304.12102」。引用时注意它的原创性归属。

**RECOMP（2310.04408）**

- **核心机制**：检索到的文档先压成摘要再入 prompt。两版：**抽取式**（选句子）与**生成式**（多文档综合）。两者都**针对下游任务训练**（不是通用摘要）。关键设计：**selective augmentation** —— 若检索内容与问题无关或没增量信息，**直接返回空串**。
- **关键结论**：压到 **6%** 而性能损失极小，显著优于「拿现成摘要模型来压」。且在一个 LM 上训的压缩器**可迁移**到别的 LM。生成式摘要「largely faithful」。
- **可借鉴**：**「允许压到零」**。这条比压缩率重要：绝大多数压缩系统被设计成「必须留点东西」，于是无关内容被硬压成一句含糊的话，反而制造噪声。GOkifu 的 `OPTIONS` 段（未结算的候选边）在语义上接近，但方向相反——它是「保留但标注不确定」，而 RECOMP 是「直接不给」。两者可以并存：**无来源支撑的条目 → 删；未结算但有来源的条目 → 标 OPTIONS**。
- **不可借鉴**：针对下游任务训练压缩器，需要任务分布和梯度。DSH 插件两条都没有。

**软提示路线：Gist / AutoCompressor / ICAE（2304.08467 / 2305.14788 / 2307.06945）**

- **核心机制**：不改文本，改**表示**。把长 prompt 编码成少量「gist token」或「summary vector」，作为 soft prompt 拼进输入。Gist 靠改注意力掩码 + 指令微调实现；AutoCompressor 分段处理长文、把历史段的 summary vector 拼给下一段；ICAE 用自编码 + 语言建模双目标预训练一个压缩器（只加约 1% 参数）。
- **关键结论**：Gist 26x、AutoCompressor 支持 30,720 tokens、ICAE 4x；都能显著降 FLOPs / 延迟。
- **可借鉴**：几乎为零（对插件而言）。**唯一可借的是概念**：AutoCompressor 的「分段 + 每段一个 summary vector + 后续段看到前面所有 vector」在结构上就是 GOkifu 的**增量 fold**（每段压一次，不重压历史）。可以用它当「分段压缩而非递归压缩」的文献先例。
- **不可借鉴**：三条都需要**改模型权重或推理栈**。DSH 插件只能操纵文本。**任何需要 soft prompt 的方案在 DSH 里都不存在落地路径** —— 这条要写死，避免以后有人提议。

### 1.4 这一族给出的两个硬事实

1. **压缩率的天花板与任务强相关**。20x 出现在 GSM8K/BBH 这类「答案由少量关键步骤决定」的任务上；一旦任务依赖长尾细节（多跳、精确标识符、时序），可用压缩率掉到个位数。RECOMP 的 6%、LongLLMLingua 的 2–6x、Selective Context 的 50% ——**同一批作者，数字差 3 倍以上，差别全在任务**。
2. **压缩有「提分」区间**。LongLLMLingua 的 +21.4% 说明：在信息被稀释的场景里，适度压缩 > 不压缩。这给「351 tokens 会不会太少」提供了一个反直觉的答案：**少可能更好，前提是留下的都是高密度的**。

### 1.5 本节对 GOkifu 的净结论

| 想借的东西 | 借不借 | 理由 |
|---|---|---|
| 分段预算（budget controller） | **借** | 直接可用，且能修「351 tokens 无分项下限」这个缺陷 |
| 抽取式 ⇒ 保真 的论证 | **借**（当论证用） | 支撑「失败边逐字」的合法性 |
| 允许压到零（RECOMP） | **借** | 与 OPTIONS 语义互补 |
| 把高相关内容挪到两端 | **借** | 零成本渲染规则，§4.5 |
| token 级删除 | **不借** | 毁标识符，§5.4 有实测 |
| question-aware 选择 | **不借** | 会话压缩没有「当前问题」 |
| 自信息剪枝 | **不借** | 会优先删错误码 |
| soft prompt / gist | **不借** | 需改权重，DSH 无落地路径 |

## 2 · 摘要式记忆

### 2.1 MemGPT 的真实机制（读了全文，不是摘要）

摘要只说「virtual context management / 分层记忆 / interrupts」。全文里真正可工程化的是一组**具体阈值和动作**（arXiv:2310.08560，§2.2 Queue Manager，【核实·全文】）：

- **主上下文 = 三段**：system instructions + **working context**（可写、可被模型自己编辑）+ **FIFO queue**（滚动消息历史）。
- **外部上下文 = 两个库**：**recall storage**（完整对话历史，可全文检索）+ **archival storage**（任意长文本对象，读写数据库）。
- **FIFO queue 的第 0 项是一条系统消息，内容是「已被驱逐消息的递归摘要」**（原文：*"a system message containing a recursive summary of messages that have been evicted from the queue"*）。**这一句是本节最关键的一句**，见 §2.5。
- **memory pressure 警告**：prompt token 超过上下文窗口的 **70%** 时，queue manager 插入一条系统消息警告模型即将驱逐，让模型有机会先把重要信息写进 working context 或 archival storage。
- **flush**：超过 **100%** 时真的驱逐，一次驱逐**约 50%** 的消息。
- **page fault 的类比是显式写出来的**：OS 把溢出数据换到磁盘，「via a **page fault**」再取回内存；MemGPT 让 LLM 自己管理什么留在上下文里，从而伪造出「更大的内存」这个假象。
- **自编辑记忆**：模型通过函数调用（`core_memory_append/replace`、`archival_memory_insert/search`、`conversation_search` 一类）**自己决定**写什么、改什么、检索什么。`request_heartbeat=true` 允许连续链式函数调用而不返回用户。

**四段**：

- **核心机制**：把上下文窗口当 L1，把「完整历史 + 长文本库」当磁盘；用**显式阈值 + 模型自编辑**在两层之间搬运数据；用 page fault 语义保证「搬出去的东西还能拿回来」。
- **关键结论**：分层 + 自编辑 + 中断控制，能在固定窗口下做文档分析和多会话聊天。**它的收益来自「可换回」**，不是来自「压得好」。
- **可借鉴**：**三条，按价值排序**：
  1. **把阈值参数化成三元组 `(warn, flush, evict_ratio)` = (70%, 100%, 50%)**。GOkifu 现在有 `INJECT_MIN_EVENTS=40` 与 `INJECT_MIN_FAILURE_DELTA=5` 两个**触发**阈值，但**没有「一次压多少」的比率**。缺这一维意味着 fold 范围由 fold-planner 隐式决定，无法调参、无法解释。
  2. **70% 处先警告、100% 才动手**。GOkifu 是到点直接压。中间那 30% 的窗口本来可以让 keeper 补抽、让 fold-planner 收敛，现在浪费了。
  3. **page fault 可以作为正式机制引进**（见 §2.6 与 §6）。
- **不可借鉴**：**递归摘要**。FIFO 头部的摘要是「摘要的摘要」——每轮驱逐都把上一轮的摘要再压一次。这是 ρ^k 几何衰减的教科书实现（§2.5 给定量）。GOkifu 的增量 fold 恰好避开了它，**不要为了「像 MemGPT」而把这条加回来**。

### 2.2 RecurrentGPT（2305.13304）

- **核心机制**：用自然语言模拟 LSTM。每个时间步生成一段文本，然后更新两处记忆：**长期记忆写硬盘**（语言化的「记忆」文件）、**短期记忆写 prompt**。相当于把 LSTM 的 cell state 换成一段可读可编辑的文字。
- **关键结论**：可以生成任意长文本而不遗忘；记忆是自然语言 ⇒ 人类**可读、可编辑**；作者顺带提出「AI As Contents」这种交互小说用法。
- **可借鉴**：**「记忆必须是人类可读可编辑的自然语言」**这条设计约束。GOkifu 的棋谱已经是可读的（节点/边/渲染），这在调试和审计上是决定性优势 —— §5.3 的 provenance 问题、§5.1 的「哪条是编的」问题，都只有在**记忆可读**时才查得出来。
- **不可借鉴**：它是**生成**框架（写小说），不需要「历史必须精确」。它的记忆更新是**重写**（rewrite），而会话压缩最怕的就是重写。RecurrentGPT 的评测指标是「文本连贯性」，不是「事实保真」。

### 2.3 2025–2026 的续作：Mem0 / A-MEM

**Mem0（2504.19413）**【核实·摘要】

- **机制**：从对话里**抽取**显著信息 → 整合（consolidate，含冲突消解：新事实覆盖旧事实）→ 按需检索；另有一个图记忆变体。
- **结论**：LOCOMO 上比 OpenAI 的记忆方案 LLM-as-Judge **+26%**；图变体只比基础版 **+2%**；p95 延迟 **-91%**、token 成本 **-90%+**（对比 full-context）。
- **可借鉴**：**「写时整合」而不是「读时压缩」**。Mem0 在**写入**阶段就做去重和冲突消解，所以读取时不用再压。GOkifu 的**置换检测（tewari）**是同一思路的不同切面 —— 但 GOkifu 在**渲染时**才做，Mem0 在**入库时**就做。入库时做的好处是：图里不会同时存在两条互斥的边，热清单渲染不用再判断。
- **不可借鉴**：Mem0 的「新事实覆盖旧事实」是**破坏性**的。对「用户改主意」这是对的；对「这个方案试过、失败、后来换个条件成功了」这是**灾难**——它会把失败边擦掉，正是 GOkifu 明确要保留的东西。**覆盖语义必须限定在「同一对象的属性」上，不能用在「尝试历史」上。** 这也解释了为什么 Mem0 的图变体只 +2%：图在这里只是索引，没承担「保留失败」的职责。

**A-MEM（2502.12110, NeurIPS 2025）**【核实·摘要】

- **机制**：Zettelkasten 式。每条新记忆生成一个结构化 note（上下文描述 / 关键词 / 标签），然后**主动分析历史记忆、建立链接**；新记忆还能**反向更新旧记忆的上下文表示**（memory evolution）。
- **结论**：六个基座模型上优于 SOTA 基线。
- **可借鉴**：「新节点入库时主动连边」——GOkifu 的 keeper 已经在做（意图→动作→结果），但 A-MEM 多了一步：**新节点可以改变旧节点的属性**。对 GOkifu 的具体含义：一条失败边在「后来成功了」之后**不应该被删除**，但**应该被标注 `superseded_by=<edge_id>`**。这样热清单可以渲染成 `FAILED (superseded by e42): ...`，信息量与「只有失败」完全不同。
- **不可借鉴**：「memory evolution 允许重写旧记忆的表示」在 A-MEM 里是无害的（它只影响检索排序）。在会话压缩里**重写旧节点 = 篡改历史**。**只许加标注，不许改内容。**

### 2.4 透明压缩：2026 年最贴近 GOkifu 的一篇

**transparent-compact（2610.20116）**【核实·摘要，单篇预印本】

- **机制**：为开源 Pi coding agent 做的**确定性**压缩。三条硬约束：(a) **用户与助手的散文（prose）在上下文中绝不被模型或算法改写**；(b) **显式标注哪里被剥掉了信息**；(c) 不做任务/上下文特定的结构化。
- **结论**：对四档模型（重点 Qwen3.8-27B，消费级硬件可本地跑的轻量模型）在**承诺（commitments：只存在于对话里的用户规则）**和**事实召回**两组探针上，**匹配或超过** Pi 的默认模型写摘要，也超过 pi-vcc（另一个确定性方法，但不逐字保留散文）。**尤其在于减少「自信的错误」（confident blunders）——把假信息当事实断言，而不是承认「没想起来」。** 前沿模型上优势仍在但更小。
- **可借鉴**：**这是本文对 GOkifu 最有价值的一篇**，三个理由：
  1. 它把「**逐字不改写**」当**第一原则**，而不是实现细节 —— 与 GOkifu「失败边逐字保留」同源。而且它证明这条在**轻量模型**上收益最大，正好是本地部署场景。
  2. 它把 **commitments（只存在于对话里的用户规则）** 单独拎出来当评测对象。GOkifu 的「约束清单」就是这个东西。**可以直接借它的探针设计来做 GOkifu 的回归测试**（现在 GOkifu 的测试里没有「约束是否在 k 次 fold 后仍在热清单」这类断言）。
  3. 「**显式标注被剥掉了什么**」是 GOkifu **缺的那一块**。现在遮蔽是静默的：模型不知道「有一段历史被折叠了」。加一行 `[folded: 12 events, 3 failures → see nodes n41-n53]` 成本个位数 token，但它把「我不知道」和「没有这回事」分开了 —— 这正是论文里 `confident blunders` 的成因。
- **不可借鉴**：「不做结构化」是它的选择，因为它要通用。GOkifu 有领域结构（棋谱），**结构化是 GOkifu 的立身之本**，不该放弃。这条只提醒一件事：结构化不能以「改写原文」为代价。

### 2.5 递归摘要的 ρ^k 衰减（定量）

这是 MemGPT 与官方 `dsh-compaction-basic` 共有的结构，也是 GOkifu 存在的理由。把它算清楚：

设一次「摘要重写」后，某条细节仍被保留的概率为 **ρ**。若每次压缩都把**上一轮的摘要**连同新事件一起重摘，则经过 **k** 次压缩的存活率为 **ρ^k**。

ρ 的实测取值（**都是单篇预印本，未见复现**）：

| 压缩方式 | 单次保留率 ρ | 出处 |
|---|---|---|
| LLM 摘要（14 个摘要模型里最好） | **0.16**（"retain at most 16.0% of recurring details"） | arXiv:2610.31710 Compact-Bench 【核实·摘要】 |
| LLM 摘要（生产环境第一次边界） | **0.157** | 同上 |
| **机械抽取** | **0.791** | 同上 |

代入：

| k（压缩次数） | LLM 摘要 0.16^k | 机械抽取 0.79^k |
|---|---|---|
| 1 | 16.0% | 79.1% |
| 2 | 2.6% | 62.6% |
| 3 | 0.41% | 49.5% |
| 5 | 0.0105% | 30.9% |

**读法**：LLM 摘要走递归，第三次压缩后关键细节基本归零；机械抽取即便递归也还有一半。
但 GOkifu 的结构是**增量 fold**：一条细节在**第一次覆盖它的 fold** 里被抽成图节点，之后**只被渲染、不再被重写** ⇒ 存活率是 **ρ¹，不是 ρ^k**。

**这里必须诚实**：GOkifu 的 ρ^k 消失了，但**风险没有消失，只是换了名字** —— 从「**被改写**」变成「**不在热清单里**」。
一个节点在 k 次 fold 后仍然完好地存在于 `graph.json`，但如果它没进那 351 tokens，模型就看不见它。
**⇒ 真正的失效模式是检索，不是损坏。** 这也是为什么 §2.6 的 page-in 和 §3.4 的可达性排序是本文对 GOkifu 的核心建议。

### 2.6 本节净结论

| 想借的东西 | 借不借 | 落地形态 |
|---|---|---|
| `(warn 70%, flush 100%, evict 50%)` 三元阈值 | **借** | config-schema 加两个键，注释可改 |
| 逐字不改写散文 + 显式标注剥离 | **借**（最高优先） | 热清单加 `[folded: ...]` 行 |
| commitments 探针当回归测试 | **借** | `test/` 新增「k 次 fold 后约束仍在」断言 |
| 写时整合（入库去重/冲突消解） | **借**（限定） | tewari 前移到 keeper |
| `superseded_by` 标注（不删边） | **借** | 边加字段，渲染加前缀 |
| page out / fault in（MemGPT + Pichay） | **借** | 见 §6.4 |
| 递归摘要 | **不借** | — |
| 新事实覆盖旧事实 | **不借**（对失败边） | — |
| 重写旧节点表示 | **不借** | — |
| soft prompt / 改权重 | **不借** | — |
