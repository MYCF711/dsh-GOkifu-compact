## 三 · 三个技术判断（都有数据支撑）

1. **官方实现会跨压缩失忆**：`selectCompactableRange` 从 surface 第一个非 system 节点开始压，而上一次 checkpoint 就在 surface 里，于是每轮都被再摘要一次。Compaction Cliff 实测安全规则五轮后只剩 10%。本插件把起点挪到「最后一个 checkpoint 之后」，`test/integration.test.mjs` 有「连续三次 fold 范围互不重叠」的硬断言。

2. **约束必须机械保留，不能靠模型遵守**：多规模实测（5/15/30 条失败边）发现约束保留率在 0/2~3/3 之间跳 —— 同一份 prompt，模型心情不同结果不同。改为 `engine.summarize()` 在模型输出后**机械追加** `CONSTRAINTS_VERBATIM` 段：规则抽什么，产物里就有什么，模型写不写都不影响。

3. **失败原因必须由规则注入**：真实模型对照证明 —— 同一段会话，官方 8 段模板平均只保留 4.67/8 条失败边（最差 3/8），而带 `[HARD FACTS]` 的棋谱 prompt 3 次全部 8/8。差异不是模型能力，是 prompt 是否把「不许丢」写成硬约束。

4. **热上下文必须是索引，不是全集**：1201 条失败边的现实里，「全部常驻」会渲染出 28,800 tokens。改为「预算内逐条列 + 超预算只列最近 50 条 + 汇总行指向 graph.json」，476 tokens 解决，且汇总行保证可发现。

5. **原始记忆必须保留，棋谱只是索引**：干净子代理实验（15 条真实死路，`evidence/棋谱有效性实验.md`）证明棋谱能让一个没有记忆、没有源码的 agent **15/15 避开已知坑**；但对照组（只给原始文档、不给棋谱）补出了 **2 条棋谱漏掉的坑** —— 任何抽取都会漏。所以三层（索引 / 节点 / 原始）都要留，砍掉原始层就是永久丢信息。

## 三·五 · v0.1.3：独立代码审查修掉的 3 个 P0

一个独立审查子代理（只读，真实日志回放 + 内存复现）报了 15 条，其中 3 个是会让插件「看起来在工作、实际在毁数据」的 P0：

| # | 问题 | 证据 | 修法 |
|---|---|---|---|
| P0-1 | `this.flushTimers` 从未初始化 | `#scheduleFlush` 第一行 `this.flushTimers.has(key)` → TypeError；**debounce 落盘从未工作** | 构造函数初始化 Map |
| P0-2 | 节点创建写死 `worldHash:"pending"`，fold 前统一回填成同一哈希 | 4 个 step 后节点 5→2、3 条边 `from` 悬空；live graph 30 个 agent 只有 1 个真哈希 | engine 注入 `state.worldHashOf()`，节点用创建时刻真实哈希；`touchPath` 真的喂给世界状态 |
| P0-3 | `mergeNodeInto` 只改 `edge.to` 不改 `edge.from` | live graph 155 条边里 **115 条 `from` 指向已删节点** | 补 `edge.from === fromId` 分支 + 新增单测 |

**这三个的共同点**：不抛异常、不报错，只是悄悄把图结构写坏。`validate()` 能查出来，但运行期从来没有人调用它 —— 这条（P1-11）还没修，已记进 HANDOFF。

**当前测试**：81 项单测全绿（修 P0 后新增 3 条：flushTimers 存在性、合并非叶子节点、真实哈希非 pending）。
