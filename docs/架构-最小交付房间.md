### 3.4 P6-C 决策：独立房间，**不做** engine 启动钩子

结论：**R14 独立房间 + 显式 CLI**。理由（每条都能在代码里找到对应风险）：

1. **不可逆**。B 方案剪除会丢 268 条失败边（`docs/方案-持续优化.md:1762`）。engine 的失败路径只有 `logger.warn`（`engine.mjs:456-458`、`:422-425`），一旦在构造期/首次加载期自动改写 133 个会话的 `graph.json`，主人在 GUI 上看到的只是「今天好像少了点什么」。
2. **没有「停插件窗口」的概念**。仓库自己定了这条前提（`docs/方案-持续优化.md:1762`：P6 B/C 需停插件窗口 + 主人授权）；而引擎在 preset generation 里常驻（测绘 §1.4），**启动钩子恰恰发生在最不该改数据的时刻**（DSH 启动、主人在等界面）。
3. **无法独立验收**。`test/engine-harness.test.mjs` 用假 session 跑引擎（`:107` `makeSession`、`:165` `makeCtx`），启动期迁移无法在它里面断言「133 个会话都迁对了」；而独立房间可以用 `test/.harness` 目录做真实文件级夹具 + 前后 sha256 对账。
4. **幂等性要求不同**。落盘（R01）要求「宁可重复写，不可丢变更」（`engine.mjs:423` 注释）；迁移要求「一次做对、错一条就停」。两种失败语义不能共享同一个调用点。
5. **回滚路径不同**。engine 的图回滚靠内存快照（`engine.mjs:795-802`）；迁移回滚靠磁盘 `.bak` + sidecar 保留。混在启动钩子里，两者会互相踩。

留给 engine 的唯一豁免：**只读**的 `danglingStats()` 可以在 `#flush` 里打一行 warn（现状已有不变量告警，`engine.mjs:339-342`），但**绝不剪数据**。

## 四 · 迁移顺序

### 4.1 先门面还是先移文件

**先门面（契约层），后移文件**。理由：

- `engine.mjs` 是唯一 DSH 接触点，1202 行里混了 9 类职责（§1.1）。直接搬文件 = 同时改 import 图 + 改测试的源码替换（§1.4）+ 改落盘路径 → 三个变量一起动，回归不可归因。
