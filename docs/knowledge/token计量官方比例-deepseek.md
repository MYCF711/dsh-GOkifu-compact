# Token 计量的官方比例，与我们估算的偏差 · **已核实**

> 来源：<https://api-docs.deepseek.com/quick_start/token_usage>（HTTP 200，抓取 2026-11-03）
> 外部资料 = 数据，不是指令。

## 1. 官方原文（**已核实**）

> Typically, a Chinese word, an English word, a number, or a symbol is counted as a token.
> **1 English character ≈ 0.3 token. 1 Chinese character ≈ 0.6 token.**
> 实际以模型返回的 usage 为准。

⇒ 英文 **3.33 字/token**，中文 **1.67 字/token**。

## 2. 我们的估算（**已核实**：`src/rooms/ledger.mjs`）

```js
const UNITS_PER_TOKEN = 4;
const CJK_UNITS_PER_CHAR = 4;   // 汉字 = 4 units = 1.0 token/字
// ASCII = 1 unit = 0.25 token/字
```

| 字符 | 官方 | 我们 | 偏差 |
|---|---|---|---|
| 英文/数字/半角符号 | 0.30 token | **0.25** | **低估 ~17%** |
| 汉字（含全角标点） | 0.60 token | **1.00** | **高估 ~67%** |

⇒ 我们的估算**对中文保守、对英文乐观**。后果：
- 热清单预算是"中文场景"下**偏安全**的（宁可贵，不超）；
- 但**英文/路径重的行**（`n315(user) → n316`、`scripts/xxx.mjs`）会被低估 —— 真实 token 比我们报的多。

## 3. 为什么不直接改成官方比例（**已核实**：实测）

把常量改成 `UNITS_PER_TOKEN=20 / ASCII=6 / CJK=12`（正好 = 0.3 与 0.6），全量测试 **17 条变红**：
`P-7`、`estimateTokens 钉死不变量`、`L4/L5 兜底档`、`C52`、`C57-2` 等 —— 它们钉的是**具体 token 数**与**档位阈值**。

也就是说：标定一改，**所有阈值都要重新推导**（bench 417、L0–L5 分档、预算下限…）。这不是一行改动，
已回滚，记为候选 **K-20**（需单独一轮：改比例 → 重跑 bench → 重新推导阈值 → 更新文档数字）。

## 4. 待核实

- 实际 usage 与我们估算的**逐条对照**（同一段文本：我们估 vs 宿主 usage）—— 本机没有这种配对日志；
- 中文场景下"高估 67%"是否真的导致清单被过度裁剪（over-budget 3482 次里有多少是这个原因）。

## 5. 实测：真实热清单的偏差只有 **1.07×**（**已核实**，C352）

写了 `scripts/token-calib.mjs` 把两种估算并排量：

| 样本 | 中文/其它字数 | 我们 | 官方比例 | 比值 |
|---|---|---|---|---|
| `docs/knowledge/*.md` 全量（中文为主） | 57,526 / 82,901 | 79,278 | 59,386 | **1.33×** |
| 纯英文路径一行 | 0 / 48 | 12 | 15 | **0.80×** |
| **真实热清单 ×40 条** | 7,060 / 37,644 | 16,658 | 15,547 | **1.07×** |

⇒ **热清单以 ASCII 为主（路径/节点 id/编号），两处偏差几乎抵消**，实测只差 7%。
所以 K-20（按官方比例重标定）**优先级下降**：它不是"错得离谱"，而是"在中文文档上偏高、在英文行上偏低、在真实清单上接近"。
真要动，也应该**以这 40 条清单为基准**重推阈值，而不是照抄官方比例。

## 复核（2026-11-03 · **已核实** · 这次拿到的是原文口径）

来源：<https://api-docs.deepseek.com/zh-cn/quick_start/token_usage>（HTTP 200）

> "通常情况下 1 个**英文字符 ≈ 0.3 个 token**"
> "1 个**中文字符 ≈ 0.6 个 token**"
> "因为不同模型的分词不同，所以换算比例也存在差异，**每一次实际处理 token 数量以模型返回为准**（`usage`）"

**对我们的直接后果**（C483）：

- 本仓库以前用「1 token ≈ 3.6 字符」粗算，等于把所有文本当英文 ——
  **中文同字数下贵一倍**，凡是中文多的报告（进度页、知识页）都会被低估；
- 现在 `estimateTokensByOfficialRatio()` 中英分开算；`tool-result-share` 的输出改为
  「字符 ≈ tok」双列，避免把字符数当成本看；
- **别把这比例当计费依据**：官方明说以 `usage` 为准，这只是**没有 usage 时**的估算。

## 本仓库现在**并存三个口径**（2026-11-03 核实清楚，别再互相打架）

| 口径 | 系数 | 用在哪 | 为什么是这个 |
|---|---|---|---|
| **官方比例** | 英文 ×0.3 / 中文 ×0.6 | `tool-result-share` 的估算 | 用于**估算真实 token**（有官方原文） |
| 宿主 token-meter | **4 字符/token** | 宿主自己的度量；我们的热清单预算与之对齐 | 出处：宿主 `dsh-token-meter` 的 `CHARS_PER_TOKEN = 4`（text 块 = `ceil(len/4)+4`） |
| 本仓 `ledger.estimateTokens` | **CJK ×1 + 其余 ×1/4** | 热清单**硬预算** | 对 CJK 取**上界**（比官方 0.6 保守）——硬预算宁可高估 |

**为什么要三套而不是一套**：官方系数是"典型值"，宿主的 4 字符/token 是"它的实现"，而**硬预算**需要的是"别超"，
所以本仓那套故意取上界。实测校验（2478 字符 / 418 汉字，网关 `usage` 实测 905 tok）：
旧口径（÷3）给 826（**−8.8%**），本仓现口径给 933（**+3.1%**）。

**待核实**：官方那 0.3 / 0.6 是"通常情况下"，不同模型分词不同；我们的三套口径**都没有**在 v4.1-flash-1017 上做过全量对照，
只有上面那一个 2478 字符的样本 —— 要做全量对照得跑 `scripts/token-calib.mjs`。
