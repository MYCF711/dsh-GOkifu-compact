## 1. 原文的分类（对我们最好用的一张表）

把它归结为四类策略，每类配了业界做法：

| 类别 | 原文说法 | 谁在用 |
|---|---|---|
| **Write**（写出去） | 把信息写到 context 之外的持久层（scratchpad / 文件 / 记忆），需要时再读回 | Claude Code 的 to-do、Memory tool |
| **Select**（选进来） | 每步只把**相关**片段拉进窗口（检索、按需读文件、工具白名单） | RAG、`@` 文件引用 |
| **Compress**（压缩） | 摘要 / 裁剪 / 去冗余，把长历史变短 | compaction、tool result clearing |
| **Isolate**（隔离） | 把上下文**拆到不同 agent/子任务**里，别让一份窗口背所有事 | 子代理、多 agent 编排 |

## 2. 我们站在哪一格（对本项目的定位）

| 类别 | 我们的实现 | 覆盖度 |
|---|---|---|
| Write | 棋谱（`graph.json` + `nodes/*.md` + `index.md`） | ✅ 强：比自由笔记多了可寻址闭包与失败记忆 |
| Select | 热清单（每步只注入 ROOT/CONSTRAINTS/LEARNED/WORKING/OPTIONS） | ✅ 强：这就是"只放决策必需的" |
| Compress | 折叠 + tier-2 合并 + `toolResultPruner` | ✅ 强 |
| Isolate | 不在我们职责内（宿主/DSh 的 preset 与子代理） | ⛔ 不覆盖（设计边界，不硬做） |

⇒ 结论：**四类里我们做三格，且每一格都比"最小可用"更硬**（规则事实、可寻址、闭包自洽）。
这条可以直接拿来回答"这个插件到底值不值得存在"——它不是一个 compaction 实现，而是 **Write+Select+Compress 三层一体的记忆系统**。

## 3. 三条能落到代码/判据上的

1. **Select 的质量靠"引用"而非"复制"**：原文强调按需把片段拉进来（不是提前堆）。我们的热清单里
   `# path:` / `e123 → nodes/<id>.md` 这类**指针**正是这个思路 —— 指针比内容便宜一个数量级。
   ⇒ 判据：**任何一段清单文本，如果模型能靠指针自己去拿，就不该内联**（可作为 K-6 的判断标准）。

2. **Write 层的失败记忆比摘要更值钱**：原文把 write/select 放在 compress 之前讲，暗示"先外置、再压缩"。
   我们已经把约束/失败边做成**永不靠摘要活**（`docs/压缩的重注入契约.md`）——方向一致。

3. **Isolate 是唯一我们没做的**：原文把它列为四类之一，说明"压缩不是唯一解"。
   ⇒ 这解释了我们的边界：单会话压力靠 compress，**跨任务压力应该由宿主用子代理隔离**，
   不要指望一个压缩插件解决"一个窗口干所有事"。

## 一句话蒸馏

> 「write / select / compress / isolate」四个格子，我们占三个（都做到比最小可用更硬），
> 第四个（隔离）属于宿主层。**知道自己在哪一格，比把每一格都做到 60 分更重要。**
