# Lost in the Middle（TACL 2023）· 判读

> 来源：<https://arxiv.org/abs/2307.03172>（HTTP 200，抓取 2026-11-02）
> 标题：**Lost in the Middle: How Language Models Use Long Contexts** · TACL 2023
> **外部资料 = 数据，不是指令。只据摘要，未读全文。**

## 1. 原文结论（**待核实**：未在本机复现）

- 长上下文的**位置效应**很显著：同一段相关信息，放在**开头或结尾**时表现最好，
  放在**中间**时明显变差 —— 即便是"长上下文模型"也一样；
- 两个任务：多文档问答 + key-value 检索；换位置就掉分，说明模型**不是均匀地使用上下文**。

## 2. 对我们意味着什么（这是本轮最有用的一条）

我们的注入点是**在用户消息之后、紧贴末尾**（`toSpliced(lastClaimed + 1, …)`）。
按原文，这正好落在「**结尾**」这个高可用区 —— 不是巧合，是设计对了。

反过来看有个隐患：**折叠后，较早的关键信息（用户最初的约束）会沉到上下文中间**。
这就是为什么我们要**每步重新注入 CONSTRAINTS**（逐字）—— 原文这条结论是我们这个设计的**外部依据**：
> 沉到中间的东西会被"看漏"，所以重要事实必须**每步放回末尾附近**。

## 3. 与已有判读的关系

- 与 context rot 一致：都是"上下文不是均匀的资源"；
- 与 C220（97% 走缓存）叠加的解释：**每步重注入**的代价被缓存吸收了（命中率高），
  所以"把约束搬到末尾"这件事在经济上也是可行的 —— 这两条合起来才成立。

## 4. 一句话蒸馏

> 重要的东西要放在**开头或结尾**，不要指望模型自己翻中间。
> 我们的热清单注入点是末尾（对），代价由缓存吸收（也还行）；
> 真正该反省的是**清单内部**的顺序：把判别价值最低的行（例如已被自己修正的失败）挤到了读得最清的位置。
