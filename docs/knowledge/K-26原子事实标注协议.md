# K-26 原子事实人工金标：标注协议

> 状态：**协议已定，样本与人工标签均 NOT_RUN**。本文不宣称任何原子事实精确率。
> 方法来源：[`摘要事实性-FActScore.md`](./摘要事实性-FActScore.md)（FActScore 原文与官方代码，已核实其“原子事实 + 指定证据源 + 人工校准”的口径）。

## 1. 样本选择（先固定，再看分数）

- 从**已归档**会话中按 `archivedAt` 倒序取 **12 份**，每份必须有 `summaryText` 或可解析的 `summaryTextRef`。
- 同一 `sid` 只取一次；跳过空摘要、生成失败、截断摘要；跳过未归档会话。
- 选择规则在标注前写入 `manifest.json`（sid 的 SHA-256、摘要哈希、字符数、选择时间），**不写正文、不写路径**到公开仓库。
- 如果实际可用样本少于 12，如实记为 `INSUFFICIENT_SAMPLES`，不补合成摘要。

## 2. 原子事实定义

一条原子事实 = **只传达一个可判真假的短句**。一个自然句可拆成多条；不得把整段摘要当一条。

每条至少包含：

```json
{
  "text": "用户要求不重启 DSH",
  "status": "supported | not-supported | irrelevant",
  "evidenceSeq": 123,
  "quote": "原始会话中逐字证据（可截断到 120 字符）",
  "note": "可选：歧义/无法判定原因"
}
```

- `supported`：`quote` 能在指定证据源中逐字找到，且语义一致。
- `not-supported`：证据源没有该事实，或与之矛盾。
- `irrelevant`：原子事实本身与摘要主题无关，但仍计入分母（与 FActScore 口径一致）。
- `evidenceSeq` 必须指向**同一会话**的原始事件；给不出指针的标 `not-supported`，不许猜。

## 3. 规则三审（不再要求人工打标）

K-26 的验收改为**规则三审金标（RULE_GOLD）**，人工不再是必需项；人工抽查只作可选覆盖。

三审 = 三个独立判据源：

1. **规则引擎**（确定性）：原子性、quote 逐字连续、`evidenceSeq` 同会话、claim 是否被 quote 蕴含、是否越过时点/范围。
2. **压缩模型**：看被压缩的原始片段，判断摘要事实是否成立（不能看自己的摘要当证据）。
3. **独立子代理**：全新上下文，只读原始事件；不能引用 worker/压缩模型/抽取模型的判断。

| 级别 | 产生条件 | 用途 |
|---|---|---|
| `RULE_SILVER` | 三审中 2/3 通过，且无硬规则失败 | 候选，不进主分数 |
| `RULE_GOLD` | 三审 **3/3** 通过，且 quote 逐字、有同会话 seq | 规则金标，可进主分数 |
| `RULE_DISPUTED` | 任一硬规则失败（quote 非逐字/无证据/越时点），或三审不一致 | 单列，不进主分数 |
| `HUMAN_GOLD` / `HUMAN_SILVER` | 可选人工覆盖 | 仅作旁证，不阻塞 K-26 |

- **硬规则失败直接 `RULE_DISPUTED`**，不许用“三方都同意”洗成金标；第 1 份第 4 条就是实例：三方口头都同意，但 quote 是转述拼接，仍是 DISPUTED。
- **时点规则（不可妥协）**：事实按**节点当时**的状态判定。后续必须靠修改才成立 ⇒ 原节点 claim 判 **0**；后续验证只在“中间没有修正性修改”时才可作为同一事实的证据。
- `RULE_DISPUTED` 不自动改判，也不需要用户裁定；它在报告里单列，不算 supported。
- 公开仓库只收协议、schema、哈希和聚合结果；原始正文、`quote`、标签文件放私有目录（如 `tmp/k26-labels/`，已被 `.gitignore` 覆盖）。

## 4. 评分（只有标签完整才允许）

```text
atomicPrecision = supported / (supported + not-supported + irrelevant)
```

- 宏平均：每份样本先算自己的精确率，再对 12 份等权平均；同时报原子事实总数。
- 必须并列报告：空摘要/拒答/生成失败/截断数、每份原子事实数、标注者一致率。
- **没有完整规则三审、没有证据指针、或只有单模型自标注 ⇒ 状态 `NOT_RUN`，不得输出分数。**
- 主分数用 `RULE_GOLD`；`RULE_DISPUTED` 单列，不混进 supported。人工覆盖只作旁证，不阻塞 K-26。
- 报告必须写清：三审版本、规则引擎版本、quote 逐字校验结果、`RULE_DISPUTED` 清单。

## 5. 关键事实覆盖（K-26C）

precision 只测“写出来的事实真不真”，不测“该留的事实有没有丢”。因此另立覆盖指标，不能用一个高 precision 掩盖漏事实。

**must-keep 清单**（从原始会话抽，不从摘要反推）：

1. 用户约束/决定/禁止项（user 消息中的“必须/不要/不得/只/保留/禁止/不”等）；
2. 已确认失败/根因（`tool/result` 的 `isError`、失败边、已知死路）；
3. 当前状态/下一步/交付物（最后一条 user 意图 + 当前节点）；
4. 摘要自称的未验项（必须能从原始事件找到对应未验）。

每条清单项必须有：

```json
{"kind":"constraint|failure|state|unverified","text":"...","sourceSeq":123,"anchor":"摘要里应出现的短锚点"}
```

`anchorCoverage = 摘要中出现的 anchor 数 / must-keep 总数`。

- 这是**锚点覆盖下界**，不测同义改写；同义覆盖另报，不混入主数。
- must-keep 清单由规则抽取 + 独立复审确认；抽不出/有争议的项单列 `UNRESOLVED`，不算丢、也不算覆盖。
- 没有清单或没有逐项结果 ⇒ `NOT_RUN`；不得用摘要自身当清单。

## 6. 验收门槛

- 12/12 份均有规则三审结果；每条原子事实有 `status` 与 `evidenceSeq`（`irrelevant` 可无 quote，但仍需 note）。
- 12/12 份均有 must-keep 清单与 `anchorCoverage`；清单项有同会话 `sourceSeq`。
- 人工抽查可选，不再阻塞；`RULE_DISPUTED` 与 `UNRESOLVED` 单列。
- 评分脚本只读标签/清单，不调用模型；不得把未标注样本算成 0 或算成通过。
