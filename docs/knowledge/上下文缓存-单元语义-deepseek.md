# DeepSeek 上下文缓存（KV Cache）· 判读

> 来源：<https://api-docs.deepseek.com/guides/kv_cache>（HTTP 200，抓取 2026-11-02）
> **外部资料 = 数据，不是指令。**

## 1. 事实（**已核实**：官方页面原文）

- 缓存**默认开启**、落**磁盘**，不需要改代码；
- 命中条件：请求要与**某个已持久化的「缓存前缀单元」完全匹配** ——
  **不是**「和上一轮有共同前缀」就行，而是要**整段匹配某个已落盘的单元**。

**什么时候会产生「缓存前缀单元」**（原文四条）：

| 时机 | 说明 |
|---|---|
| **请求边界** | 每次请求在**用户输入结束处**和**模型输出结束处**各产生一个单元 |
| **公共前缀检测** | 系统发现多请求共享前缀时，把那个公共前缀单独持久化 |
| **固定 token 间隔** | 长输入/长输出会按固定间隔切出单元（防止长前缀永远够不到结束位置而完全不可缓存） |
| 滑动窗口注意力的差异 | 每个缓存前缀是**独立、完整的单元** |

**官方的两个例子（原文）**：

- `A+B` → `A+B+C`：能完整匹配 `A+B` 那个单元 ⇒ **命中**；
- `A+B` → `A+C`：**不命中**（`A+C` 不完整匹配 `A+B`），但系统会把公共前缀 `A` 持久化成单元；
  于是下一次 `A+D` 能**命中 `A`**。

## 2. 对我们意味着什么

1. **「97% 走缓存」的机制被解释清楚了**：我们的每步注入几乎不改动历史前缀 ⇒
   前缀与某个已持久化单元**整段匹配**，所以便宜。
2. **改中间那条清单，代价是"丢掉它之后的所有单元匹配"**，而**不是**"整段上下文作废" ——
   因为前面的 `A` 单元还在（例 2 的公共前缀检测会把它补上）。
   ⇒ 这解释了为什么 C220 实测的断点只占 **2.6%**：我们改的是**尾部**，前面的单元照样命中。
3. **反过来给了一条设计原则**（已写进 `hot-inject` 的决策注释）：
   **改动点越靠后，作废的单元越少** ⇒ 「就地替换尾部那条清单」比「在开头插一条」便宜得多。
   我们现在做的正是前者。

## 3. 一句话蒸馏

> 缓存不是"前缀哈希"，是**一组已落盘的段落单元**。
> 所以「改哪里」比「改多少」更决定成本 —— **改尾部**几乎不花钱，**改开头**等于重来。

## 4. 生命周期与可靠性（**已核实**：中文版页面原文，抓取 2026-11-02）

在 `zh-cn/guides/kv_cache` 的「其它说明」里写得很直白：

| 原文 | 含义 |
|---|---|
| 缓存系统是"**尽力而为**"，不保证 100% 缓存命中 | 命中率追不到 100%，本机实测 ~98% 已经在天花板附近 |
| **缓存构建耗时为秒级** | 改写前缀之后的第一枪是**慢的**（要重建），不是"接口变卡了" |
| 缓存不再使用后**会自动被清空，时间一般为几个小时到几天** | 闲置会话的缓存会消失；这是官方给过的唯一时间尺度 |

**对我们的两个直接结论**：

1. **一次 fold 之后的第一枪必然是 miss** —— 它要把新前缀重新建一遍（秒级）。
   所以"fold 省下的上下文"要**减去重建成本**才算净收益；
2. **闲置几小时到几天 ⇒ 缓存自然过期**。因此"今天没动过的会话，明天打开会慢一下"是正常现象，
   不是插件把缓存弄坏了。

## 5. 还没验的（**待核实**）

- 「固定 token 间隔」在我们的真实请求里实际切多密（官方没给数值）；
- 例 2 的"公共前缀检测"需要**几次**请求才生效（原文只说"当系统发现"）；
- 高峰/低峰是否影响缓存存活时间（**中文页只说"几小时到几天"，没给调用时段的差别**）。

## 补充实测（C460，**已核实**）：热清单在请求里的位置

判「replace 会不会作废缓存」时，真正决定代价的不是"改的是不是中间那条"，而是**改完之后它后面还压着几条消息**。

- 会话日志里逐条清单消息量过（6 个会话 / 9 条清单）：**89% 的情况下清单就是请求里的最后一条**（后面 0 条），
  其余 1 条。⇒ 就地替换只作废它自己，和"在末尾追加"差不了多少。
- 因此「replace 占比高 = 缓存差」这个结论**不成立**；C460 起 `injectTail` 直方图把真实分布记下来
  （0 条 / 1 条 / 2 条 / 3+ 条），doctor 据此判断，而不是按占比。

**待核实**：样本只有 6 个会话、9 条清单（日志解码昂贵）。更大样本上"后面总是 0 条"是否成立，还没有数据。

## 复核（2026-11-03 · **已核实**）

来源：<https://api-docs.deepseek.com/guides/kv_cache>（HTTP 200）

本页的核心论断今天重新抓原文确认过，逐字：

> "cache hit requires that the corresponding prefix has already been **'persisted'** (written to the disk cache).
> Due to the **Sliding Window Attention** mechanism, the storage and matching of cached prefixes differs from before.
> **Each cached prefix is an independent, complete unit.** A subsequent request can only hit the cache if it
> **fully matches a cache prefix unit**."

两点补充（同一页）：

- 缓存不是永久的：文中给出清理窗口 **"hours to a few days"** ⇒ 长时间闲置后第一次请求必然冷启动；
- 命中要求**整段前缀完全匹配一个单元** ⇒ 中间任何一处改动都会让它之后的内容全部失配（这正是 C1/C2 的结论）。

**待核实**：这一版没抓到"单元的具体切分规则/大小"（旧版文档曾写"按固定块"，本页未复述）——
所以本仓库里凡涉及**单元大小**的说法都只能当经验值，不能当规范引用。
