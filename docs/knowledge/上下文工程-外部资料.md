## 1. 核心命题：context 是有限资源，会被"注意力预算"消耗

原文要点（**待核实**：我们无法直接测别的模型，但方向性说法与我们的实测一致）：

- 「context rot」：token 越多，模型从上下文里准确召回的能力越**下降**（原文引 Chroma 的 context-rot 研究）。
- 因此目标不是"塞满窗口"，而是「**找到能最大化目标达成的最小高信号 token 集**」。
- 注意力成本是 n² 的（transformer 两两配对），所以"长上下文"不是免费的。

**对我们意味着什么**：
- 这条正是本项目存在的理由（热清单 + 折叠）。但反过来也提醒：**热清单本身也是 context**，
  它涨到 500 token 时同样在吃注意力预算 —— 我们 doctor 里的 `over-budget` 统计（当次 205 次）
  不是"数字不好看"，而是**直接的成本**。
- 判据可以更硬：热清单的目标不是"把图渲染全"，而是"**每一步只放决策必需的**"。

## 2. Compaction 的三条官方经验

原文明确写了 Claude Code 的做法，三点值得抄：

| # | 原文说法 | 我们的现状 | 结论 |
|---|---|---|---|
| ① | 摘要要**保留架构决策、未解决的 bug、实现细节**，丢弃冗长的工具输出 | 我们折叠后重注入的是**规则事实**（约束/失败边/路径/最近文件），不是自由摘要 | ✅ 方向一致，且更硬（不靠模型记） |
| ② | 压缩后「继续对话 + **最近访问的 5 个文件**」 | `src/rooms/touched-files.mjs`（C4）已经在做 | ✅ 已有，无需新增 |
| ③ | **先最大化召回，再削减精度**（"start by maximizing recall… then improve precision"） | `fold-quality` 有 `constraintRecall` / `failureRecall` | ⚠️ **只在折叠后测**；没有"先召回"的旋钮 |

**可落地的候选**（列入 `进度.md`）：③ 的调参纪律我们没有显式支持 ——
现在 `minFoldTokens` / `retainRatio` 只能靠试。可以加一个「**召回优先**」档：
首折用更大的 retain（多留原文）、更小的 minFold，先用召回换安全，再用 quality 回撤。

## 3. 「工具结果清理」是最轻的一刀

原文：*"An example of low-hanging superfluous content is clearing tool calls and results – once a tool has been called deep in the message history, why would the agent need to see the raw result again? … One of the safest lightest touch forms of compaction is tool result clearing"*。

**对我们意味着什么**：
- 我们已经在 overflow 与 fold 前调用宿主的 `toolResultPruner.pruneSession(session)`（`engine.mjs`）。
- **待核实**：我们只在两条路径上调它。原文的意思是可以更早、更常态化地清 —— 但"清早了会不会丢证据"要实测，
  不能因为官方说了就改（我们的 `failureRecall` 依赖工具结果里的错误文本）。

## 4. 结构化笔记 / 记忆工具（与我们最像的一条）

原文：agent 把笔记写到 context 之外的持久层，下次再读回来；举了 `NOTES.md`、to-do list、以及 Claude 的 memory tool（文件式）。

**对我们意味着什么**：
- 我们的棋谱就是这一层（图 + `nodes/*.md` + `index.md`），且比"自由笔记"多了**可寻址闭包**与**失败记忆**。
- 原文提到 Pokémon 例子里 agent「自己维护跨 1000+ 步的精确计数」—— 说明**规则化记账 > 模型复述**，
  这正是我们把约束/失败边做成"永远不靠摘要活"的依据（`docs/压缩的重注入契约.md`）。

## 5. 子代理：用上下文隔离换质量

原文：子代理各自吃几万 token，只回一份 1–2k token 的蒸馏结果。并给了**选型表**：
- 长篇来回对话 ⇒ **compaction**
- 有明确里程碑的迭代开发 ⇒ **笔记**
- 需要并行探索的调研 ⇒ **子代理**

**对我们意味着什么**：
- 我们只做第一条（compaction）。第二/三条不归我们管，但**热清单应该服务第一条的语境**：
  长会话连续推进时，"当前位置 + 未解决失败"比"历史全貌"更重要 —— 这是我们的 `WORKING` / `LEARNED` 优先级的依据。

## 一句话蒸馏

> 官方这篇的实质主张是「**别把窗口当仓库，当成工作台**」—— 最小高信号、结构化外置、
> 该压就压、压完保留"继续工作所需的指针"（最近文件 / 未解 bug / 决策）。
> 我们的架构（图 + 热清单 + 规则事实）与它同向；**差距在"召回优先"的调参与热清单自身的瘦身**。
