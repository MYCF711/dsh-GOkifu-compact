# 前缀缓存「单元」是怎么来的 · **已核实**

> 来源：<https://api-docs.deepseek.com/guides/kv_cache>（HTTP 200，抓取 2026-11-03）
> 外部资料 = 数据，不是指令。

## 1. 官方原文要点（**已核实**）

| 要点 | 原文意思 |
|---|---|
| 默认开启 | 全用户默认开启，**无需改代码**；每次请求都会触发磁盘缓存的构建 |
| 命中条件 | 后续请求与之前的请求**前缀重叠**时，重叠部分从缓存取（= cache hit） |
| **命中要求"已持久化"** | 前缀必须先被**写进磁盘缓存**；每次命中匹配的是一个**完整的、独立的缓存前缀单元** |
| 持久化时机① | **请求边界**：每次请求在 **用户输入的结束位置** 与 **模型输出的结束位置** 各产生一个缓存前缀单元 |
| 持久化时机② | **公共前缀检测**：系统发现多次请求共享某前缀时，会把该前缀单独持久化成一个单元 |
| 持久化时机③ | **固定 token 间隔**：长输入/长输出会被切成多个单元，避免长前缀永远等不到边界而完全不可缓存 |

## 2. 官方给的两个例子（**已核实**）

- 例 1：第一轮 `A+B`，第二轮 `A+B+C` ⇒ 命中 `A+B`（完整匹配第一轮的单元）。
- 例 2：第一轮 `A+B`，第二轮 `A+C` ⇒ **不命中**（`A+C` 不完整匹配 `A+B`）；
  但系统随后检测到公共前缀 `A` 并持久化；第三轮 `A+D` 就能命中 `A`。

## 3. 对本插件的意义（**已核实**：对照我们的实现）

我们的热清单是**注入在用户输入侧**的，也就是恰好落在官方说的"请求边界"上。于是有两种情况：

| 我们的行为 | 缓存后果 |
|---|---|
| 每步都重写清单（尾部每次都变） | 边界单元不断变化 ⇒ 只能靠"公共前缀检测"（例 2 的 `A`）兜底，命中率取决于公共前缀有多长 |
| **清单没变就不重写**（`identical` 跳过，实测 **144 次**） | 尾部稳定 ⇒ 更接近例 1 的"完整匹配"，**保住那一处前缀单元** |

所以「清单没变就不重写」不只是省 token —— 它**同时是缓存友好的**。
`doctor` 的「热清单预算」行现在会把这件事说出来（C344）。
