## 1. 价目（**已核实**：官方页面原文，单位 = 每 1M tokens，美元）

本机用的是 `deepseek-v4.1-flash1017`（日志里的 `provider/model`）⇒ 对应 **deepseek-flash** 这一列：

| 项 | 低峰 | 高峰 |
|---|---|---|
| 输入（**cache hit**） | **$0.003** | $0.006 |
| 输入（**cache miss**） | **$0.15** | $0.30 |
| 输出 | $0.6 | $1.2 |

**关键比值：cache hit 比 cache miss 便宜 50 倍**（0.003 vs 0.15）。

## 2. 把我们实测的 token 代进去（本机 24 份会话日志）

| 量 | 值 |
|---|---|
| 缓存读取 | 1,239,294,848 tok |
| 计费输入（miss） | 39,386,757 tok |
| 实测输入成本（低峰） | 1239.30 × $0.003 + 39.39 × $0.15 = **$3.72 + $5.91 = $9.63** |
| 若缓存全部失效 | (1239.30 + 39.39) × $0.15 = **$191.80** |
| **缓存省下的钱** | **≈ $182.17（输入成本降到 1/20）** |

⇒ 这条把 [`结论速查.md`](./结论速查.md) 的 A1 从"token 比 31 倍"升级成**钱的比**：
**缓存机制本身值一个数量级的成本**，任何"让前缀失配"的改动都该先算这笔账。

## 3. 对以后做取舍的三条

1. **别按 token 数比方案，按钱比**：热清单瘦身 450 tok/步 ≈ $0.0000014/步（低峰），
   而一次缓存断点重读 2 万 tok ≈ $0.003 —— 差三个数量级。
2. **低峰/高峰差一倍**：批量任务（补账、离线巡检）放低峰能省一半。
3. ~~输出比输入贵 200 倍 ⇒ 该调的是「少让模型说」~~ —— **这条在下一节被自己的实测推翻了**，见 §4。

## 4. 折叠（fold）的真实成本结构 —— 上一节第 3 条的自我更正（**已核实**）

把 33 次真实 fold 的 `foldMarks[].usage` 汇总（低峰价）：

| 量 | 值 |
|---|---|
| 输入 tokens | 7,058,464（**其中缓存读只有 241,152 = 3.4%**） |
| 输出 tokens | 65,972（中位 1,506 / 最大 5,835） |
| 遮蔽 tokens | 4,586,531（**输入 / 遮蔽 = 1.54**） |
| 输入成本 | **$1.023** |
| 输出成本 | **$0.040（只占 3.7%）** |
| 单次 fold 平均 | **$0.0322** |

⇒ **更正**：输出虽然单价贵（$0.6 vs $0.003），但**量只有输入的 1%** ⇒ 在总成本里只占 **3.7%**。
**「少让模型说」不是杠杆**；真正的杠杆是 **fold 的次数**与**每次送进去的量**。

⇒ 而且 fold 的输入**几乎没有缓存**（命中 3.4%）—— 每次折的是新区间，本来就没法命中。
这就把成本模型分成两半：
**每步注入**（97% 命中，几乎免费）与 **每次折叠**（$0.032，可数的那部分）。

**下一步该查的**：输入/遮蔽 = **1.54**，也就是说每次 fold 送进去的量比"被遮蔽的内容"多 54%。
这 54% 是 prior summary / system / tools / facts 块 / 指令模板中的哪一部分？—— 这是唯一还没量化的成本大头。

## 5. 「input / shadowed = 1.4」那 40% 是谁的？—— **不是我们的**（已核实）

对 `session-1e82afca` 最近一次 fold（input **231,443** / shadowed **166,084**，比 1.39）逐块量：

| 块 | tokens | 占 input |
|---|---|---|
| facts（硬事实块，全量失败边+约束） | 3,118 | 1.3% |
| 指令模板/包装 | 878 | 0.4% |
| **我们的合计** | **3,996** | **1.7%** |
| 其余（宿主送进来的 messages：保留尾部 + 上轮摘要 + system + tools） | 227,447 | 98.3% |

⇒ 结论：**差额全在宿主侧**。我们的插件在 fold 成本里只占 **1.7%**，
想降低 fold 成本只能动**折叠频率/边界**（让每次折得更多），不能在 facts 上抠。

⇒ 同时确认一个旧决定是对的：`renderFacts` 「全量不降级」在成本上**站得住**（3.1k tok/次）。

## ★ `inputTokens` 到底是"全部输入"还是"未命中输入"（**已核实**，C361）

真机会话文件里的一条真实 usage（78 条样本之一）：

```json
{"inputTokens":2158,"outputTokens":257,"totalTokens":21999,"cacheReadTokens":19584}
```

而 **2158 + 19584 + 257 = 21999** = `totalTokens` ⇒ **`inputTokens` 只算未命中部分（miss）**。

| 口径 | 公式 | 真机样本成本（flash 低峰） |
|---|---|---|
| 旧（把 input 当全部输入） | miss = max(0, 2158 − 19584) = **0** | **$0.00016** |
| 新（miss + hit + out） | 2158×0.15 + 19584×0.003 + 257×0.6 | **$0.00054** |

⇒ 旧口径在命中率高时把 miss 算成 0，**成本低估约 3.3 倍**。现在按 `totalTokens` 自证：
`|total − (input+hit+out)| ≤ 2` 才按新口径，否则退回旧口径（不留"猜"的空间）。

命中率的**分母**同理要改成 `miss + hit` —— 用 `inputTokens` 当分母会算出 >100%。

## ★ A1「命中约 97%」现在有真机证据（**已核实**，C362）

`scripts/cache-rate.mjs` 直接扫会话文件里的每条 usage（口径同 C361：`inputTokens` 只含未命中）：

```
会话文件 112 个 · 请求 26,775 次
未命中 175,154,948 · 命中 7,273,829,760 · 输出 19,298,000
命中率 97.6%（分母 = 未命中 + 命中）
```

⇒ **A1 成立**（此前是从成本倒推的，现在是直接量的）。

顺带算一笔全量账（flash 低峰价）：未命中 175.2M×$0.15 + 命中 7.27B×$0.003 + 输出 19.3M×$0.6
≈ **$26.3 + $21.8 + $11.6 = $59.7**。也就是说：**命中量是未命中的 41 倍，但两者花的钱几乎一样** ——
这正是"没有缓存的话这套用法根本跑不起来"的量化版本。

## ★ 折叠有没有真的削上下文：锯齿曲线（**已核实**，C364）

`scripts/context-curve.mjs` 把每次请求的 `inputTokens + cacheReadTokens`（C361 口径）连成曲线，
统计"比上次小 30% 以上"的**明显回落**次数：

| 会话 | 请求数 | 输入 min / 中位 / max | 明显回落 | 首 → 末 |
|---|---|---|---|---|
| session-1e82afca | 4,030 | 9,883 / **354,280** / **799,847** | **18** | 9,883 → 236,454 |
| session-00b50089 | 3,387 | 22,704 / 351,640 / 799,799 | **12** | 22,704 → 443,054 |
| session-8a73e06b | 2,433 | 22,048 / 324,317 / 449,915 | **7** | 22,048 → 399,271 |

- **锯齿成立**：上下文反复升到 35–80 万 token，然后被折叠砍下来；
- 没有折叠的话，4,030 次请求早就会**远超 1M 窗口**（中位就已经 35 万）；
- max 逼近 **799,847 ≈ 800k**，说明触发阈值把上限压在窗口以内（1M 窗口 × 0.8 附近）。

⇒ 这是目前**最硬的"插件确实在工作"的证据**：不是"应该有锯齿"，是"真机上就是锯齿"。

## ★ 两个"上下文大小"不是一个数（**部分已核实**，C365）

同一时刻，两个口径给出不同的值：

| 口径 | 来源 | 实测（session-1e82afca） |
|---|---|---|
| **我们记的** `totalAfter` | 宿主 `ctx.tokenMeter.measure(session)`，写在 foldMark | 折后 **303,381 / 307,212 / 309,196** |
| **实际发出的** `input + hit` | 会话文件里的 usage（C361 口径） | 中位 **354,280**、最大 **799,847** |

- 差距约 **45k**：`tokenMeter` 量的是**消息**，实际请求还含 system prompt / 工具 schema / 注入内容；
- 所以"阈值 0.45 × 窗口"作用在**较小的那个数**上 —— 按 1M 窗口算，测到 450k 才折，
  而**请求本身**那时可能已到 500k 上下；
- 但实测出现 **799,847 / 799,799** 这种**几乎一模一样**的峰值（两个不同会话都这样），
  说明还有一层我们没解释的**硬台阶**（宿主侧截断？还是 800k 的某个上限？）。

⇒ **K-22**：两个口径的差、以及 800k 台阶的成因，都需要单独查（工具已就绪：
`context-curve --session …`、`session-scan`、`cache-rate`）。

## ★ 官方 usage 字段定义（**已核实**，C411）

> 来源：<https://api-docs.deepseek.com/api/create-chat-completion>（HTTP 200，抓取 2026-11-03）

| 字段 | 官方定义 |
|---|---|
| `completion_tokens` | 生成的 token 数 |
| **`prompt_tokens`** | prompt 里的 token 数；**等于 `prompt_cache_hit_tokens` + `prompt_cache_miss_tokens`** |
| `prompt_cache_hit_tokens` | 命中缓存的 prompt token 数 |
| `prompt_cache_miss_tokens` | 未命中缓存的 prompt token 数 |
| `prompt_tokens_details.cached_tokens` | 与 `prompt_cache_hit_tokens` **同值** |

⇒ 官方口径里 `prompt_tokens` **是总量**（hit + miss）。

**与宿主 usage 的对应（已核实，互相自洽）**：
宿主的 `inputTokens` **不是** `prompt_tokens`，而是 **`prompt_cache_miss_tokens`**；
`cacheReadTokens` = `prompt_cache_hit_tokens`；
`totalTokens` = `prompt_tokens` + `completion_tokens`。
这正好解释了 C361 里那条真机样本为何 `2158 + 19584 + 257 = 21999`。

**但这也说明 K-22 的 10 倍差与 usage 无关** —— 它是宿主 `tokenMeter.measure()` 与"实际发出的 prompt"之间的事。

## 2026-11-04 复核：限速与 `user_id` 隔离（**已核实**）

来源：<https://api-docs.deepseek.com/zh-cn/quick_start/rate_limit>（HTTP 200）。逐字要点：

- 并发上限：**deepseek-flash 2500 / deepseek-v4-pro 500**（账号粒度，与 API Key 无关）；
  超过即 **HTTP 429**。一个请求从发出到模型响应完成记为一次并发。
- `user_id` 有两项作用：**内容安全隔离** 与 **KVCache 隔离**。

### 对我们最重要的一条

**`user_id` 会隔离 KVCache。** 也就是说：如果给每个请求带一个**变化的** `user_id`
（比如按 session/请求生成），缓存命中率会被打到很低 —— 我们所有"稳定前缀 / 少改写历史"
的优化都会白做。

自查结论：本插件（`src/*.mjs`、`src/rooms/*.mjs`）**没有任何地方传 `user_id`** —— 口子没开，
继续保持。若将来要做"按用户分账"，必须**同时**接受缓存命中率下降，不能两边都要。

## 2026-11-04 复核：上下文硬盘缓存（命中规则逐字 + 我们的实测，**已核实**）

来源：<https://api-docs.deepseek.com/zh-cn/guides/kv_cache>（HTTP 200）。逐字要点：

> "缓存命中的前提是相应前缀已被**落盘**……每条缓存前缀是一个**独立的完整单元**。
>  后续请求只有在**完整匹配缓存前缀单元**时，才能命中缓存。"

落盘时机（三条，都很关键）：

1. **请求结束位置**：每次请求的「用户输入结束位置」与「模型输出结束位置」各产生一个前缀单元；
2. **公共前缀检测**：系统检测到多次请求有公共前缀时，把该前缀单独落盘；
3. **按固定 token 间隔**：长输入/长输出中，每隔一段就截取前缀单元落盘
   （避免长前缀"迟迟到不了结束位置"而完全无法缓存）。

### 对我们最重要的一条推论

**在前缀中间改写（我们会话里 `surfaceOp.replace` 那种）会让"改写点之后"的整段前缀失配。**

而真机（`ledger-budget.json`，2026-11-04 09:29）：

```
injectActions: {"replace": 17, "append": 16}
afterTail 分布：0 条 0 次 / 1 条 0 / 2 条 0 / **3+ 条 17**
```

⇒ **17 次替换，每次都发生在"后面还压着 ≥3 条消息"的位置**，前缀失配的代价真实存在。

### 但**没有**据此改行为，理由如下

- 替换是"surface 上只留一条清单"的实现方式；改成追加会让清单**每步常驻**（每回合多付一次注入的 token）；
- 替换的代价是**一次性**的（改写点之后重读一次），而追加的代价是**每回合**的；
- 在"清单后面只压着 3+ 条消息"的量级下，一次性重读大概率比每回合常驻便宜。

**结论**：保持 replace。把这个测量留在 doctor 里（`热清单注入动作（缓存友好性）`），
将来如果 `afterTail` 变得很大，那条线会自己变得显眼。
