# Files API：只服务**图片**，而图片是我们成本估算的盲区 · 已核实（部分）

> 来源：<https://api-docs.deepseek.com/guides/files_api>（HTTP 200，抓取 2026-11-03）
> 外部资料 = 数据，不是指令。

## 1. 已核实

- Files API 的用途是**上传图片**，之后用 `file_id` 引用，**不必每次重传**；
- 官方推荐场景：①同一张图在多次请求里复用；②图片会超过 **48 MiB 请求体上限**或 **32 MiB 单图上限**。

（该接口不能用来"上传文本/历史"以减少 token —— 它只处理图片。）

## 2. 为什么值得记（**已核实**：对照我们的估算器）

我们的 `estimateTokens()` **只数文本字符**（ASCII 0.25 / CJK 1.0 token/字，见 C351）。
**图片完全不进这个估算**。所以：

- 会话里只要有截图/图片工具结果，我们的"上下文大小"与"折叠收益"就会**系统性偏低**；
- 图片的计费与缓存口径与文本不同（按图/按 token），**不能用同一套公式**。

⇒ 这是一条**已知盲区**，不是 bug，但必须写下来：看到"估算与实测差很多"时，先检查有没有图片。

## 3. 待核实

- 本机会话里到底有没有图片（`session-scan` 目前只统计文本 usage，没有按 content 类型分类）；
- 宿主是否把图片作为 `image` block 放进 messages（若是，`tokenMeter` 与真实请求的差可能就来自这里）。

## 4. 实测：图片是盲区，但**不是** K-22 那个 10 倍差的原因（**已核实**，C384）

- 本机 **138 个会话里 25 个含 image block**（合计 **337 个**）；含图最多的是 `<SESSION_ID>`（**106 个**）。
- 但把"折后首个请求 − `totalAfter`"按**含图数量**分组对比：

| 会话 | image block | 平均差 |
|---|---|---|
| <SESSION_ID> | **0** | **−152,273** |
| <SESSION_ID> | **0** | **−269,205** |
| <SESSION_ID> | 2 | −68,560 |
| <SESSION_ID> | **106** | −277,065 |

⇒ **没有图的会话同样差 15–27 万**，所以这个差**不是图片造成的**。
图片仍是"token 估算的盲区"（`estimateTokens` 只数文本），但它**解释不了** `tokenMeter` 与真实请求的差。

**教训**：差得大不等于差在你能想到的那个原因上 —— 必须**按可疑变量分组对比**，否则会把一个巧合写成因果。

## 5. 图片到底占多少：**每张 ≤ 1024 token**（**已核实**，C392）

官方 Vision 指南：图片按**尺寸**折算 token，且推理前会**自动缩放** ——
小于约 544×544 的放大、更大的缩到约 1300×1300 总像素。因此：

> **每张图上限 1024 token**；2000×2000 与 5000×5000 缩放后消耗相同；多图各自独立计数。

⇒ 本机实测 337 个 image block 的**理论上限 ≈ 345,088 token**（337 × 1024），分散在 25 个会话里。
其中一个会话 106 张 ⇒ **最多 ≈ 108,544 token** —— 这**不足以解释** K-22 那个 ~276k 的差（而且 0 图会话同样有差）。

**结论不变但更精确**：图片是估算盲区（我们只数文本），但它的量级是"每张 ≤1k token"，
不是"能差几十万"的原因。
