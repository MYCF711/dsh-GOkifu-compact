| `isPermanentSummaryError(msg)` | `400/401/402`、`Invalid Format`、`Authentication Fails`、`Insufficient Balance`、`invalid api key` ⇒ true；`429/500/503` ⇒ false（那是"等一会儿可能就好"） |
| 失败分支 | 判为永久 ⇒ ①`foldFailures` 顶到 7（退避直接到上限 480 事件，不再每 30 个事件白试）②`forceRulesNext = true` |
| `summarize` | 消费 `forceRulesNext` ⇒ 这一次**不再花模型调用**，直接规则摘要（消费后立刻清标记） |

**为什么不是"不压缩"**：铁律是「压缩永不失败」。永久性错误的正确处置是**立刻走规则摘要**，
而不是继续重试或干脆不压 —— 现在两件事都做到了：不白试，也不丢压缩。

**测试（C242）**：5 条该判永久的 + 6 条不该判的（429/503/500/socket hang up/空/null）+ 反证（`1401 tokens` 不许命中 `401`）
+ **接线守卫**（静态断言：判别式必须真的被失败分支用上、`summarize` 必须消费 `forceRulesNext`）。
顺带修了一处：分类块原先插在 `restore()` 与 `#flush(tree)` 之间，把 C112 的「回滚后 6 行内必须 tree 落盘」窗口挤爆了 —— 挪到 flush 之后。

## 第 43 轮 · 2026-11-02 23:5x（goal 第 41 轮）· 12 个会话塞进一个 HTTP 请求，是会坏的

**问题**：面板点「开始补账」时，客户端发的是 `{}` ⇒ 服务端用默认 `limit=20` 处理**全部**欠账。
而一个会话的收尾折叠要十几秒（foldMark 实测 `ms≈14000`）⇒ **12 个会话 ≈ 3 分钟挂在一个请求上**。
浏览器/宿主任何一侧超时都会让用户看到"失败"，可服务端其实还在跑 —— 用户再点一次就**重复补**。

**做了（C259）**：真跑时按批（`limit: 5`），并把"还剩多少"明确写进面板：

```
补完 5 / 5（真折叠 4；失败 0）
还有 7 个没补 —— 再点一次「开始补账」继续
```

- 每次请求 ≤ 5 个会话（≈ 75 秒，比一次 3 分钟安全得多）；
- 剩余数量 = `due - total`（服务端两个字段本来就有，只是没算过）；
- 补完了就不出现这一行（零成本）。

**测试（C259）**：一批 5/12 ⇒ 两行且写明「还有 7 个」「再点一次」；全补完 ⇒ 只有一行、不许再让用户点。

## 第 44 轮 · 2026-11-02 24:0x（goal 第 42 轮）· 两个标签页同时补账，会互相踩

**问题（顺着上一轮的分批发现的）**：面板按钮只能防**本页双击**（`backfillBusy`），
但防不了**两个标签页**，也防不了 curl。两个请求同时真跑 ⇒ 同一批归档会话被**各 resume 一次**
⇒ 两次收尾折叠 + 归档状态来回切（`unarchive → resume → archive` 交叠）。

**做了（C260）**：模块级在途闸门 `BACKFILL_GATE`。
- 同一时刻只允许一次**真补账**；第二次直接返回 `{ ok:false, code:"backfill-busy" }`（200，不是 500）；
- **dryRun 不进闸门**（它不 resume、不调模型，随便打）；
- 释放写在 `finally` 里 —— 一次异常不许把闸门**永久焊死**（那会让补账从此不可用）。

**测试（C260）**：闸门可读可重置 + 源码接线守卫（真跑前检查 / `backfill-busy` 这个 code 必须存在 /
释放必须在 `finally` / dryRun 判断必须排在闸门之前）。

## 第 45 轮 · 2026-11-02 24:1x（goal 第 43 轮）· 上一轮我算错了：不是 75 秒，最坏 15 分钟

```
5 个 × 180 秒 = 最坏 15 分钟挂在一个 HTTP 请求上
```

⇒ 我上一轮的数字**错了**，而且分批这件事因此并不足以把请求限住。

**做了（C261）**：
- 服务端接受 `perItemMs`（夹紧 **10s–180s**，外部脚本仍可用默认）；
- 客户端真跑改 `limit: 3, perItemMs: 90_000`（与引擎自己的 `closeoutTimeoutMs` 一致）⇒ **最坏 4.5 分钟、典型 45 秒**；

## 第 46 轮 · 2026-11-02 24:2x（goal 第 44 轮）· 两层超时同时到点 = 原因丢失

**发现**（接着上一轮的 perItemMs 往下看）：引擎自己有 `closeoutTimeoutMs`（默认 **90s**），

## 第 52 轮 · 2026-11-02 25:2x（goal 第 50 轮）· 缓存不是"前缀哈希"，是**一组落盘的段落单元**

**学了**：DeepSeek《Context Caching》→ [`上下文缓存-单元语义-deepseek.md`](./上下文缓存-单元语义-deepseek.md)

四条原文事实（已核实）：
① 缓存默认开、落磁盘；② 命中要求**完整匹配某个已持久化的「缓存前缀单元」**；
③ 单元产生于**请求边界**（用户输入结束处 / 模型输出结束处）、**公共前缀检测**、**固定 token 间隔**；
④ 官方例子：`A+B → A+C` 不命中，但会把公共前缀 `A` 存成单元，于是 `A+D` 能命中 `A`。

**判读（解释了我们自己的数字）**：

- 反过来给出一条设计原则：**改动点越靠后，作废的单元越少**。
  「就地替换末尾清单」几乎免费，「在开头插一条」等于把后面全部作废。

**做了（C268）**：把这条原则连同出处写进 `hot-inject` **做替换决策的那一行上面**——
以后谁想改成"在开头插一条"，会先看到这段注释和那份文档链接。

**没做的事（待核实，已写进文档）**：固定 token 间隔到底切多密、公共前缀检测几次生效、缓存有没有 TTL ——
官方页面都没给，等真机数据再说。

## 第 66 轮 · 2026-11-02 27:3x（goal 第 64 轮）· 缓存满了就全清，是最贵的一种"省事"

**发现**（读面板缓存代码）：

```js
const GRAPH_CACHE_MAX = 2000;

```

两个问题：
1. **上限 2000 形同虚设** —— 一个 2000 会话的 home，把 2000 张图（每张几百 KB JSON → 解析后更大）全驻内存；

- 上限 **2000 → 256**（够用，且内存有界）；

- 删掉 `clear()`。

**测试（C282）**：插入 5 条上限 3 ⇒ 只留最近 3 条；命中后续命，后来的插入淘汰的是**没被访问过**的那条；

## 第 73 轮 · 2026-11-02 28:4x（goal 第 71 轮）· K-15 第二步：**真的分段折**

## 第 126 轮 · 2026-11-03 00:2x（goal 第 124 轮）· 学了新主题：缓存「单元」是怎么来的

四条**已核实**（页面原文）：

## 第 142 轮 · 2026-11-03 03:0x（goal 第 140 轮）· 残留清单的成因找到了，也堵上了

上一轮把「一个会话残留十余份真清单」缩小成小问题。这轮定位成因：

`findLedgerNode()` 只找**最后一条**清单。当它返回 `null`（清单被 fold 压掉、或上一版是旧格式）时，
注入走**追加**分支 —— 而清理历史（`elideLegacyLedgers`）**只在会话开头跑一次**（`state.legacyElided`）。
⇒ 之后每次"被压掉 → 再追加"，都会在 surface 上多留一份**永远不会被清理**的旧清单。

**做了（C360）**：走到**追加**分支时先跑一次 `elideLegacyLedgers`（保留最后一条、其余换成占位）
⇒ 常驻清单收敛到 **1~2 份**，与 fold 次数无关。清理失败不影响本次注入（try/catch）。

**测试（C360）**：造「历史里有 2 条旧清单 + 当前清单被压掉」的局面，注入后断言**常驻真清单 ≤2 份**。

**教训**：一次性清理（one-shot）配上**可以反复发生的触发条件**，等于清理只在第一次有效。
凡是"只在开头做一次"的动作，都要问一句：**它防的那个情况会不会再来？**

## 第 149 轮 · 2026-11-03 04:1x（goal 第 147 轮）· 事件退避 ≠ 时间退避
