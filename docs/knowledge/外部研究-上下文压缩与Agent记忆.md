## 1. 「上下文腐坏」：token 越多，召回越差

**外部做法**：Anthropic 把上下文当成**有限注意力预算**（attention budget），并引用 Chroma 的
*context rot* 研究：窗口里 token 变多，模型准确召回的能力**单调下降**；这不是某一家模型的缺陷，
而是 transformer 的 n² 注意力关系 + 训练分布偏向短序列共同造成的。
[已核实] https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents

**它的前提**：任务需要模型在长历史里做**精确召回**（找约束、找死路）。

**我们的现状**：本仓库正是押在这一点上 —— 热清单 `hotLedger` 主动控制注入量，
`constraintRecall` / `failureRecall` 两个探针就是在量"折叠后还能不能召回"。
`src/rooms/fold-quality.mjs` 的 `describeStructure` 要求 `目标/棋谱/死路` 三段齐全。

**能不能落地**：已经落地。**但今天发现的两处"探测器恒假"正好是这条原则的反面**：
探针报"死路缺失"，实际是段名写成了 `## 已探明死路`（C638）；探针报"仪器未生效"，
实际是分母混进了 283 条离线补折（C608）。**召回探针本身不可信，等于没有召回。**

## 7. Context Rot：长上下文里性能是**非均匀**退化的（Chroma 技术报告）

**外部做法**：Chroma 用 18 个模型（GPT-4.1 / Claude 4 / Gemini 2.5 / Qwen3 等）做了控制变量实验：
**只改输入长度、任务难度不变**，看性能怎么变。
[已核实] https://www.trychroma.com/research/context-rot

**四条与我们直接相关的结论**：

| 外部结论 | 我们的对应 |
|---|---|
| 性能随输入长度**非均匀**退化（不是"塞得下就行"） | 热清单 + 折叠的**根本理由**；`maxChars` 60,000 不是保守，是必要 |
| **Focused 输入（~300 tok）显著优于 Full 输入（~113k tok）** | 折叠的本质收益 —— 我们押对了 |
| **靠前的信息更容易被正确取用**（position accuracy 最高在开头） | `## 目标` 放第一段是对的；但我们的**死路在最后**，这是风险 |
| **Distractor（似是而非的内容）影响非均匀且随长度放大** | 我们的"已验证事实"与"死路"混在同一段时，可能互为 distractor |

**一个反直觉的发现**（值得记）：**打乱结构的海堆比有逻辑连贯性的海堆更容易**。
报告的解释是：连贯上下文会让模型试图建立叙事，反而被误导；碎片化的信息它只做检索。

**对我们的含义**：这条**不能直接套用** —— 我们的摘要要的是"下一个 agent 能接着干活"，
不是"检索一句话"。但它提示一件事：**摘要里的叙事性内容（例如"我们试了 A 又试了 B"）可能是有害的**，
除非它承载了决策。

**能不能落地**：
- 「死路在最后」这条已经有实测支撑（`failureRecall` 0.43 那次就是死路被区间合并）；
- 「已验证事实 vs 死路 互为 distractor」**待验证** —— 可以设计一个 A/B：把死路提到目标之后，
  看 `failureRecall` 与"下一个 agent 是否重踩"有没有变化。**这是 T33 之后最值得做的实验。**

---

## 本轮结论（第 6 轮追加）

1. **【可做】死路段落位置 A/B**：Chroma 的 position accuracy 结论 + 我们的 `failureRecall` 缺口，
   共同指向"死路在最后可能吃亏"。设计一个只在**摘要渲染顺序**上变的对照实验（不改提示词内容）。
2. **【待核实】叙事性内容的代价**：如果摘要里"我们试了 A 又试了 B"这类叙述确实挤占预算且不承载决策，
   应该压成"结论 + 证据"两段。目前**没有数据**，先记为候选。
3. **【已确认】折叠的方向是对的**：Focused ~300 tok 优于 Full ~113k tok，是外部独立验证的最强一条。

## 8. DeepSeek Context Caching：命中要求**完全匹配一个前缀单元**

**外部做法**（官方文档，`[已核实]`）https://api-docs.deepseek.com/guides/kv_cache

> 缓存按**磁盘前缀**命中。每个缓存前缀是一个**独立完整的单元**，后续请求必须**完全匹配**某个单元才算命中。
> 单元在三种位置持久化：
> ① **请求边界**（用户输入结束处 / 模型输出结束处）
> ② 检测到多请求**公共前缀**时
> ③ 长输入的**固定 token 间隔**

官方例子直接对上今晚的账：

| 第 N 轮 | 第 N+1 轮 | 命中？ |
|---|---|---|
| `A + B` | `A + B + C` | ✅ 完全匹配 `A+B` |
| `A + B` | `A + C` | ❌ 不匹配；但系统会记住公共前缀 `A` |
| `A + B` / `A + C` | `A + D` | ✅ 命中 `A` |

**这解释了 T45 的 $94**：把热清单**就地改写**在早期槽位 ⇒ 新请求**不是**旧单元的完整前缀 ⇒ 整段作废。
**「到末尾追加」之所以对**：旧请求的「输入结束位置」恰好是新请求的一个完整前缀单元。

**也解释了 T46 的 A 类**：TTL 会清掉单元（文档：「不再使用时自动清除，通常几小时到几天」），
而真机在 300 秒处出现拐点 —— 说明这台机器上单元寿命更短（网关/负载因素），**改代码救不了**。

---

## 本轮结论（第 13 轮追加）

1. **【已修 T45】热清单改到末尾追加**：$97.02 → 预计 $3.08（省 $93.95）。
   机制由官方文档确认：**完全匹配前缀单元**是硬条件，不是「内容变了就该重算」。
2. **【已证伪 T46】`none` 组的 6.3 亿未命中里 $81 是 provider 物理账**，可落地天花板 $15.20。
3. **【新发现，已派 T48】离线折叠 913/916 条 `cacheReadTokens` 为空** ——
   引擎侧命中率 97.6%，离线侧几乎 0。若根因是「prompt 开头每次都变」，
   把**不变的部分前置**就能形成公共前缀单元。**先算天花板再动手。**

## 9. 摘要质量怎么评：我们今晚踩过的三个陷阱（附外部依据）

**外部背景**：RAG 原论文把「为模型决策**提供出处（provenance）**」列为**开放性研究问题**——
不是工程细节，是没解决的问题。[已核实] https://arxiv.org/abs/2005.11401

**这解释了为什么我们的「可定位率」一路改不动**：出处可查本身就没有公认好指标。

### 三个陷阱（今晚各踩一次，都有真机数字）

| 陷阱 | 我们踩的例子 | 判据 |
|---|---|---|
| **① 测的是形状，不是质量** | 「可定位率」= 折到尾部 **99.6%** vs 折历史中段 **43.9%** | 指标与「折痕折在哪」强相关 ⇒ 它测的是生产条件 |
| **② 没有方差 ⇒ 循环** | 「区间保真度 A」**85.6% 恒等于 1.0** | 它量的是 sanitize 的**输出**，却用来审计 sanitize 的**输入** |
| **③ 与已有指标 ρ>0.8 ⇒ 同一个东西** | 「区间保真度 B」与可定位率 **ρ=0.895** | 换个名字不产生新信息 |

**这三条能提前判死一个坏指标**，不用等它污染一整轮验收 —— 比指标本身更有价值。

### 一个推论（对任何「自动质量指标」都适用）

> 指标必须有**方差**，且方差必须来自**你改得动的东西**。

我们的可定位率方差来自「这一折折在哪」—— 那是**补账策略**决定的，不是代码质量。
所以无论今晚改多少行，它都不会动。**这不是指标不敏感，是指标在测别人的事。**

### 待验证

- T54 的「逐字可回查率」是第四个候选：按 n-gram 把摘要里的「动作→结果」反查回输入消息原文。
  它**不看 id、不看区间** ⇒ 理论上绕开①②③。**如果它也过不了，说明我们还没有能力衡量摘要质量**——
  那就该改成**任务式验收**（给下一个 agent 一条摘要，看它能不能做成一件具体的事），而不是继续发明事后指标。

## 10. 定稿：我们没有「摘要质量指标」，但有三类比它更可靠的东西

**结论（2026-11-05，五个候选全数判死）**：

| 候选 | 死法 | 决定性数字 |
|---|---|---|
| 可定位率 | **形状** | 折到尾部 99.6% vs 折历史中段 43.9% |
| 区间保真度 A | **循环** | 85.6% 恒等于 1.0（量 sanitize 的输出，审计它的输入） |
| 区间保真度 B | **冗余** | 与可定位率 ρ=0.895 |
| 逐字可回查率 | **方向** | 率≥0.99 组 T33=7.91 vs 率=0 组 7.86（差 0.05/10） |
| `constraintRecall` / `failureRecall` | **循环** | 众数 99.9% / 97.3%；分子就是补回函数的返回值 |

**最扎人的一条**：`constraintRecall` / `failureRecall` 是**补回函数给自己打分** ——
生产在模型输出后机械追加缺失项，再对同一份最终文本算 recall。
`offline-fold.mjs` 的注释自己写着「`failureRecall` 按设计恒 = 1」。**我们一直在看一个恒等式的重述。**

### 那还剩什么（三类，用途必须分清）

| 类 | 例子 | 语义 | 能回答什么 |
|---|---|---|---|
| **① 不变量**（必须 = 1） | `constraintRecall` / `failureRecall` / `sectionsMissing` / `endedCleanly` | 红了就是**破了** | 「补回与写回没坏」——**不是**「摘要好」 |
| **② 缺陷探针**（越低越好） | 幻觉 id / 越界 id / tool_call 泄漏 / 提示词回灌 / 重复行 | 抓得到**具体的坏** | 「这条烂在哪」——量不出「好」 |
| **③ 代理分**（有人读校准） | T33 五判据机械分（偏差 +0.5~0.68） | 近似 | 「大致什么水平」——不能反过来当金标准 |

### 该改成什么

**任务式验收**：给下一个 agent 一条摘要，看它能不能做成一件具体的事。

这不是退而求其次 —— **它是唯一能定义「有用」的方式**。
比率永远在问「像不像」，任务在问「能不能」。

### 一条可复用的判据（今晚总结）

> 一个自动指标要能用，必须同时满足四条：
> ① 有方差（不能 >80% 恒等）；② 与「你控制不了的东西」不相关；③ 与已有指标 ρ<0.8（否则是同一个）；
> ④ **分子不能是你自己的修复函数的输出**。
>
> 今晚五个候选，分别死在第 ②、①、③、方向、④ 条上。

## 11. 任务式验收：业界怎么量「有用」

**外部做法**：SWE-bench 系列把 Agent 的质量定义成**任务解决率（resolved rate）**——
给一份 issue，看它产出的 patch 能不能让**测试通过**。不是看 diff 像不像、不是看中间步骤合不合理。
[已核实] https://www.swebench.com/

**为什么这条对我们重要**：今晚五个「事后指标」全判死，它们共同的错是——
**都在问「产物像不像样」，而 SWE-bench 问的是「任务成没成」。**

| 维度 | 事后指标（全判死） | 任务式验收 |
|---|---|---|
| 问什么 | 摘要里的字对不对得上 | 照着摘要做，能不能做成 |
| 金标准 | 无（所以只能互相校准，结果循环） | **测试/结果**（客观） |
| 形状依赖 | 强（可定位率 ρ(形状) 显著） | 无（任务成不成与折痕折在哪无关） |

### 我们的任务式验收怎么落地（不调模型的最小形态）

摘要的目的只有一个：**让下一个自己别重蹈覆辙**。所以最小的任务式验收是：

> **重踩率**：折叠产出的摘要里列了死路，之后 N 轮里有没有出现**相同 action** 的新失败边？

这是「任务」的最小可观测形态：
- **有客观结果**（失败边是真实记录，不是评价）；
- **与形状无关**（后续行为，不是折痕位置）；
- **分子不是修复函数的输出**（真实失败，不是补回返回值）。

**已派 T56 验证**。如果它也过不了四条判据，那说明「不调模型就量不出有用」——
到那时只能接受「漂移观测 + 人工抽检」，而不是继续造指标。

### 一条可直接复用的判断

> **如果一个指标需要「金标准」来校准，而你没有金标准 —— 那它不是指标，是循环。**
>
> SWE-bench 之所以成立，是因为**测试通过与否不依赖任何人的判断**。
> 我们今晚五个候选，全部倒在这一条上。

## 12. 观测点：应该在**归档时刻**，不是折叠时刻（Lead 转述用户观点）

**用户的判断**：一个任务完成之后，是最好的观测状态。

**为什么这是对的（四条，逐条都能对上今晚的失败）**：

| 折叠时刻观测 | 归档时刻观测 |
|---|---|
| 未来未知 ⇒ 只能问「像不像」 | **全轨迹已知** ⇒ 能问「有没有用」 |
| 没有金标准 ⇒ 五个指标全倒在循环上 | **任务成没成**是客观金标准（= SWE-bench 的 resolved rate） |
| 形状偏差（折到尾部 99.6% vs 中段 43.9%） | 所有折痕**同样完成**，比较的是同一份完整轨迹 |
| 不可复现（语料在漂） | 冻结状态 + 确定结局 ⇒ **可回放** |

### 一个我之前漏掉的正向信号

T56 只算了「**重踩率**」——但归档时能算的是**四格**：

| | 之后重踩了 | 之后避开了 |
|---|---|---|
| **摘要列了** | 警告无效（可能没看） | ✅ **摘要有效的正向证据** |
| **摘要没列** | 漏写 | （无信息） |

**「列了且避开了」才是摘要有用的证据。** 我之前只统计了左上格（重踩），把右下角的正面证据整个漏掉了。

### 为什么这条能绕开今晚五个死法

| 死法 | 归档时刻为什么不死 |
|---|---|
| 形状 | 归档时所有折痕都「完成」，形状差异被**固定** |
| 循环 | 分子是**后续真实发生的事**，不是补回函数的输出 |
| 冗余 | 四格是**新信息**，没有任何现有指标算过 |
| 方向 | 「避开」天然是**归纳**的产物（列死路的目的是避坑，不是抄原文） |

### 落地口径

```
观测点：任务归档（closeout）时冻结
对象：该会话所有 foldMark 的摘要
金标准：归档时的完整轨迹（哪些 action 真的又试了、哪些真的没再碰）
度量：四格混淆矩阵 → 精确率（列了的有用）/ 召回率（有用的列了）
反事实：对照组 =「摘要那一段被抹掉」的同一轨迹（如果没有对照组，只能说相关）
```

## 13. 归档 = 「结束」，不是「成功/失败」——这条改掉了整个金标准

**用户的原话**：
> 归档就说明 user 觉得会话已经结束，注意是**结束**，不是成功和失败。
> 这意味着你不需要去衡量成功和失败，因为很多时候 user 只是试探性地问一个问题。

### 为什么这条是决定性的

今晚五个指标都要一个「金标准」，而**「任务成没成」从来没被记录过**：
`closeout` 的字段只有 `at / source / folded / partial / foldNote / offlineCovered …`，
**没有成功/失败**。所以所有指标只能拿别的指标互相校准 ⇒ **循环**（五个候选全死在这条上）。

**但「结束」不需要评判** —— 它是 user 的决定，是一个**确定的时刻**。
于是金标准变成：**在这段确定的历史里，摘要说的东西对不对。**

### 「试探性地问一个问题」为什么重要

它意味着**大部分会话根本不该有「成败」**。硬套 resolved rate 会把「问完就走」判成失败 ——
那是**给数据加噪声**，再拿噪声当金标准。

### 落地：把摘要当**可验证的预测**

| 断言 | 摘要里长什么样 | 归档时怎么验 | 性质 |
|---|---|---|---|
| **A 停点预测** | `## 当前节点` / 「停在 nX」 | 之后第一条 assistant 动作**从哪继续**？ | **正向**——命中就是「定位准」 |
| **B 死路预测** | `## 已探明死路` 列了 action X | 之后**有没有再出现** X 的失败边？ | **负向**——不重踩是弱信号，重踩是强反例 |

**A 是最强的正面证据，而之前根本没人测过它。**
T56 只测了 B，还只统计了「重踩」这一格，把正面证据整个漏掉。

### 一句话

> **成功需要评判，结束不需要。** 有金标准的地方才可能有指标 —— 而「结束」这个时刻，
> 金标准就是**历史本身**。

## 14. Lost in the Middle：**位置决定一切**，这给 T45 的修复补上了第二重理由

**外部结论**（`[已核实]`）https://arxiv.org/abs/2307.03172
Liu et al., TACL 2023：

> 模型在**开头或结尾**出现相关信息时表现最好；
> 必须在**长上下文中间**取用时**显著变差** —— **即便是明确的长上下文模型也一样**。

### 对我们产品的两条直接推论

**① T45 的修复不只是省缓存，还改善了注意力**

T45 把热清单从「就地改写早期槽位」改成「挂到末尾」，理由是**打断 prompt cache**（省 $93.95）。

但按 Lost-in-the-Middle，**末尾本来就是模型看得最好的位置之一**。所以那次修复是**双赢**：

| 维度 | 改前（早期槽位） | 改后（挂末尾） |
|---|---|---|
| 缓存 | 整段前缀作废（$97.02） | 只加尾部（$3.08） |
| **注意力** | **落在中间 ⇒ 看得差** | **落在末尾 ⇒ 看得好** |

**② 「摘要放哪」是一个一等设计参数，不是实现细节**

如果摘要被注入到长上下文的**中段**，模型读它的概率就低 —— 那「摘要写得好不好」根本轮不到发挥。
这可能解释了 T56 的 **0.37% 重踩率**（低得可疑）：不是摘要有效，是**没人读到**。

### 一条可测的推论（待验证）

> 摘要/清单的「距上下文末尾距离」应该与「被引用概率」**负相关**。
> 如果测出来无关，说明位置不是瓶颈（那 T56 的低重踩就是别的原因）；
> 如果强负相关，那**所有「摘要质量」指标都应该先控制位置**，否则量的还是位置。

### 与今晚其它结论的关系

| 今晚的发现 | Lost-in-the-Middle 的解释 |
|---|---|
| 可定位率是**形状**函数 | 形状的一部分就是**位置** |
| 重踩率 0.37% 低得可疑 | 可能不是摘要好，是**位置差** |
| T45 省 $93.95 | 顺带把信息挪到了**模型看得见的地方** |

**一句话**：压缩的收益不只是「token 少了」，
还有「**信息从中间挪到了两头**」—— 后者可能更值钱，且**从来没人量过**。

## 15. MemGPT：让 **agent 自己决定**换出什么，而不是系统替他决定

**外部做法**（`[已核实]`）https://arxiv.org/abs/2310.08560
Packer et al., MemGPT：

> **Virtual context management** —— 借操作系统的分层内存思想，在快/慢两层之间搬运数据，
> 让有限上下文看起来像无限。并用 **interrupts** 管理 agent 与用户之间的控制流。

### 我们的设计其实是同构的

| MemGPT | 我们 |
|---|---|
| core memory（常驻窗口） | **热清单**（hot ledger，每轮注入） |
| archival memory（按需读） | **节点文档**（`nodes/nX.md`，agent 可 grep/read） |
| 换出（page out） | **折叠**（fold：一段历史 → 摘要） |

### 但有一个关键差异：谁来决定换出

| | 触发者 | 后果 |
|---|---|---|
| **MemGPT** | **agent 自己**（function call 主动 page out） | agent 知道「什么对我还有用」 |
| **我们** | **系统阈值**（压力 / 归档 / 欠账） | 系统**不知道**什么重要，只能按 seq 切 |

**这可能是今晚许多问题的共同根源**：

- 退化区间（`seq 8-8`）—— 系统按「欠账」切，不看内容；
- 虚构缺口（60.1%）—— 系统数**事件数**，不数**内容**；
- 锚点全抹（`n?`）—— 系统按「区间边界」抹 id，不管那条 id 对后续有没有用。

**三条都是「系统在不知道内容重要性的情况下做决定」的副作用。**

### 一条可考虑的方向（不是本轮要做的事）

> 让 agent **主动声明**「这一段可以折了」/「这条必须留」，系统只负责执行。
>
> 代价：agent 每轮多一次判断（可能更贵）；收益：**折叠边界由「内容重要性」决定，而不是「seq 序号」**。

**这解释了为什么今晚五个质量指标全判死**：
我们试图**事后**衡量「折得好不好」，而 MemGPT 的思路是**事前**让「知道内容的人」来决定。

**事后指标 vs 事前判断** —— 后者根本不需要指标。

## 16. 纠正：归档补折是**会话记录**，不是 token 优化（Lead 转述用户观点）

**用户的判断**：它就是会话记录。后续这个项目继续上次的进度进行更新或更改时，这个记录就可能被读到。

**我（Lead）错在哪**：把「归档补折」当成「实时折叠」来算 ROI，
看到「摊销记 0」就推出「纯浪费」。**摊销记 0 只说明它不省当前会话的 token，不说明它没价值。**

### 价值 = 项目连续性，不是 token 账单

Memory-ledger 里早有一条用户约束（2026-11-03）：

> 「所以需要的不是会话自己去压，而是**归档的日志**需要去调用默认模型压缩一次，
> 这样就**不用依赖对话模型**。」

⇒ 归档补折的设计目的**本来就是**：让「下次接着干」**不依赖当时那个对话上下文**。

**类比**：日志一年只翻 3 次 ≠ 日志没用。**记录的价值在于「需要时它在」**。
而「下次继续这个项目」没有记录 = 从头读几十万 token 原文，或干脆重开项目。

### 关键：记录有**两条**传递路径，我只量了其中一条

| 路径 | 载体 | 有没有被量过 |
|---|---|---|
| ① 会话内注入 | `compaction/summary`、热清单 | T57 量过：送达 **7.13%** |
| ② **跨项目读取** | 新会话读 `docs/knowledge/进度.md`、`派单表.md`、HANDOFF、`nodes/nX.md`、棋谱 | **从没量过** |

**T57 的 7.13% 结构上就不可能测到路径 ②**：
新会话里根本**没有**旧会话的 `compaction/summary` 事件，那把尺子只能测会话内。
⇒ **拿只能测会话内的尺子，去否一个跨项目的价值，是尺子先错了。**

### 一条可以直接查的硬证据（跨会话引用）

新会话的工具参数里出现**旧会话 id / 旧节点 id** ⇒ 就是「下次继续时读到了上次的记录」。
（`docs/knowledge/进度.md`、`docs/派单表.md`、HANDOFF.md 本身就带大量会话 id 与节点 id，
新会话读这些文档时会把它们带进上下文 —— 这**就是**记录价值的传递。）

### 正确的账（反事实成本，不是引用率）

```
成本：补折 $5.4（已发生）+ 待补 689 段
收益：避免「下次接着干时从头读原始日志 / 重开项目」
对照组：不补折 ⇒ 下次只能读原文（几十万 token），或没有上下文直接重来
```

**结论**：**T68 若按「引用率低 ⇒ 纯浪费」出结论，那个口径不含路径 ②，不能作为停止补折的依据。**

## 17. 纠正：「真实使用 0 次」的原因是**消费方还没造出来**，不是「没用」

**用户的原话**：
> 老会话的 kifu 真实复用少是因为配套的 GOkifu 记忆系统还在制作没有正在实装。当然没有复用。

**我（Lead）在 T68 里犯的错**：
看到「504 个归档会话 / 1158 段摘要 / **真实使用 0 次**」就推出「不值得且贵 ⇒ 建议停止」。

**正确的解读**：
归档补折的产出（棋谱、摘要）是**给配套的 GOkifu 记忆系统用的**。
**记忆系统还在制作、没有实装 ⇒ 消费方根本不存在 ⇒ 复用率当然是 0。**

### 这是一条通用的判断错误

> **「没人用」不等于「没用」—— 可能是用它的东西还没造出来。**

我把「当前复用率」当成了「长期价值」的代理指标，
而**复用率的分母依赖于一个还不存在的系统**。
这跟今晚判死的五个指标是同一类错：**用一把量不到目标的尺子，去否定目标本身。**

### 对 T68 结论的修正

| 原结论 | 修正后 |
|---|---|
| 「真实使用 0 次 ⇒ 不值得 ⇒ 建议停止自动补折」 | **复用率低是因为消费方未实装**，不能据此否定价值 |
| 「停止可省 $3.39–$5.30」 | 省的是**未来的记忆资产**，停掉等于在建一半时拆地基 |

**但「按钮 + 模型选择」的设计仍然更好** —— 理由不是「没人用」，
而是**让用户自己决定什么时候补、用什么模型（可以用免费模型）**。
这是**控制权**问题，不是**价值**问题。

### 给以后的判据

评估「某个产物有没有用」之前，先问一句：**它的消费方上线了吗？**
没上线 ⇒ 复用率天然是 0，**这不构成否定证据**。

## 18. Mem0：图记忆带来的**准确率提升有限**，真正的大头是**成本与延迟**
来源：[arXiv:2504.19413 · Mem0: Building Production-Ready AI Agents with Scalable Long-Term Memory](https://arxiv.org/abs/2504.19413)（摘要已核实；LOCOMO 细项未核）

**做法**：动态**抽取 → 整合 → 检索**对话里的显著信息；增强版用**图记忆**表达对话元素之间的复杂关系。

**结果（摘要原文）**：
- 相对 OpenAI 的 LLM-as-a-Judge 提升 **26%**；
- **图记忆版**比基础版**总分只高约 2%**；
- 相对 full-context：**p95 延迟低 91%**、**token 成本省 >90%**。

### 对我们（棋谱 DAG）的直接印证
我们用的是**图**（节点=状态、边=尝试+验证），与 Mem0 的图记忆同族。
**但论文的量化结论提醒我**：
> **图结构带来的「准确率」提升是有限的（~2%），真正的收益在「成本与延迟」（>90%）。**

⇒ **别把「用了图/DAG」当成「质量必然更好」的论据。**
我们今晚实测的「摊销 ROI 中位 $16.55/段」「重读率 2.38%」正是**成本侧**的收益，
与 Mem0 的「省 >90% token 成本」**同向**。
**我们真正该守的是「成本可算清」和「失败记忆可回溯」这两条，不是「图很高级」。**

### 与「复用率 0 次」的关系
Mem0 是**给长期记忆检索用的**（与我们的配套记忆系统同域）。
它的收益前提是**有检索方在用** —— 这与用户说的「复用少是因为记忆系统还没实装」一致。

## 19. A-MEM（NeurIPS 2025）：**agentic 记忆组织** —— 正是用户警告的那条路
来源：[arXiv:2502.12110 · A-MEM: Agentic Memory for LLM Agents](https://arxiv.org/abs/2502.12110)（摘要已核实；NeurIPS 2025；细项未核）

**做法**：按 **Zettelkasten** 方法做**动态索引与链接**的记忆网络。
- 每条新记忆生成带**结构化属性**的笔记（上下文描述 / 关键词 / 标签）；
- **记忆演化**：新记忆会触发对**已有记忆**的上下文与属性更新；
- **由 agent 自己决定**如何组织（agent-driven decision making）。

### 与我们（棋谱 DAG + 规则抽取）的对照
A-MEM 的「动态索引与链接 + 图记忆」与我们的 DAG 同族（置换检测也呼应「回到已有节点」）。
**但它的「由 agent 自己组织记忆」正是用户警告的方向**：
> 「**把压缩主动权交给 agent 本身是很危险的事情。**」

⇒ 我们的选择是**确定性**的：
- **规则抽取**失败边（不让模型决定留什么）；
- **逐字注入**热清单（模型无权丢）；
- **折叠由预算/阈值触发**，不是「模型自己决定什么时候压」。

**A-MEM 验证了「图记忆 + 动态链接」的价值，但它的 agentic 组织方式我们不采用。**
我们保留「**确定性的结构**」与「**模型无权丢的失败记忆**」这两条硬保证。

## 20. Context Engineering 综述（166 页 / 1411 引用）：**理解强、生成弱**的不对称
来源：[arXiv:2507.13334 · A Survey of Context Engineering for Large Language Models](https://arxiv.org/abs/2507.13334)（摘要已核实；2025-07；166 页、1411 引用）

**定位**：把「上下文」当成一门**正式学科**（不是简单的 prompt 设计），
拆成**检索与生成 / 处理 / 管理**三大组件，再整合成 RAG、记忆系统、工具推理、多智能体。

**最关键的一条结论（摘要原文）**：
> **模型「理解复杂上下文」很强，但「生成同样复杂的长输出」明显更弱 —— 这是一个根本性的不对称。**

### 与我们今晚遇到的摘要截断（T42）的关系
我们的摘要就是「**生成**」：模型能**读**很多（上下文），但**写不出**好的长摘要。
- T42 实测：`outputTokens` 里含 reasoning ⇒ 摘要被截断；
- 综述证实这不是「我们的模型不行」，而是**生成侧的天然短板**。

⇒ 我们的修法与这个判断一致：
- **别把「让模型写更长的摘要」当解法**（生成侧有上限）；
- **把「结构化事实 + 有限润色」当主路径**（hybrid = 规则事实 + 模型润色，而不是全模型生成）；
- **截断必须可判**（T42 的三态判据），因为**生成侧截断是常态，不是异常**。

**这份综述也解释了为什么我们坚持「规则抽取失败边、逐字注入热清单」**：
**把最关键的信息交给「确定性结构」，而不是交给「模型生成」。**

## 18. REFLEX：信念图 + 形式化约束求解来消解矛盾（已核实 · 2026-11-07）

来源：https://arxiv.org/abs/2305.14250 （Kassner et al., 2023，Language Models with Rationality）

**做法**：在 LLM 之上加一层**理性自省层**：
先用**反向链**把相关「信念」及其推理关系**物化成一张图**，
再用**形式化约束求解器**找出并**最小化图里的矛盾**。
结果：**一致性提升 8–11 个百分点**（绝对值），且**不损失整体准确率**。

**与我们的棋谱 DAG 的关系**：
- 我们：节点 = 状态哈希、边 = 尝试 + 验证信号、**失败边/已修正失败**逐字注入；
- REFLEX：信念 = 图、**用约束求解器显式消解矛盾**。

**同一条思路**：让「信念」显式、并**消解矛盾**。
我们用「同 action 后续跑通 ⇒ 标为已修正」来消解；REFLEX 用形式化方法。

**可借鉴**：我们的图里目前只标「**已修正**」，没有标「**当前仍矛盾**」。
REFLEX 提示：可以把「哪些信念互相矛盾」也**显式标出来**。

**边界**：这偏向**推理/一致性层**，而我们的职责是**压缩**。
⇒ 记为「了解，不直接吸收」；若以后做「图的一致性检查」，可回头参考它的形式化方法。
