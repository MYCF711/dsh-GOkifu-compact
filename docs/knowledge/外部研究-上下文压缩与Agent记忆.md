## 1. 「上下文腐坏」：token 越多，召回越差

**外部做法**：Anthropic 把上下文当成**有限注意力预算**（attention budget），并引用 Chroma 的
*context rot* 研究：窗口里 token 变多，模型准确召回的能力**单调下降**；这不是某一家模型的缺陷，
而是 transformer 的 n² 注意力关系 + 训练分布偏向短序列共同造成的。
[已核实] https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents

**它的前提**：任务需要模型在长历史里做**精确召回**（找约束、找死路）。

**我们的现状**：本仓库正是押在这一点上 —— 热清单 `hotLedger` 主动控制注入量，
`constraintRecall` / `failureRecall` 两个探针就是在量"折叠后还能不能召回"。
`src/rooms/fold-quality.mjs` 的 `describeStructure` 要求 `目标/棋谱/死路` 三段齐全。

**能不能落地**：已经落地。**但今天发现的两处"探测器恒假"正好是这条原则的反面**：
探针报"死路缺失"，实际是段名写成了 `## 已探明死路`（C638）；探针报"仪器未生效"，
实际是分母混进了 283 条离线补折（C608）。**召回探针本身不可信，等于没有召回。**

## 2. 压缩要保什么：架构决策、未解 bug、实现细节

**外部做法**：Claude Code 的 compaction 明确保留三类 —— architectural decisions、unresolved bugs、
implementation details，丢弃冗余工具输出；**先最大化召回，再收紧精度**。
[已核实] 同上

**它的前提**：压缩产物要能被"下一个自己"直接接着干活，而不是给人读的摘要。

**我们的现状**：我们的三段式（`## 目标` / `## 棋谱` / `## 已探明死路` + `## 已验证事实`）
与这三类**一一对应**：目标≈决策、死路≈未解 bug、棋谱≈实现细节。
`docs/方案书.md:81` 也写明失败边必须**逐条出现、不合并、不省略**。

**能不能落地**：**这正是 C607 修的那条** —— `renderFacts` 把动作截断到 80 字符，
6 条死路的文件名被切掉，模型合理地合并成 `e693—e698`，`failureRecall` 掉到 0.333。
外部原则（逐条）与我方契约（`方案书:81`）一致，**是实现的截断违背了契约**。

## 3. 工具输出清理是"最安全的轻量压缩"

**外部做法**：Anthropic 把 tool result clearing 称为最安全、最轻的压缩形式 ——
工具结果一旦深埋在历史里，模型不需要再看原始输出。
[已核实] 同上

**我们的现状**：`collectMessages` 的 C481 已经**整条跳过 `tool/result`**；
`tool/call` 只留 120 字符摘要。真机核对（C612 审计）：

```
tool/result 69,489 条（92,781,778 字符）**一条都没进输入**
```

**能不能落地**：已落地，而且比外部建议更激进（我们是完全不进，不是"清旧"）。
**代价**：`maxChars` 的 60,000 预算就全花在消息正文上 —— 而正文里 **63% 是 reasoning**（见第 4 条）。

## 4. 我们自己的发现：预算被"草稿纸"吃掉 63%

**外部没有直接对应**（这是我方真机统计出来的）：折叠区间内的字符构成

| 块类型 | 占比 |
|---|---|
| `assistant:reasoning` | **63.0%** |
| `user:reminder`（`<system-reminder>` 样板） | 16.6% |
| `user:text`（真实用户输入） | 15.0% |
| `assistant:text`（真实正文） | 5.3% |

**结论**：**真实事件只占 20.3%**，其余是模型自己的思考和每轮重复的脚手架。
这条已经派单（C613）：先证伪"剔除 reasoning 会不会丢结论"，再决定剔除还是降权。

**为什么这条值得单独记**：外部文章讲的是"丢什么"，我们这里的问题是
**"根本没有把预算花在事件上"** —— 属于同一目标的更上游。

## 5. 结构化笔记 vs 自然语言摘要

**外部做法**：structured note-taking（agentic memory）让 agent 把进度写到上下文之外
（`NOTES.md` / memory tool），需要时再拉回来；比纯摘要更能维持长任务的连贯性。
[已核实] 同上

**我们的现状**：这正是本仓库的核心（棋谱 graph + `foldMark` 可审计 + 热清单重注入）。
**我们比外部多走了一步**：每条折叠都有 `foldMark` 记区间/字符/耗时/质量，
而 Claude Code 的 compaction 只产出一段摘要文本。

**能不能落地**：已经是我们最强的差异化。**但要防止"记了但没人读"** ——
今天 doctor 报的 `sectionsMissing`、`finishReason` 缺失，本质都是"记了字段但下游读不到"。

## 本轮结论（1–3 条可做）

1. **【已派 C613】剔除/降权 reasoning 块**：折叠预算里 63% 是草稿纸，真实事件只占 20.3%。
   先证伪再改，风险是"有些结论只在思考里"。
2. **【已做 C612】`perMessageChars` 保持 2000**：真机数据证伪"长的是工具输出"，
   放宽只 +0.9pp 覆盖率却少看 27% 事件。**不改是正确决策，已写进代码注释防重问。**
3. **【待做】外部原则 ↔ 探针口径对齐检查**：第 1、2 条都指向同一件事 ——
   **契约写在文档里，探针却按另一套口径判**。建议加一条门禁：文档里每条"必须…"都要能定位到
   一个断言它的测试，否则报 `!`。

## 明确不做的

- **不引入向量检索**：我们的会话是单一线性日志，没有"跨会话语义搜索"的需求；
  真要做也应该走 `worldHash`/`transposition` 那条已有线索，而不是新加一个索引系统。
- **不把 `maxChars` 提到 120k**：C612 算过，+12,243 token/段 ≈ +$0.36/日（低峰），
  但**先解决 63% 的 reasoning 浪费**再谈加预算，否则是给草稿纸加钱。
