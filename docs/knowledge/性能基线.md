# 性能基线（本机实测，随时补）

> 目的：**改性能之前先看这里**。没有数字的"优化"一律不做 —— 本仓库已经踩过"凭手感优化"的坑。
> 采集方式统一写在这里，别人复跑能对上。最近一次：2026-11-02 16:2x 本地。

## 1. 热路径：每一步都要跑的渲染

场景：`agent/pre-step` 每次注入热清单 ⇒ `renderLedger(graph, {level})`。

| 图规模 | `renderLedger` 单次 | 说明 |
|---|---|---|
| **2,467 节点 / 12 次 fold**（`session-00b50089…`，本仓库最大会话） | **22.4 ms** | 50 次取均值（`renderLedger x50 = 1118.6ms`） |
| 输出体积（同一次，level 5） | 1,577 字符 ≈ **451 tok** | 与 doctor 的「热清单分项占用」口径一致 |
| **41 个会话的分布**（2026-11-02 16:4x 实测） | p50 **0.68 ms** · p90 **2.14 ms** · p99 **22.0 ms** | 那时 p50 只有 77 节点、p90 491 节点 ⇒ **典型会话的渲染可以忽略** |
| **54 个会话的分布**（2026-11-02 22:0x **每会话 15 次取中位数**） | p50 **0.47 ms**（70 节点）· p90 **16.9 ms**（495 节点）· p99 **143.4 ms**（2,292 节点） | **分布已经变了**：大图变多，p99 从 22 ms 涨到 **143 ms** —— 大会话的渲染不再可忽略 |

复跑脚本（一次性，不落盘）：

```bash
node --input-type=module -e '
import { loadSessionGraph } from "./scripts/graph-audit.mjs";
import { renderLedger } from "./src/rooms/ledger.mjs";
const g = loadSessionGraph("D:/DeepSeek Harness/home/chess-context/sessions/<id>/graph.json").graph;
const t0 = performance.now(); for (let i=0;i<50;i++) renderLedger(g,{level:5}); 
console.log(((performance.now()-t0)/50).toFixed(2), "ms/次");
'
```

**判读（已核实）**：单次 22ms 是 **CPU**，不是 token 成本；典型会话（50–300 节点）约 0.5–3ms。
⇒ **当前不是瓶颈，不值得为它加缓存**（加缓存的失效判断风险 > 22ms 的收益）。
真正贵的是**注入的 token**（451 tok × 每一步），那是 `over-budget` 统计在管的事。

### 1.3 分项计时（C313）：95% 的时间在拼字符串，不在查图

`measureLedgerTimings(g)`（C313）把渲染前要做的大活各自重跑并计时。最大会话（2,467 节点）：

| 段 | 耗时 | 占比 |
|---|---|---|
| `danglingStats` | 0.36 ms | 2% |
| `failureEdges` | 0.25 ms | 1% |
| `options` 扫描 | 0.25 ms | 1% |
| `successScan` | 0.22 ms | 1% |
| `paths` / `tewari` | 0.00 ms | 0% |
| **合计可归因** | **1.08 ms** | **约 5%** |
| **`renderLedger` 总计** | **21.95 ms** | 100% |

⇒ **查图几乎不花钱，钱都花在拼字符串上。**
所以 K-16 的方向要改：不是缓存图查询，而是**少拼字符串 / 分段拼**（或干脆接受它）。

### 1.2 一个坑：`measureLedgerSections` 不是计时函数

第一次想按「分项耗时」定位热点，调用 `measureLedgerSections(g, { level: "full" })` —— 结果全 0。
看实现才知道：签名是 **`measureLedgerSections(text)`**，输入是**渲染出来的文本**，
返回的是**每个分段的字符数**（给预算占比用），**不是时间**。

⇒ 目前**没有任何「按分项计时」的仪器**。要做 K-16 的增量渲染，第一步得先造这个仪器，
否则「哪几段真会变」只能靠猜 —— 而本仓库的规矩是：**没有数字不做优化**。

### 1.1 复测结论（2026-11-02 21:5x）

| 项 | 16:4x | 21:5x | 变化 |
|---|---|---|---|
| 会话数 | 41 | **49** | +8 |
| p50 | 0.68 ms（77 节点） | **0.45 ms**（51 节点） | 略好 |
| p90 | 2.14 ms（491 节点） | **22.0 ms**（2,467 节点） | **×10** |
| p99 | 22.0 ms | **143.4 ms**（15 次中位） | **×6.5** |

⇒ 结论有变：**典型会话仍然可以忽略（p50 < 0.5 ms），但大图会话（约 2,300 节点）的渲染已到 143 ms 量级**。
每步注入都要渲染一次，这已经不是噪声 —— 列成候选 **K-16（大图增量渲染）**。
