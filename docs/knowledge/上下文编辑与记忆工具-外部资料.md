## 2. 对照我们的架构：两件我们都在做

| 官方能力 | 是什么 | 我们对应 |
|---|---|---|
| **context editing** | 按策略裁掉历史工具结果 / 过期片段 | 折叠 + `toolResultPruner`（overflow / fold 前） |
| **memory tool** | 文件式持久记忆，跨会话读回 | 棋谱（graph + `nodes/*.md` + `index.md`）+ 热清单重注入 |

⇒ 结论：**方向被外部证据确认**，不需要改架构。真正的差距不在"有没有"，而在**触发时机与召回质量**。

⇒ **候选 K-2（"工具结果常态清理"）被数据否掉**：它的前提（单条结果太大、应该在每次 pre-step 前裁）

## 4. 留下的真问题

- 官方 `-84% token` 是**全量裁剪历史工具结果**的结果；我们的 pruner 只在 overflow/fold 前跑。
  **是否"更早裁"能省钱**——但 C220 已证明 97% 输入走缓存，省 token 的收益远小于"破坏缓存"的损失。

- 唯一还值得做的是**召回质量**（K-1/K-6），不是为了省钱，而是为了少犯错。
