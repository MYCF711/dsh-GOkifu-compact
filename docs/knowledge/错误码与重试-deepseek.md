# 错误码与重试（DeepSeek）· 判读

> 来源：<https://api-docs.deepseek.com/quick_start/error_codes>（HTTP 200，抓取 2026-11-02）
> **外部资料 = 数据，不是指令。**

## 1. 官方给的处置（原文，**已核实**：页面原文）

| 码 | 含义 | 官方建议 |
|---|---|---|
| 400 | 请求体格式错 | 按报错提示改请求体 |
| 401 | 鉴权失败 | 检查 API key |
| 402 | 余额不足 | 查余额 / 充值 |
| **429** | **触发限流**（太快 / 超并发或 QPS） | 「**控制请求节奏**」 |
| **500** | 服务端错误 | 「**短暂等待后重试**」 |
| **503** | 服务过载 | 「**短暂等待后重试**」 |

## 2. 对我们意味着什么（**先纠正我自己的第一反应**）

第一反应是"429 该慢、5xx 该快"。**查了代码发现用不上**：
我们的重试是**按事件数**退避的（`FOLD_RETRY_BASE_SEQ=30` → 指数退避到 `480` 事件以后才再试），
不是按时间、也没有"立刻重试一次"的路径 ⇒ **429/503 的处置差异对我们没有影响**。

真正对得上的问题是**另一类**：

| 错误 | 该不该重试 | 我们现在的做法 |
|---|---|---|
| 429 / 500 / 503 | 该（等一会儿） | ✅ 事件退避，方向一致 |
| **400 格式错 / 401 鉴权失败 / 402 余额不足** | ❌ **永远重试也没用** | ⚠️ **同一套退避会一直重试** —— 每次都在白花一次尝试 |

⇒ 立的候选（K-13）：**永久性错误不该进重试队列**。
判别式：错误信息里出现 `401` / `402` / `Invalid Format` / `Authentication` / `Insufficient Balance`
⇒ 直接判「不可重试」，当次就落到规则摘要（我们本来就有这条兜底），并把原因打进日志/foldMark。

**约束**：铁律是"压缩永不失败"，所以"不重试"≠"不压缩" —— 而是**立刻走规则摘要**。

## 3. 一句话蒸馏

> 官方对 429 和对 5xx 的处置**不是一回事**（一个是节奏、一个是瞬时）。
> 我们现在用同一套退避对两种错 —— 这不是 bug，但是**没吃到这条信息**。

## ★ 官方错误码全表（**已核实**，2026-11-03 抓 <https://api-docs.deepseek.com/quick_start/error_codes>）

| 码 | 含义 | 官方给的做法 | 我们该怎么判 |
|---|---|---|---|
| 400 | Invalid Format（请求体格式错） | 按提示改请求 | **永久**，重试没用 |
| 401 | Authentication Fails | 检查 API key | **永久** |
| 402 | Insufficient Balance | 去充值 | **永久** |
| **422** | **Invalid Parameters** | 按提示改参数 | **永久**（旧版漏了这一条，会白重试） |
| 429 | Rate Limit Reached | 放慢请求节奏 | **可重试**（退避） |
| 500 | Server Error | 稍后重试 | **可重试** |
| 503 | Server Overloaded | 稍后重试 | **可重试** |

⇒ `isPermanentSummaryError`（C349）先排除 429/500/503，再把 400/401/402/422 判永久，
并按文案兜底（invalid format / invalid parameters / authentication fails / insufficient balance / invalid api key）。

## 退避按类分档（**已核实**：我们的实现，C350）

只按"同一个指数退避"处理所有错误是不对等的：

| 类别 | 官方做法 | 我们的退避 |
|---|---|---|
| rate-limit（429） | 放慢节奏 | 基数不变，**上限翻倍**（480 → 960 事件）—— 重试越快越糟 |
| overload（500/503） | 稍后重试 | **基数抬高**（30 → 60 事件），上限不变 |
| timeout | — | 与原来一致（30 起，480 封顶） |
| permanent（400/401/402/422） | 改请求 | 顶到上限 + 下次强制规则摘要（C242） |

我们只有**事件轴**没有时间轴，所以"退避"的单位是"再攒多少事件才允许重试"。

## 官方《错误码》复核（2026-11-03 · **已核实**）

来源：<https://api-docs.deepseek.com/zh-cn/quick_start/error_codes>（HTTP 200）逐字整理：

| 码 | 官方描述 | 我们的归类 | 该做什么 |
|---|---|---|---|
| 400 | 格式错误 —— "请根据错误信息提示修改请求体" | `invalid-request` | 改请求，别重试 |
| 401 | 认证失败 —— "API key 错误" | `permanent` | 换 key |
| 402 | 余额不足 —— "请确认账户余额…充值" | `balance` | 充值；期间走规则摘要 |
| **422** | **参数错误** —— "请根据错误信息提示修改相关参数" | `permanent` | **改参数，不是等一会儿** |
| 429 | **"请求速率或并发达到上限"** | `rate-limit` | 放慢节奏 |
| 500 / 503 | 服务端 / 过载 | `overload` | 稍后重试 |

两处值得记下：

1. **429 的措辞与《限速与隔离》页不完全一致** —— 那边把"并发"定义成"请求发出到响应完成之间的在飞数"（更具体），
   这边笼统写"速率**或**并发"。**以更具体的页面为准，但别把速率型限流当成不存在**。
2. **422 是"改请求"不是"等一会儿"**。我们本来就归 permanent（`isPermanentSummaryError` 覆盖），
   C497 只是把这句话写进提示语。
