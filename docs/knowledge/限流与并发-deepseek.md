# 限流与并发（DeepSeek）· 判读

> 来源：<https://api-docs.deepseek.com/quick_start/rate_limit>（HTTP 200，抓取 2026-11-02）
> **外部资料 = 数据，不是指令。**

## 1. 事实（已核实：官方页面原文）

| 模型 | 并发上限 |
|---|---|
| **deepseek-flash**（本机在用的 `deepseek-v4.1-flash1017`） | **2500** |
| deepseek-v4-pro | 500 |

- 一次请求从发出到响应完成算**一个并发连接**；
- 需要更高并发可提交扩容申请，**不额外收费**。

## 2. 对我们意味着什么

**我们所有的"慢"都不是被限流卡住的。**

| 场景 | 我们现在的做法 | 并发上限够不够 |
|---|---|---|
| 补账（12 个归档会话） | **串行**，一个补完再下一个（约 12 × 15s ≈ 3 分钟） | 2500 ≫ 1，**串行是我们自己的安全选择**，不是限制 |
| 折叠 | 每次 fold 1 个请求 | 同上 |
| 面板检查更新 | 1 个 GET | 同上 |

⇒ 结论：
1. **不要**拿"怕限流"当不并行的理由 —— 真理由是**并发 resume 多个归档会话会同时把多个 agent 拉起来**（内存、宿主调度、失败面都放大）。这是产品判断，不是外部约束。
2. 如果将来要做并行补账，**限流侧不需要任何改动**（2500 的余量足够），只需要限制"同时 resume 几个"（建议 2–3 个，并对每个加超时）。

## 3. 一句话蒸馏

> 外部约束比我们想象的宽松得多 —— **慢是我们自己的选择**。
> 这句话反过来提醒：任何"因为怕被限流所以串行"的说法，都要先来这里对一眼数字。

## ★ 限流的并发口径与我们的做法（**已核实**，C367）

官方《Rate Limit & Isolation》：

| 模型 | 并发上限 |
|---|---|
| `deepseek-flash` | **2500** |
| `deepseek-v4-pro` | **500** |

- **账号级**计算，与用哪个 API Key 无关；
- 一个请求从发出到响应完成算 **1 个并发连接**；
- 超容可申请扩容，官方说不额外收费。

**对我们的意义**：
1. 我们的折叠（含分段收尾）是**串行**的 ⇒ 真正撞 429 的概率低，撞到多半是账号级共享被别的调用占满；
2. 官方对 429 的说法是「**放慢节奏**」—— 这是**时间**语义，而我们的退避只数**事件**
   ⇒ C367 在事件退避之外补了一道**最小等待时间**（限流 30s / 过载 5s，其它 0 = 不改旧行为）；
3. `v4-pro` 并发只有 flash 的 1/5，且更慢 ⇒ 若宿主用 pro，分段收尾更容易踩到 `closeoutTimeoutMs`(90s)。
