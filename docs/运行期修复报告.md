## Bug 1 · 把系统注入当成了「用户的话」

**现象**：`graph.json` 里出现 `<hindsight_knowledge>`、`<system-reminder>`、`Subagent …` 等「user 节点」，
根目标与约束集被记忆注入污染 —— 热上下文里的 CONSTRAINTS 全是从 Hindsight 说明里抽出来的句子。

**根因**：`user/message` 这个事件类型下，`source.kind` 有 8 种：

```
user(3) / agent-instructions(2) / runtime-context(1) / skill-catalog(1)
/ plugin:hindsight(2) / agent-message(2) / subagent-settled(2) / chess-context(6)
```

旧代码只排除了自己注入的 `chess-context` 和压缩 checkpoint，其余全建 UserNode。

**修法**：`keeper.mjs` 加 `isHumanMessage()`，只有 `source.kind ∈ {user, prompt, human}` 才建 UserNode；
其余只计数（`state.injected`）不进图。

**验证**（同一份 1024 事件回放）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| user 节点数 | 13 | **3**（全是真人输入） |
| 约束条数 | 4（全是 Hindsight 说明） | **0**（这个会话的真人消息里确实没有约束句） |

## Bug 2 · 只读工具的文本被当成「失败」

**现象**：55 条 failure 里 30+ 是误报 —— `get_goal` 返回的 JSON（含「失败」二字）、
`hindsight_search_knowledge_pages` 的记忆正文、`read` 读到的代码注释（含 `EACCES`）全被判 failure。
热上下文因此被垃圾失败边塞满。

**根因**：旧 `verifier.mjs` 用一条 `ERR_RE` 通吃所有工具，且匹配词包含「失败」「错误」「Error」
这类**叙述性词汇**。只读工具的返回体天然充满这些词。

**修法**（分层判定，顺序即优先级）：

| 优先级 | 信号 | 适用范围 |
|---|---|---|
| ① | `isError`（宿主标记） | 任何工具 |
| ② | `[exit code: N]`，N≠0 ⇒ failure；N=0 ⇒ **success（最终裁决）** | 任何工具 |
| ③ | `N passed` / `N failing` 计数 | 任何工具 |
| ④ | 行首错误行（`Error:` / `Traceback` / `ENOENT`…） | shell/write；只读只认硬错误 |
| ⑤ | 写类成功（diff / 写入回执） | write |
| ⑥ | 其余 ⇒ **unverified**（绝不判 success） | — |

关键取舍：**有退出码时只信退出码**。`bash("sed -n '1,100p' 源码")` 的 exit 0 输出里到处是 `error:`，
用关键词覆盖 exit 0 会制造大批误报。shell 没有退出码时（后台任务/流式）直接 unverified，不猜。

**验证**（同一份回放）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| failure 边 | 55 | **8** |
| 其中误报 | ~30（人工核对） | **0**（8 条逐条核对：read_image 文件过大、3 个目录不存在、curl 超时、grep 无匹配、2 个脚本真报错） |
| unverified | 116 | 173（判不出来的老实标未验证） |

## Bug 3 · 落盘滞后

**现象**：`graph.json` 的 mtime 比会话落后很久；重启/崩溃会丢掉最后一个窗口的落账。

**根因**：旧代码 `if (st.events % 25 === 0) this.#flush(session)` —— 每 25 个**有变化**的事件才写一次，
且只在 `agent/status: idle` 时补写。长会话里 idle 很少。

**修法**：`#scheduleFlush()` —— 任何变化都排一次 1.2s 后的写，同一会话合并（debounce）。
`graph.md`（人读视图）只在 idle 和 fold 后渲染：bench 实测 2000 条边渲染 md 要 **380ms / 386KB**，
不能每 1.2s 做一次。

## Bug 4 · 热上下文在失败边多时会爆炸

**现象**：bench（2000 边）里 `renderLedger` 输出 **28,800 tokens** —— 比它要省的上下文还大。
「所有已探明死路常驻」在 1201 条失败边的现实里不可行。

**根因**：降级链只截短每条的长度，没有**条数上限**。

**修法**：五级降级 + 硬预算：

| 档位 | 策略 |
|---|---|
| L0 | 全量：意图 + 原因 + seq |
| L1 | 原因截短 |
| L2 | 只留意图 |
| L3 | 只留 id + 意图前 22 字 |
| L4 | 最近 50 条（L3 格式）+ **汇总行**：`… 1151 earlier dead ends omitted for budget: e1..e1150 — full text in graph.md` |

原则：**能逐条列出的绝不合并**；实在列不下时用汇总行保证「可发现」，而不是假装不存在。
摘要用的 `renderFacts` 另有一套上限（800 条：最早 80 + 最近 720 + 汇总行），因为摘要是一次性成本。

**验证**（bench 2000 边 = 1201 条失败边）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 热上下文 tokens | 28,800 | **559**（预算 500，超 12%） |
| 渲染耗时 | 4.6ms | 4.42ms |
| 丢失边数 | 0（但 token 爆炸） | 1151 条进汇总行（**可发现**，全文在 graph.json） |
| 摘要事实块 | 222,050 字符 | **81,167 字符**（约 1/3） |

## Bug 7 · `read` 读到含 `[exit code: 1]` 字样的文件，被判成 failure

**现象**：`read` 一个测试文件（文件内容里写着 `[exit code: 1]` 这个测试用例名），整条 read 被判 failure。

**根因**：`EXIT_RE` 对所有工具生效。但退出码只属于**执行类工具**（shell）；read/write/mcp 返回的是**内容**，
内容里出现 `[exit code: N]` 只是文本。

**修法**：退出码解析移进 `if (cls === "shell")` 分支。

**验证**：新增单测「read 读到含 exit code 字样的文件仍是 unverified」；回放里这类边消失。

## Bug 8 · 模型在失败边多时会丢掉全部约束（多规模实测）

**现象**：多规模测试（5 / 15 / 30 条失败边）里，约束保留不稳定：

| 场景 | 第一次 | 强化 prompt 后 |
|---|---|---|
| A（5 条失败边，2 条约束） | 2/2 | **0/2** |
| B（15 条失败边，3 条约束） | **0/3** | 3/3 |
| C（30 条失败边，3 条约束） | 3/3 | 3/3 |

**根因**：约束保留依赖模型「遵守指令」。在失败边占满输出预算时，模型会优先保失败边、牺牲约束 —— 而约束丢失 = **任务漂移**，比失败边丢失更致命。

**修法（设计层面的改动）**：**约束不经过模型**。

`engine.summarize()` 在模型输出之后，机械追加一段：

```markdown
## 约束（机械保留，逐字；不由模型改写）
- 必须保持公开 API 响应字段不变，不许改接口契约。
- 不许动 prod 配置文件，任何改动只能走测试环境。
```

来源是 `renderFacts` 里的 `CONSTRAINTS_VERBATIM` 段（规则抽取、逐字）。模型写不写都不影响这段出现在产物里。

**验证**：
- 单测 `extractConstraintsBlock 从事实块里逐字取出约束` / `没有约束时返回空串`
- 81 项全绿

**教训**：凡是「必须 100% 发生」的事，不要交给模型 —— 用规则做，让模型只做表达。
