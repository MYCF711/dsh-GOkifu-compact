# P1-4 实测：热清单就地替换（surface 永远只有一条）

> 2026-10-29 · 对应 HANDOFF 未完成清单第 1 项（原 P1-4「彻底修法」）
> 复现：`node test/real-ledger-replace.mjs`（真实包）、`node test/run.mjs engine-harness`（假 DSH 接线）

## 一 · 问题：插件自己的热上下文成了最大的上下文消费者

旧版每注入一次清单就**追加**一条新的 `user/message`，旧的一条都不替换。拿真实会话日志数一遍
（`<DSH_HOME>/sessions/*/session.v4.jsonl.zstd`，统计 `source.kind === "chess-context"` 的 user/message 事件）：

| 会话 | 注入条数 | 累计字符 | ≈ tokens |
|---|---:|---:|---:|
| `session-5acafe42`（就是那个死循环会话） | **176** | **809,819** | **≈ 270,000** |
| `session-365cdcf6` | 103 | 238,083 | ≈ 79,000 |
| `session-5787ac6b` | 74 | 155,569 | ≈ 52,000 |
| 其余 9 个会话 | 22 | 21,875 | ≈ 7,300 |
| **合计** | **375** | **1,225,074** | **≈ 408,000** |

`session-5acafe42` 的对比尤其刺眼：它的上下文峰值是 672,392 token，其中**约 27 万 token 是这个插件
自己追加的热清单**（226 次压缩里 223 次失败 ⇒ 那些消息一条都没被折掉）。
也就是说：**插件为了省上下文而注入的东西，成了上下文爆炸的主因之一。**

## 二 · 修法：用 DSH 官方的 surface 替换机制就地改写

DSH 的 surface 只支持两种操作（`dsh-session/lib/types/surface.js`）：`append` 与
`{op:"replace", startSeq, endSeq}`（+`sourceEventSeqs` 逐条列出被遮蔽节点）。官方
`system-prompt` 的 in-history 提交、`compaction-tool-result-pruner` 都在用替换。

所以 `pre-step` 里改成：

```
找到当前 surface 上最后一条 source.kind === "chess-context" 的节点
  ├─ 有 → session.append("user/message", 新清单, {
  │         surfaceOp: { op: "replace", startSeq: 旧.seq, endSeq: 旧.seq },
  │         sourceEventSeqs: [旧.seq],
  │       })     ← 就地替换；**不进** decision.messages（surface 已经是新的）
  └─ 没有（首次 / 被 fold 遮蔽）→ 走原来的追加路径（decision.messages）
```

配套：
- 内容与 surface 上那条**一字不差**时直接返回（不写日志、不推进 `contentGeneration`）
- 锚点失效（刚好被 fold 遮蔽）时 `append` 会抛错 ⇒ **捕获后退回追加**，绝不因为这里失败而丢信息
- 限流保持原样（≥40 事件、失败边 +5）：替换不占额外 prompt，但会写一条日志事件并推进
  `contentGeneration`（⇒ 下游 `startsSeries`），节奏不动最稳
- 被 fold 遮蔽后必须**立刻补回**（不等限流）——否则模型会在一段时间内看不到死路清单
- 新增配置 `hotLedgerReplace`（默认 `true`），置 `false` 可退回旧的追加行为

## 三 · 验证

### 3.1 真实包上的机制验证（`node test/real-ledger-replace.mjs`，8/8）

| 用例 | 结果 |
|---|---|
| 追加一条清单 → surface 多一个节点 | ✓ |
| 替换旧清单 → surface 仍是「system + 一条清单」，旧 seq 消失 | ✓ |
| **连续替换 50 次 → 仍只有一条清单**（这就是 P1-4 要的形态） | ✓ |
| `surfaceOp: "replace"`（字符串）被拒绝 —— 必须是对象形状 | ✓ |
| 替换**不在 surface 上**的 seq（已被 fold 遮蔽）会抛错 ⇒ 引擎必须先检查 | ✓ |
| `sourceEventSeqs` 漏掉被遮蔽节点会抛错 | ✓ |
| 替换后仍能按 `source.kind` 找回「当前清单」（锚点定位依据） | ✓ |

### 3.2 假 DSH 接线验证（`node test/run.mjs engine-harness`，13/13）

- 「清单已在 surface 上时就地替换」：第一次追加 → 第二次**替换**（`decision.messages` 里没有新增、
  surface 上仍只有 1 条、内容是新的失败数）；再调一次被限流门拦住（surface 长度不变）
- 「被 fold 遮蔽后立刻补回」：手工把清单节点从 surface 移走 → 下一次 `pre-step` 立刻重新注入
- 变异自检：把 `hotLedgerReplace` 强制为 false ⇒ P1-4 用例变红（`src/engine.mjs` 恢复后 sha256 逐字一致）

## 三·五 · 历史包袱清理（配套）

surface 只支持 append/replace，**不能删除节点** ⇒ 老会话上已经压着的旧清单不会自动消失。
但可以逐条**替换成一行占位**（内容早过时：最新那条清单覆盖同样信息，全量轨迹在 graph.json）。

实测（把会话日志的 surface 折一遍，看还剩多少清单节点）：

| 会话 | surface 节点 | surface 上的清单节点 | 合计字符 | ≈ tokens |
|---|---:|---:|---:|---:|
| `session-5acafe42` | 806 | **44** | **295,255** | **≈ 98,000** |
| 当前会话（重启后） | 732 | 4（3 条旧 + 1 条新） | 3,593 | ≈ 1,200 |

清理逻辑：进程内每个会话跑一次（`legacyElided`），保留最后一条，其余 >200 字符的换成占位；
幂等（占位 < 200 字符，下次跳过）。测试：harness「P1-4 配套：历史遗留的旧清单被换成一行占位」；
变异自检（关掉清理 ⇒ 用例变红）。

## 四 · 遗留（不虚报）

1. **历史清单只能「变空」不能「消失」**：占位仍占 surface 的一个节点（约 100 字符）；
   彻底消失要等下一次 fold 把它们遮蔽。
2. **本机 DSH 里的运行实例还没带上这个改动**：插件在启动时 import，需要再重启一次才生效
   （重启前，运行中的实例仍按旧逻辑追加）。
3. **`startsSeries` 的连带效应未做端到端测量**：替换会推进 surface 的 `contentGeneration`，
   下游会把这次请求标成新 series。替换频率与旧的追加频率相同（同一套限流门），
   但「series 标记」对网关侧 prompt 缓存的实际影响没有实测（需要真实长会话的计费数据）。
