# 热清单标记 A/B 实验（2026-10-29 · 子代理盲测）

> 目的（goal ③）：**带手割标记 vs 不带**，在真实模型上验证标记是否真的让 agent 少走死路。
> 复现：`node test/ab-render.mjs [--scenario=trap] [--dir DIR]` —— 同一张棋谱，三种标记档位各渲染一份。
> 受试者：`subagent`（独立上下文、**只看清单**、自足虚构场景 `svc-4021`，不需要读任何文件）。

## 0 · 三个臂

| 臂 | `hotLedgerMarkers` | 模型看到什么 | 本场景 token |
|---|---|---|---|
| A | `semantic`（默认） | `[dead redundant:e1]` / `[blocked:permission]` + 按用到的标记**动态生成图例** | 315 / 320 |
| B | `terse` | 只有三态 `[dead]` / `[blocked]`（说不出是什么被挡住），图例仍在 | 275 / 314 |
| C | `off` | 完全不打标记（退回纯失败列表） | 177 / 170 |

每个受试者收到同一句话：「只依据这段清单作答，不读文件、不执行命令」，然后要求一行 JSON：

```json
{"next_action":"…","retry_now":["e2"],"retry_when":{"e3":"…"},"take_working_path":true,"why":"…"}
```

`retry_now` = 这一轮就要重新执行的失败做法（**打分主项**：重试一条已证明无效的路 = 浪费一轮）。

## 一 · 实验 1：错误文本已经说清了该怎么做（3 臂 × 3 样本）

场景：`WORKING: user → n2 (exit 0)`；三条失败边分别是
`e2` 同终点（dead + redundant）、`e3` EACCES（blocked:permission）、`e4` 缺文件（blocked:missing-resource）。

判据（各 1 分）：① 不重试 e3 ② 说得出 e3 的**重开条件** ③ 不重试 e2 ④ 走 WORKING 路 ⑤ 不重试 e4。

| 受试者 | 臂 | `retry_now` | 走 WORKING | 得分 |
|---|---|---|---|---|
| a568981d | A | `[]` | ✓ | **5/5** |
| b4bc93de | A | `[]` | ✓ | **5/5** |
| 623a9f54 | A | `[]` | ✓ | **5/5** |
| 49cece0d | B | `[]` | ✓ | **5/5** |
| 048d1375 | B | `[]` | ✓ | **5/5** |
| 80ea1332 | B | `[]` | ✓ | **5/5** |
| 3a0fbacb | C | `[]` | ✓ | **5/5** |
| 5b54fa15 | C | `[]` | ✓ | **5/5** |

**结论：8/8 满分，三个臂没有差别。** 原因写得很直白 —— 报错原文本身就能推出该怎么做：
`EACCES: permission denied` 就是权限、`cp: cannot stat` 就是文件不在、`expected 1 got 2` 就是做法错了。
**与 1.1.0 那次三态 A/B（行为差异为零）结果一致。**

## 二 · 实验 2：错误文本**误导**（2 臂 × 6 样本）—— 这才是标记的适用面

场景（`--scenario=trap`）里，最诱人的下一步是错的：

```
- e2 "再跑一遍测试（上次可能是 flaky）" → Error: flaky test run aborted (SIGKILL) after 12s [dead redundant:e1]
```

`e2` 的报错**长得像可重试**（flaky / SIGKILL / 12s），但它到达的局面与成功边 `e1` 相同 ⇒ 重跑只会再撞同一堵墙。
**「它与 e1 等价」这件事，只有手割标记说得出来 —— 报错原文里没有。**

判据（各 1 分）：① **不重试 e2** ② 不重试 e4 ③ 走 WORKING ④ 说得出 e3 的重开条件。

| 臂 | 受试者 | `retry_now` | 得分 | 关键理由（原话节选） |
|---|---|---|---|---|
| A（标记） | c059ab65 | `[]` | **4/4** | 「e2 已死且与工作路径 e1 重复」 |
| A | 00a6cf79 | `[]` | **4/4** | 「e2 与它重复，是死路」 |
| A | b64af993 | `[]` | **4/4** | 「e2 被 e1/n2 工作路径覆盖已判 dead」 |
| A | 58202197 | `[]` | **4/4** | 「e2 判 dead + redundant:e1，重跑拿不到新信息」 |
| A | 8e631a38 | `[]` | **4/4** | 「e2 是 dead 且 redundant:e1 —— 工作边 e1 已到达同一位置」 |
| A | 48a0ae5d | `[]` | **4/4** | 「e2 是 dead+redundant（working 路径已到同一位置，重跑无新信息）」 |
| C（无标记） | 436fdca7 | **`["e2"]`** | 3/4 | 「SIGKILL(12s) 是外部中止，**不是对该做法的否定性证据**」← 重跑了等价死路 |
| C | f381bfb3 | `[]` | 4/4 | （把 e2 的重试条件写成「确认 SIGKILL 不是代码问题之后」） |
| C | d5ba9c2a | `[]` | 4/4 | 「根因是缓存键算错，三次失败都未触及根因」 |
| C | a471d5e7 | `[]` | 4/4 | 「flaky 假设与 e4 的证据矛盾：expected 1 got 2 是稳定错值」 |
| C | b337d6dd | `[]` | 4/4 | 「e2 盲目重跑已被 SIGKILL 证明不是 flaky」 |
| C | 906eb407 | `[]` | 4/4 | 「e2 同条件重跑仍会 SIGKILL」 |

### 读数

| 指标 | A（带标记） | C（不带标记） |
|---|---|---|
| 重试等价死路 | **0 / 6** | **1 / 6** |
| 总分 | 24 / 24 | 23 / 24 |
| 理由里**引用了标记** | **6 / 6** | 0 / 6（只能引报错原文） |

### 诚实结论

1. **标记确实被读、被用** —— 带标记的 6 次回答，6 次都在 `why` 里直接引用了 `dead` / `redundant:e1`；
   不带标记的 6 次只能从报错原文反推，其中 1 次推错并打算重跑等价死路。
2. **但差异不显著** —— n=6，Fisher 精确检验 p≈0.5。这是一条**方向性**证据，不是统计结论。
   能确定的只有：标记不改变「报错原文已经说清」的场景（实验 1：零差异），
   只在**报错原文误导**时有价值（实验 2：1/6 vs 0/6）。
3. **所以默认值怎么定**：保留 `semantic` 为默认（成本 +6.6%，见第三节），
   并把档位做成配置 `hotLedgerMarkers: semantic | terse | off` —— 预算敏感的场景可以关掉，
   关掉后热清单退回纯失败列表（本场景 320 → 170 tokens）。

## 三 · 全库代价与收益（同一语料 45 个真实会话，新旧代码各跑一遍）

复现：`node test/measure-ledger.mjs <out.json>`；旧版在 `git worktree add <dir> 52f49bd` 出来的检出里跑同一文件。

| 指标 | 旧（v1.3.4 / 52f49bd） | 新（v1.4.0） |
|---|---|---|
| 热清单 tokens 合计 | 19,267 | 20,579（**+6.8%**） |
| **带原因的失败边** | 89 | **209（2.35×）** |
| 展示失败边条数 | 139 | 139（没为了省钱少列） |
| 平均降级档位 | L1.40 | L1.42 |
| 三档对照（semantic / terse / off，同一语料） | — | 20,645 / 20,639 / **19,649**（关掉标记省 4.8%） |

- 「带原因」从 89 → 209 是这次最大的消费者收益：旧版 L3+ 直接把 `→ 报错原文` 整段砍掉，
  而模型判断「这是不是同一个坑」靠的正是报错原文 —— 实验 1/2 里 **12/12 次回答都引用了它**。
- 代价 +6.8% ≈ 每屏多几十个 token，换 2.35 倍可见原因 + 标记自解释。热清单仍占窗口的 0.2%~0.4%。

### 顺带修掉的性能坑（`node test/bench.mjs 2000`）

| 版本 | 渲染热上下文 |
|---|---|
| 52f49bd | 4.9 ms |
| 本轮（先给每个档位都算手割） | **7.58 ms** ← 回归 |
| 本轮（手割只算一次 + 跳过注定装不下的档位） | **0.478 ms** |

原因是旧版在 1201 条失败边时要为 L0–L3 **各拼一遍 1201 行字符串**（注定装不下还白拼），
且手割分析被放进档位循环里重复 6 次。现在：手割只对尾部 30 条算一次，档位按**每行下界**预判并跳过。

## 四 · 变异自检（证明测试真的锁住了这两件事）

把两处修复同时回滚（图例关掉 + L3+ 重新砍掉原因），跑 `node test/run.mjs markers`：

```
✗ 标记裸奔：只有 blocked 失败、没有成功路径时，图例必须出现
✗ 手割标记的图例：redundant / longer 必须被解释（旧图例从来没有）
✗ 原因在任何降级档位都保留（旧版 L3+ 全砍）
✗ renderFailureLine：level 3 也带原因，只是更短
✗ markers:"off" 完全不打标记；"terse" 只写三态但图例仍在
== 4 passed, 5 failed ==
```

恢复后 `src/ledger.mjs` 的 sha256 与变异前逐字一致（`993a959f…`），全套 104 项重新全绿。

## 六 · 局限（不虚报）

1. **n 偏小**：每臂 3~6 次采样，实验 2 的差异（1/6 vs 0/6）不具统计显著性。
2. **单一模型**：全部采样来自 `group/deepseek-v4.1-flash1017`（与本机默认路由一致）。
3. **合成场景**：两张自足棋谱，不是真实会话回放；真实会话里「等价但报错不同」的边比例未知。
4. **打分是我的规则**：`retry_now` 是否包含某条边是客观的，但「该不该重试」的正确答案由场景设计者（我）认定。
5. **受试者是 subagent**：与 DSH 主会话的 pre-step 注入同源（同一份渲染代码），但注入位置/上下文结构不完全相同。
