## 二 · 逐维度评分

### A · 压缩有效性 —— **21 / 25**

**证据（1.8.1 窗口内，13 次 fold / 9 个会话 / 遮蔽 2,460,294 tokens / 0 失败）**

| 会话 | fold 前真实 prompt | fold 后第一条 | 降幅 |
|---|---:|---:|---:|
| e16faf2b | 814,430 | **228,081** | **−72%** |
| aebc6e78 | 849,854 | **245,496** | **−71%** |
| fcfa5be3 | 723,613 | **214,936** | **−70%** |
| fcfa5be3（第 2 次） | 449,715 | 212,964 | −53% |
| 15a2dcb3 | 449,973 | 226,257 | −50% |
| 9d07d733 | 450,880 | 230,167 | −49% |
| 1331683e（两次） | 449,719 / 450,507 | 247,035 / 221,462 | −45% / −51% |
| a0d03648（两次） | 449,886 / 448,821 | 257,512 / 245,488 | −43% / −45% |
| 31b196f9 | 449,951 | 260,507 | −42% |

- **压缩比** 2,460,294 ÷ 摘要输出（窗口内实测 12,000 量级）≈ **100:1 以上**；被遮蔽的 246 万 token 从后续每一次请求里消失。
- **8 个大会话全部稳定落在 21–26 万**，锯齿周期清晰（涨到阈值 → 压回 30%~50%）。
- **增量语义成立**：`range.mjs` 只压「上一个 checkpoint 之后」，一段历史一生只摘一次；`tier2After` 把过多 checkpoint 合并，避免表面堆积。

**扣 4 分**
1. **同工作量下并未明显优于官方**：steps 600+ 桶的每步平均 prompt，gokifu 427,587 vs 官方 431,724（仅低 1%）；steps 300–600 桶低 6%。增量 fold 的理论优势（不重压、不衰减）在「平均 prompt 大小」这个指标上还没变成可测量的收益。
2. **小窗口会话上 fold 是负收益**：4 个测试会话共 16 次 fold，遮蔽 3.4K–12.6K tokens，但真实 prompt **不降反升** +749 / +2,513 / +2,679 / +1,052。`minFoldTokens` 固定 8000 不随窗口缩放，小窗口下摘要成本大于收益。

### B · 压缩可靠性 —— **16 / 20**

**证据**
- 窗口内 **13 次 fold，0 失败**（`compaction/end` 无 error 事件）。
- **三层降级兑现**：`summaryMode: hybrid` 在摘要模型不可用时退回当前路由，再不行退回**规则摘要（零模型调用）**——今天有 3 次 fold 完全靠规则摘要落地（0 input / 0 output / 摘要 9.8K–13.6K 字符）。
- **事务安全继承官方**：`compactRegion` 的锁、surface 稳定性校验、工具对边界全部由 `BasicCompactionEngine` 负责，本插件只覆盖策略层——这是「不重交一遍 bug」的正确选择。
- **失败即回滚**：`compactIfNeeded` 在 fold 前对图做 JSON 快照，任何未完成路径 `restore()`，保证「foldCount 没变 ⇒ 图也没变」。
- `checkpointSeq` 记的是 checkpoint 消息自身 seq（不是被遮蔽区间起点，后者 fold 后已不存在）。

**扣 4 分**
1. **压缩失败不告警**：`engine.mjs` 的几处 catch 只写 `logger.warn`，没有任何升级机制。上下文是「只增不减」的静默失效——今天这件事真实发生过（详见 §4 参考数据），而当前版本**没有代码阻止它再次静默发生**。
2. **摘要模型故障无自愈路径**：三层降级的第三层是规则摘要，质量明显下降（无模型润色、8–14K 字符），但**没有向使用者说明降级发生了**；热清单里也不提示「你的压缩质量正在降级」。

### C · 上下文质量与判定正确性 —— **13 / 25**

**正面证据**
- **失败记忆逐字保留**：窗口内 199 条失败边，每条都带 `intent` / `errorSnippet` / `evidence seq`，模型无权丢弃（`renderFacts` 把 HARD FACTS 作为 AUTHORITATIVE 输入塞进摘要指令）。
- **热清单可用且便宜**：1,274 字符/次（今天 105 次 / 34 个会话），预算内五级降级，**每一档都保留报错原文**（最省一档也留 25 字）。
- **就地替换生效**：`surfaceOp: replace` 53 次 / append 52 次 ⇒ surface 上永远只有一条清单，不会重现「累积 176 条 / 27 万 token」的旧事故。
- **现场活证据**：本评测会话里，热清单把两条真实踩坑（`e25` ENOENT 路径、`e27` 多帧 zstd）逐字回灌，我当场改法、各一次成功——**这一层是真的在改模型动作**。
- 真实模型对照（历史数据，仅参考）：失败边保留 8/8 vs 官方 4.67/8。

**扣 12 分**

**C-1（扣 7）· 图坍缩导致「死路/冗余」判定全错（当前版本行为，非历史）**

| 统计（1.8.1 窗口内） | 值 |
|---|---:|
| 新增边 | 4,624 |
| **自环边（`from === to`）** | **3,929 = 85.0%** |
| 失败边 | 199 |
| 其中被判 `dead` | **57** |
| 其中带 `redundant` 标记 | **77** |
| **两者合计 = 错误的收敛标记** | **134 / 199 = 67%** |

实测复核：今天判 `dead` 的 109 条（全日）**全部**的「成功参照边」与它指向同一节点，**0 条是真替代路径**。

**因果链**（读源码可验）：
1. `keeper.mjs` 在 `step/end` 用 `worldHashOf()` / `constraintHashOf()` 的真实哈希建节点；
2. `worldHash` 的判据是**触碰文件的 size + mtime**，`constraintHash` 是约束文本哈希——**只读型 step 里两者都不变**；
3. `addAgentNode` 命中 `stateIndex` 时**不新建节点**，返回旧 id；
4. 于是本步所有边的 `to` 都指向已有节点 ⇒ 自环，`from === to`；
5. `tewariAnalysis` 的 `sameEndpoint` 因此恒真 ⇒ `redundant` / `dead` 全线误报。

**对模型的伤害**：热清单会发出 `[dead retry-if:e101]`，语义是「这条路有工作路径避开它，除非那条路失败否则别再试」。而真相是「同一步里另一条命令成功了」。**这会诱导模型过早放弃可行路径**——比信息缺失严重得多，因为它是有毒的确定性陈述。

**C-2（扣 5）· 88% 的边是 `unverified`，成功路径常年缺席**

窗口内 4,624 条新增边：success 333 / failure 199 / **unverified 4,090（88%）**。

后果：热清单的 `WORKING:` 行（当前成功路径）在只读型会话里经常**不存在**（本会话就是：63 条边 60 条 unverified，只有 CURRENT PATH 没有 WORKING）。模型看到的是「我试过很多事，但不知道哪些成了」。

设计上「宁可不判也不误判」是对的，但代价是棋谱最核心的「成功路径」信号几乎全丢。给只读工具补一档弱成功判定（read 到文件存在且非错误行）就能把 88% 里的大部分变成可用信号。

### D · 成本效率 —— **12 / 15**

**证据**
- **1–2 条请求回本**：e16f 一次 fold 花 62.9 万新输入，之后每条请求少带 58.6 万（814,430 → 228,081），17 条请求共省约 **1,000 万 token**。
- **缓存命中时极便宜**：`fcfa` 第二次 fold 只要 6,394 新输入 + 540,672 缓存读 + 4,453 输出；`aebc` 那次是 5,329 + 647,168 + 5,439。
- **规则摘要零成本**：3 次 fold 完全没调模型（input/output 都是 0）。
- 输出侧很省：单次摘要输出 1,201–5,439 tokens（`maxTokens: 8192` 留了充足余量）。

**扣 3 分**
1. **冷缓存首折贵**：62.9 万全新输入一次打出去，对小预算场景是明显尖峰。
2. **小窗口 fold 过频**（见 A 的扣分）：1.2 步一次 fold，为压 2K token 付一次完整调用，净亏。

### E · 运行期开销 —— **14 / 15**

**实测（`node test/bench.mjs 2000`，2000 边 / 1201 失败边压力）**

| 操作 | 耗时 | 说明 |
|---|---:|---|
| 事件落账（一对 assistant + tool/result） | **0.008 ms** | 每步 2 次 |
| 渲染热上下文（500 token 预算） | **0.491 ms** | 输出 323 tokens，降级到 L5 |
| 增量 fold 范围选择 | **0.008 ms** | 2001 个 surface 节点 |
| 渲染硬事实块（摘要用） | 1.132 ms | 81,167 字符，只在 fold 时 |
| 序列化 graph.json | 3.574 ms | 1.41 MB，1.2s debounce |

- 每步固定开销 = 落账 0.016ms + 热上下文 0.491ms ≈ **0.5 ms**，对交互完全不可感知。
- 热清单 323 tokens 占典型 prompt（45 万）的 **0.07%**——这是它敢每步注入的理由。
- 跳档优化真实有效：注定装不下的档位按「每行下界 × 条数」预判跳过，2000 边渲染从 7.6ms 降到 0.49ms。

**扣 1 分**：`graph.json` 每次 debounce **全量重写**（1.41MB，随会话线性增长，5,000 边时约 3.5MB），`index.md` 每次 flush 也整篇重写（~50KB × 84 个会话）。当前规模下可接受，但长会话是线性增长的 IO 账单。

## 六 · 指导意见（按对性能的影响排序）

### P0 · 修自环（直接影响模型决策正确性）

`addAgentNode` 在「新节点 id === 本步起点 id」时**强制新建**，`tewariAnalysis` 排除 `from === to` 的边。这是最小改动，能立刻把 67% 的错误标记降到接近 0。

根本改法：把 `worldHash` 从「触碰文件 mtime」升级为「本步是否改变了世界」——只读步沿用旧哈希但强制新建节点，置换只在「写后收敛到相同文件状态」时触发。

**验收**：`verify-graphs.mjs` 加两条不变量——自环边数 = 0、边/节点比 ≤ 1.5；跑一遍全库 84 个图必须全绿。

### P0 · 压缩失效必须喊出来（防止再次静默）

1. 连续 3 次 fold 失败 → `logger.warn` 升级 + 系统通知；
2. **在热清单里插一行**：`⚠ 上下文压缩已连续失败 N 次（最后错误：…）`——热清单是唯一必然进 prompt 的位置；
3. 降级到规则摘要时同样提示：`⚠ 本次摘要由规则生成（无模型润色）`。

### P1 · 把 88% 的 unverified 救回来（提升成功路径信号）

给只读工具补 `weak-success` 档：read/glob/grep 成功返回且无错误行 ⇒ 记 `weak-success`，**只用于 WORKING 路径推断，不进「已验证事实」段**。这会直接改善热清单里 `WORKING:` 行的命中率。

### P1 · `minFoldTokens` 随窗口缩放

改为 `max(8000, 窗口 × 0.08)`。当前小窗口会话 1.2 步一 fold、fold 后 prompt 反而 +749~+2,679，是净亏。

### P2 · 降低落盘的线性成本

`graph.json` 全量重写改为「按节点增量追加 + 周期压缩」，或把 `nodes/*.md` 改为按需渲染。当前 1.41MB / 2000 边尚可，5,000 边时会成为可感知的 IO。

### P2 · 冷缓存首折的成本削峰

首折前先跑一次轻量预热（或把 `thresholdRatio` 的首折阈值调低，让第一次压缩发生在更小的上下文上），把 62.9 万的尖峰摊薄。
