## 这句话是什么意思

它来自 JS 私有字段/私有方法的**品牌检查**：某个方法被调用时，`this` 不是该类（或其子类）的实例。
在我们的场景里，典型成因是：

1. **同一插件被装载了两份**（旧实例还在内存里，或热重载后新旧类共存）；
2. 压缩引擎被**另一个插件/包装器代理**（例如 preset 里排在引擎前面、对 `ctx.compaction` 做了装饰）；
3. 宿主以**非绑定方式**调用（`const { compactNow } = engine` 之类）。

**结论（有依据的怀疑对象）**：同组里只有一个「包装器」—— `tool-result-pruner`。
它按名字与配置都像是「在压缩过程中拦工具结果」的那类插件；这类实现通常要把 `ctx.compaction`
换成自己的代理对象，于是宿主的 `/compact`（`command-compact`）拿到的是代理，`this` 自然不是
`ChessCompactionEngine` 的实例 ⇒ 正是我们看到的报错。

**还没有证据的部分**（不写死）：

- 若再报同样错 ⇒ 基本锁定 pruner 包装，届时修复方向是「让引擎方法代理友好」（不用 `super`，改为持有基类引用并在包装对象上转调）。

## 重启后复现（2026-11-02T06:27Z）—— 假设 2 排除，锁定「调用方式」

重启（`buildId 73628449623a` / pid 9044 / 1.17.3）后，用户报「不能手动压缩」，日志给出决定性对比：

| 时间 | 会话 | 类型 | 结果 |
|---|---|---|---|
| **14:27:23** | `<SESSION_ID>` | **manual**（`sourceCommandId` 存在） | ❌ `Receiver must be an instance of class ChessCompactionEngine` |
| 14:28:52 | `<SESSION_ID>` | auto（无 `sourceCommandId`） | ✅ 成功 |

⇒ **同一次重启、同一个会话、同一个引擎实例**：自动折叠好、手动压缩坏。
「安装/热重载期间类身份短暂不一致」这个假设被排除（那会连自动一起坏）。

结论：**只有手动路径的调用方式有问题** —— `command-compact` 调用 `ctx.compaction.compactNow(...)` 时
`this` 不是引擎实例（把方法摘下来调、或经代理转调）。自动路径由我们自己 `this.compactIfNeeded(...)` 调用，所以不受影响。

## 修复（C214）

引擎在**构造时**把三个公开入口绑定到自身：

```js
for (const name of ["compactNow", "compactRegion", "compactIfNeeded"]) {
  this[name] = this[name].bind(this);
}
```

- 摘下来调用（`const fn = engine.compactNow; fn(...)`）仍然指向真身 ⇒ `super.compactNow(...)` 的私有品牌检查通过；
- 对「包装器在构造后复制方法引用」的场景同样有效（复制到的是绑定版本）；
- 测试 **C214**：摘方法调用不许抛；绑定后 `compactNow/compactRegion` 必须是 bound function（没有 `prototype`）。

**验证方式**：重启后在新会话（或本会话）执行一次 `/compact` —— 应当成功并留下 `trigger: "manual"` 的 foldMark。
