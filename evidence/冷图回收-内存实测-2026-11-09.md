# 冷图回收：内存实测与四条风险的闭环（2026-11-09）

> **性质**：只读实测 + 代码修复。**0 模型调用、不写 home、不删磁盘**。
> 唯一碰真实数据的是「读 `graph.json`」与「读它的 mtime」。私有会话 id **不出仓库**（按名次编号）。
> 生成于 2026-11-09；量的是本机真实落盘根 `<DSH_HOME>/chess-context`（1592 张 `graph.json`）。

---

## 0. 一句话

**这台机器上 1592 张真实棋谱图若全部驻留 = +295.7 MB 堆 / +418.1 MB RSS；走闸门释放后堆只剩 +0.3 MB，RSS 在第 8 秒回到基线。磁盘一个字节没动。**

这是「无意义的内存占用」那个洞的定量闭环 —— 不是估算，是可复跑的一个脚本。

---

## 1. 问题到底是什么

`graphs` / `runtime` 是**按会话常驻**的（`docs/架构-房间契约.md` §R09「状态归属」当时写着「本次不修」）。插件**没有任何清理路径**：窗口关掉、会话归档，图还在进程里。

进程活久了就是「一千多个会话的图全在内存里」。C658 补了闸门（五条件），C659 补了三条风险并把长进程 RSS 验掉。

---

## 2. 怎么量的（可复跑）

```bash
# 最大的 12 张（快，约 5 秒）
node scripts/graph-cache-memory.mjs --home "$DSH_HOME/chess-context" --top 12

# 全部 + 释放后空转 20 秒采 RSS（约 1 分钟）
node scripts/graph-cache-memory.mjs --home "$DSH_HOME/chess-context" --all --soak 20
```

脚本做的事：
1. 只读扫 `<home>/sessions/*/graph.json`，按字节降序取前 N（或全部）；
2. 起一个 `--expose-gc` 子进程，把图 `JSON.parse` 进 `engine.graphs`（模拟「全驻留」），`gc()` 两次后量 `heapUsed` / `rss`；
3. 走**公开闸门** `releaseColdGraphs()` 全部释放，等一拍再 `gc()` 复量；
4. 逐张比对 `mtimeMs`，**必须全未变**；
5. `--soak` 时每秒采一次 RSS，看它到底会不会还给系统。

退出码 0 = 七条断言（全部释放 / graphs / runtime / sessionRefs / lastSeen 清空 / 堆回落 / 磁盘未变）全过。

## 4. 四条交接风险的闭环

| # | 风险（C656 交接单原文） | 处理 | 证据 |
|---|---|---|---|
| 1 | 活跃性只认 `agent/status`，未收到该事件的会话可能被 idle 扫回收 | `session/event` / `agent/status` / `#pinGraph` 三处 `#markSeen`；闸门加**第六判据 `recent`**（15 分钟静默窗口） | 用例「C659 静默窗口」：窗口内一律拒收并归因 `recent`，压到 0 后放行 |
| 2 | 维护缝在 fold 成功但未到下一次 full flush 的窗口可能丢标量记账 | `#invalidateFullFlush`：fold 成功即作废 `full` 标记，闸门必须等到**下一次成功的 full 落盘** | 用例「C659 fold 成功会作废 full 标记」：真跑一次 fold，之后拒收归因 `no-full-flush`，idle full flush 后恢复放行 |
| 3 | `sessionRefs` 仍可能保留归档 Session 引用 | 回收时一并删 `sessionRefs` 与 `lastSeenAt`；**另加封顶 4096 的 `seenIds`**（只存 id 字符串）保住「本进程处理过这个会话」这条信息 | 用例「C659 回收会一并释放 sessionRefs 与 lastSeen」（归零 + 重载后重新挂上）与「C659 回收之后仍然认得出…」（归档收尾不被静默跳过，且没见过的 id 不硬做） |
| 4 | 真实长进程 RSS 未验 | 新增 `scripts/graph-cache-memory.mjs` + `--soak` | §3：RSS 第 8 秒从 479.6 掉回 **67.4 MB** |

**风险 4 的结论要更正 t6 复核**：交接单写的「RSS 不会立刻归还（V8 保留页）…长跑进程的真实收益是「不再继续增长」，不是「当场把 RSS 还回系统」」——**只等了一拍**。实测第 8 秒 decommit 就把 418 MB 还回去了。所以这个功能**是真的把内存还给系统**，不只是停止增长。

---

## 5. 边界（别把上面的数读过头）

1. **这是"单进程内加载并释放"的测量**，不是 DSH 主进程的长跑观测。真实收益取决于「会不会攒到 1592 张」——取决于用户开了多少会话；但**上限与释放效率**就是上面这些数。
2. **158 张图 ≠ 每台机器都 +418 MB**。图上限受会话数与单图大小影响；本机中位数远小于最大值。
3. **释放后第一次事件要重读磁盘**（`graph.json` + 可能的 nodes）。这是回收的**代价**，由「静默 15 分钟 + 保留当前热图」压住：真正马上要用的图不会被收。
4. **不做磁盘收益**：这个功能**不应该**改变磁盘（实测 mtime 全未变）。任何"回收顺便清理磁盘"的想法都不在范围内。
5. **不默认关闭**：冷图回收不是可选特性，是资源生命周期；出问题时该调的是静默窗口，不是关掉它。
