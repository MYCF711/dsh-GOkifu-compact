## #9 `foldRange` 显式 forgotten 边界

| 项 | 内容 |
|---|---|
| 想解决什么 | 折叠区间之外、但被「遗忘」的历史（既不在摘要也没被折叠）目前只能靠**推断**（`closure` + `preGraph`）；给出显式边界后，可以回答「这条 seq 到底被谁覆盖」 |
| 要动什么 | **`graph.json` schema**（新增字段），以及 `foldMark.closure` 的语义 |
| 风险 | **高**：schema 变更 ⇒ 旧图读不了（`version` 不符直接重建空图，`full` 落盘会覆盖）；影响所有历史会话 |
| 测试策略 | 纯函数级（区间代数）+ 一次迁移脚本 dry-run；**必须先有备份与回滚** |
| 什么时候做 | **不要现在做**。等重启后拿到新 fold 的真实 `closure` 样本，再判断是否真的缺这层信息 |
| 结论 | ⛔ 暂缓（理由：schema 变更 + 无真机样本双重风险） |

## #10 fold-planner 预算两档动态化

| 项 | 内容 |
|---|---|
| 想解决什么 | 现在「折多少」用的预算是**静态两档**；若能按窗口规模/增长速率动态选档，可减少「折得太碎/太早」（成本口径里 share<30% 的那部分） |
| 要动什么 | `src/rooms/fold-planner.mjs`（纯函数）+ `engine` 传参；**不动 schema** |
| 风险 | **中**：改变折叠区间选择 ⇒ 直接影响 `bench 415 tokens` 与「失败边保留 8/8」两条硬判据；若变差必须能一眼看出 |
| 现有护栏 | C127/C128（规划器随机不变量）、C59（渲染不变量）、bench-repro、`hot-inject` 随机用例 |
| 测试策略 | ① 先加**判据**（当前档位选择的性质：区间单调、门槛不破、保留不超界）；② 再实现两档；③ bench 必须 ≤415 且失败保留仍 8/8，否则回退 |
| 什么时候做 | **可以现在做**（不碰 schema），但必须接受「行为改变在重启前无法真机验证」 |
| 结论 | 🟡 可做，但要按「先判据、后实现、bench 说了算」的顺序；本轮未开始（守夜期不加行为改动） |

## 重启后第一件事（决定这两条的取舍）

1. 跑 `evidence/重启验收清单` 六步；
2. 看**第一次新 fold** 的 `closure` / `boundary` / `quality` 是否仍然全 1、`openAtEnd=0`；
3. 看 `budgetFloorOver` / `budgetIrreducible` / `overBySession` 的**首次分布**：
   - 若 `budgetFloorOver` 占比高 ⇒ 说明超预算主要来自「不可裁的下限」，**#10 的收益有限**，优先做别的；
   - 若 `budgetIrreducible` 占比高 ⇒ 说明「再省就得丢失败记忆」，**不要动预算**；
   - 若两者都低 ⇒ 主要是表达冗余 ⇒ #10 值得做，但先做「表达压缩」类改动（更安全）。
